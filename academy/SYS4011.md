## 要注意的问题<img src="./icons/didi.gif" /><img src="./icons/microsoft.gif" /><img src="./icons/paypal.gif" /><img src="./icons/kingdee.gif" /><img src="./icons/baidu.gif" />

八条原则速览（具体判断走下节"答题 SOP 决策树"：容量与热点看 STEP 7，异步与削峰看 STEP 8，故障与冗余看 STEP 11，代价权衡看 STEP 13）：

1. 提高硬件能力有上限：服务器增加到某个程度后，系统所能提供的并发访问量几乎不变，加机器不能根本解决问题。
2. 分层：横向切分，每层只承担单一职责，层与层之间有清晰边界；逻辑上分层，物理上可分可合部署以使用更多计算资源。
3. 分割：纵向切分，高内聚低耦合，先粗粒度再细粒度，利于开发维护，也利于分布式部署、提升并发与扩展。
4. 使用缓存：空间换时间，是网站优化的第一定律；CDN、反向代理、热点数据都是对缓存的使用。
5. 消息队列：解耦 + 削峰 + 异步。
6. 分布式开发：不同服务部署在不同机器节点，一个服务也可部署多台机器，利用 Nginx 负载均衡，解决单点、提高并发。
7. 分库分表：分库（读写分离）、分表（水平分表、垂直分表）。
8. 集群与冗余：集群让多台服务器提供相同服务以支撑并发；冗余保证部分服务器宕机时网站仍可正常工作，是高可用性的重要保证。

## 答题 SOP 决策树

拿到任何一道系统设计题都走这一条流程。实战案例见 [SYS401A - 微信支付系统](./SYS401A.md) 与 [SYS401B - 秒杀系统](./SYS401B.md)。

```text
START | 拿到系统设计题
  |
  v
开场话术
  - 我先确认核心业务链、设计边界和成功标准。
  - 然后确定规模、数据与交互方式，走通正常流程，
    再检查并发、故障、监控和验证，最后解释取舍。
  - 每一步只展开与本题有关的分支；已经确认的结论不重复讨论。
  |
  v
STEP 1 | Scope & Success   确认原题、职责边界和成功标准

  |-- D01 题目是不是一个“大平台”？
        YES --> [ 与面试官选定一条核心业务链 ]
        NO  --> [ 按原题范围设计 ]

  |-- D02 面试官已明确指定子系统或处理链路？
        YES --> [ 保留原题的输入、外部参与方和最终结果 ]
             --> [ 可以简化实现，不能换成自己熟悉的另一道题 ]

  固定确认：
    1. 谁发起请求？系统接收什么？最终交付什么？
    2. 哪些步骤由我们控制？哪些依赖外部系统或协议？
    3. “成功”指已受理、已完成处理，还是最终结果已确认？
    4. 本轮不设计哪些内容？

  最小产出：
    一条核心链 + 我方边界 + 最终成功标准 + 明确不做的内容
  |
  v
STEP 2 | System Type   判断系统类型，建立最小骨架

  |-- D03 主要是在完成业务流程？
        YES --> [ Client -> Application Service -> Durable Store ]

  |-- D04 题目本身就是 Cache / MQ / Scheduler / KV Store？
        YES --> [ Client -> Target System ]
             --> [ 不强套 Business Service + DB ]
             --> [ 后续仍检查数据、故障和可观测性 ]

  |-- D05 同时存在协调逻辑与高频执行路径？
        YES --> [ 区分 Control Plane / Data Plane ]
             --> [ 说明控制面管理什么，数据面执行什么 ]
             --> [ 只有安全边界允许时，数据面才使用旧元数据继续服务 ]
             --> [ 权限撤销、所有权变更等不能默认允许旧状态继续生效 ]

  最小产出：
    一个最小骨架 + 关键职责；暂不堆组件
  |
  v
STEP 3 | Deployment Context   租户、权限与部署范围

  |-- D06 是否 Multi-Tenant？
        YES --> [ tenantId 是一等维度 ]
             --> [ 身份来自可信认证上下文，不只相信请求参数 ]
             --> [ 检查 DB / Cache / MQ / Object Storage 的租户边界 ]
             --> [ 明确 Quota / Fairness / Isolation / Noisy Neighbor ]

  |-- D07 Region / Geo 要求是什么？
        无要求
          --> [ 不自动增加 Multi-Region ]

        就近访问
          --> [ Routing + Home Region，明确读写位置 ]

        Region 容灾
          --> [ 先确认 RPO：允许丢多少数据 ]
          --> [ 再确认 RTO：允许多久恢复 ]
          --> [ 关键状态：复制 + 切换，解释复制延迟与数据损失边界 ]
          --> [ 可重建状态：重建来源 + Warm-up，确认能在 RTO 内恢复 ]

        多 Region 同时写
          --> [ 明确写入归属、冲突处理和一致性要求 ]
          --> [ 再决定是否 Active-Active，不只增加一个标签 ]

  最小产出：
    租户与权限边界 + 部署范围；涉及容灾时给出 RPO / RTO
  |
  v
STEP 4 | Sizing / SLO   用规模和目标驱动后续选择

  固定动作：
    1. 确认 Read / Write / Event Rate，区分平均值与峰值。
    2. 确认对象大小、总数据量和保留时间。
    3. 确认 P95 / P99、可用性、新鲜度与允许的错误。
    4. 确认突发流量、热点 Key、热点租户和流量倾斜。
    5. 没有数字时提出 Working Assumptions，让面试官纠正。
    6. 只估算会改变设计的数量，不做无用途的精确计算。

  最小产出：
    几个能影响架构选择的规模数字 + SLO
  |
  v
STEP 5 | Data / State / Identity   先定义正确，再选择保护机制

  |-- D08 关键状态，还是可重建数据？
        丢失不可接受 --> [ Durable Store，明确 Source of Truth ]
        可以重建     --> [ 明确重建来源、时间和成本，再选缓存或派生存储 ]

  |-- D09 Source of Truth 与 Derived Data 并存？
        YES --> [ 明确传播方式、允许的延迟、失败恢复和重建方式 ]
             --> [ 使用缓存时说明更新 / 失效 / TTL，不能只画一个 Redis ]

  |-- D10 一个业务会重复执行、重试或保留历史？
        YES --> [ 区分 Business Object / Logical Operation / Attempt ]
             --> [ 同一操作重试复用身份；新业务轮次产生新身份 ]

  |-- D11 对象有明确生命周期？
        YES --> [ 给出关键状态、合法转换与终态 ]
             --> [ 说明每次转换由谁触发，迟到结果能否修改当前状态 ]

  |-- D12 Retry 不能重复产生副作用？
        YES --> [ 定义 Idempotency Key 的业务范围与租户范围 ]
             --> [ 说明键由谁产生、重试如何复用、保留多久 ]
             --> [ 相同键但内容不同：拒绝或按明确协议处理 ]
             --> [ 重复到达时：返回已有结果或处理中状态 ]

  |-- D13 同一业务不能存在两份？
        YES --> [ 对正确的业务字段建立 Unique Constraint ]
             --> [ 不只依赖“先查不存在，再插入” ]

  固定检查：
    - 写出本题必须始终成立的业务规则。
    - 指出条件检查与状态修改在哪里原子完成。
    - 选择条件更新、唯一约束、本地事务或锁，并说明保护范围。
    - 本地事务不自动覆盖 HTTP、MQ 或其他数据库。

  例：
    库存 --> 可用量不能扣成负数。
    KYC  --> 同一审核轮次只能产生一次有效最终决策。
    支付 --> 同一资金操作不能重复记账。

  最小产出：
    关键对象与标识 + 状态转换 + 正确性规则 + 原子保护边界
  |
  v
STEP 6 | Interaction Model   请求负责到哪里，结果如何返回

  |-- D14 当前 API 的执行模式？
        工作很快且时限可控
          --> [ Sync ]

        工作很慢或依赖不稳定
          --> [ 可靠受理 + operationId + Async ]
          --> [ 区分“已受理”和“业务完成” ]

        保存未来执行的 Definition
          --> [ Sync 保存 Definition，Execution 以后处理 ]

  |-- D15 异步结果如何返回 Client？
        简单查询 / 不需持续推送 --> [ Polling ]
        单向实时推送           --> [ SSE ]
        双向实时通信           --> [ WebSocket ]

        发生断线
          --> [ 结果可重新查询；需要时支持事件游标或断点恢复 ]

  |-- D16 第三方稍后返回最终结果？
        支持 Webhook --> [ 验证来源、关联业务、处理重复与乱序 ]
        支持 Query   --> [ 按协议查询，控制频率和截止时间 ]
        无可靠实时确认
          --> [ 保留待确认状态，通过回执 / 对账 / 人工核实 ]
        注意 --> [ 不默认第三方一定支持 Webhook 或幂等重试 ]

  条件检查：
    多个任务并行
      --> [ 全部完成 / 部分完成 / 满足条件即可？ ]
      --> [ 部分失败、迟到或永久缺失，整体如何结束？ ]

    有明确截止时间
      --> [ 分配整体与下游 Timeout Budget，给重试留预算 ]
      --> [ 调用方超时后，后台任务是否仍继续？ ]

    支持取消
      --> [ 区分取消请求与取消成功；已产生副作用如何处理？ ]

    Agent / 工具执行
      --> [ 明确允许操作、权限边界、隔离环境与人工确认点 ]

  最小产出：
    关键 API 的输入 / 输出 / 受理语义 / 完成条件 / 结果获取方式
  |
  v
STEP 7 | Data Access / Capacity / Partitioning   按瓶颈选择扩展方式

  |-- D17 Read Path 有什么要求？
        查询本身低效
          --> [ 先检查访问模式、索引、扫描量与返回数据量 ]

        重复读取多，允许一定陈旧
          --> [ 评估命中率和维护成本，再加 Cache ]

        允许副本延迟
          --> [ 可以使用 Read Replica ]

        必须读取最新状态
          --> [ 选择满足要求的读取方式 ]
          --> [ 多步业务判断仍需事务 / 版本 / 并发控制 ]

  |-- D18 Write Path 真的成为瓶颈？
        可以合并       --> [ Batch，说明延迟代价 ]
        可以稍后完成   --> [ Async，说明可靠受理与完成语义 ]
        单节点确实到顶 --> [ Partition / Sharding ]

  |-- D19 数据量 x Retention 超过单节点能力？
        YES --> [ Partition / Tier / Archive，匹配查询与保留要求 ]

  |-- D20 一旦进入 Partition？
        YES --> [ 明确 Partition Key、Ownership、数据倾斜 ]
             --> [ 补齐 Rebalancing / Replica / Failover ]
             --> [ 说明跨分片查询、唯一性与事务的处理边界 ]

  |-- D21 Hot Read？
        YES --> [ Local Cache / 多副本 ]
             --> [ 解释热点更新与新鲜度要求 ]

  |-- D22 Hot Write？
        YES --> [ 判断业务是否允许拆分、分桶或合并 ]
             --> [ 不能破坏原来的顺序、唯一性或余额约束 ]

  |-- D23 大对象不适合关系数据库？
        YES --> [ Object Storage 存对象，DB 存必要元数据与引用 ]
             --> [ 检查对象与元数据不一致时的恢复 ]

  |-- D24 需要全文搜索或复杂检索？
        YES --> [ 评估 Search Index ]
             --> [ 明确索引更新延迟与重建来源 ]

  |-- D25 Application 本身成为吞吐瓶颈？
        YES --> [ 尽可能无状态 + Horizontal Scale ]
             --> [ 确认 DB / 下游 / 共享资源能承受新增流量 ]

  最小产出：
    读写路径 + 必要索引 / 缓存 / 分片方案 + 对应触发依据
  |
  v
STEP 8 | Async / Queue / Stream / Worker   解耦后仍要控制积压

  |-- D26 峰值远高于均值、生产快于消费，或任务需要后台处理？
        YES --> [ API / Producer -> Queue / MQ -> Worker Pool ]
             --> [ 说明为什么值得异步，以及何时算可靠受理 ]

  |-- D27 系统依赖 Queue 承担大量工作？
        YES --> 检查：
          - Producer Rate 与 Consumer Rate 是否长期匹配？
          - 可接受的积压量与最长等待时间是多少？
          - Partition、顺序要求是否限制并行度？
          - CPU / GC / DB / 下游，谁限制消费能力？
          - Retry / Poison Message 是否阻塞正常任务？
          - 扩 Worker 会不会压垮下游？
          - 队列或线程池满了：拒绝、限流、降级还是可靠延期？
          - 任务不能静默丢弃；DLQ 需要恢复责任与处理入口。

  |-- D28 持续事件流，需要近实时聚合、排名或窗口统计？
        YES --> [ Partition by Key + 必要的 Stateful Processing ]
             --> [ 产出 Materialized View ]
             --> [ 明确顺序范围、迟到数据和状态恢复 ]

  条件检查：
    RPC / MQ / SDK 等基础设施题
      --> [ 区分 IO 线程与业务执行 ]
      --> [ 明确连接数、在途请求、Buffer 上限与 Backpressure ]
      --> [ 慢调用方不能无限占用共享资源 ]

  最小产出：
    异步边界 + 并行与顺序范围 + 积压上限 + 过载处理方式
  |
  v
STEP 9 | Middle Layer   每多一层都要证明价值

  |-- D29 BFF / Gateway 值不值得存在？
        有聚合、协议适配、安全或路由价值
          --> [ 可以增加，明确职责 ]
        只是透传
          --> [ 不增加无收益的中间层 ]

  |-- D30 跨多个 Domain 动态取字段？
        YES --> [ 评估 GraphQL 等方式 ]
             --> [ 同时考虑权限、查询成本和后端调用放大 ]

  最小产出：
    保留必要中间层；说清它解决什么问题
  |
  v
STEP 10 | Minimal Architecture + Happy Path   把设计走到结果

  固定动作：
    1. 只画前面真正触发的组件。
    2. 从一个具体请求或事件开始，走到 STEP 1 的成功标准。
    3. 每一步说明谁负责、读取什么、写入什么、返回什么。
    4. 在关键位置标出状态变化与原子事务边界。
    5. 检查数据库、对象存储、队列中的记录如何相互关联。
    6. 回看原题，确认没有遗漏外部参与方或最终交付。

  纪律：
    - 正常路径先讲清。
    - Outbox、ACK 丢失和接管等故障机制在下一步展开。
    - 但不能把核心业务约束和原子性留到最后补。

  最小产出：
    一张必要架构图 + 一条完整执行链
  |
  v
STEP 11 | Failure Playbook   检查每个关键边界的失败窗口

  固定检查：
    - 每次返回“成功”时，究竟确认了什么？
    - 数据只在内存、已写入系统缓存，还是已完成持久化或副本确认？
    - 中途崩溃后，谁发现、谁恢复、从哪里继续？
    - 是否会重复产生副作用、遗漏工作或让旧结果覆盖新结果？

  |-- D31 远程操作 Timeout / Response Lost？
        Read
          --> [ 在总预算内重试、切换可用副本或明确失败 ]
          --> [ Fallback 必须满足该业务允许的新鲜度与正确性 ]

        幂等 Write / Business Create
          --> [ 同一操作复用 Idempotency Key ]
          --> [ 按协议重试，必要时查询已有结果 ]
          --> [ 版本条件要防止旧请求覆盖新状态 ]

        外部副作用结果未知
          --> [ UNKNOWN / PROCESSING ]
          --> [ Query / Webhook / Receipt / Reconciliation ]
          --> [ 未确认前，不换新身份盲目重做或补偿 ]

  |-- D32 DB 状态修改与 MQ 通知必须一致？
        YES --> [ 评估 Transactional Outbox / CDC 等可靠传播方式 ]
             --> [ 业务状态与待发事件同事务，发送失败可恢复 ]
             --> [ 不把外部发送当成本地事务的一部分 ]

  |-- D33 MQ 可能重复投递？
        YES --> [ Consumer Idempotency ]
             --> [ 去重记录与本地业务效果需原子协调 ]
             --> [ 涉及外部副作用时，继续检查外部幂等与查询能力 ]

  |-- D34 Worker 成功但 ACK 丢失？
        YES --> [ 接受重新投递，保证业务效果幂等 ]
             --> [ 提交进度不能越过尚未处理成功的工作 ]
             --> [ Exactly-once 必须说明适用边界 ]

  |-- D35 多个 Node 可能同时处理同一份工作？
        YES --> [ 原子 Claim + 必要的 Lease / Heartbeat / Takeover ]
             --> [ 接管后，旧 Worker 恢复执行怎么办？ ]
             --> [ 用执行版本 / 所有权令牌等，让写入端拒绝过期执行 ]
             --> [ 下游不支持时，明确幂等能力与剩余风险 ]
             --> [ 不能只说“有分布式锁，所以不会重复” ]

  |-- D36 非核心下游持续失败？
        YES --> [ Circuit Breaker + 业务允许的 Degrade ]
             --> [ 不把必要的合规或资金检查直接降级成通过 ]

  |-- D37 核心下游失败，但可以稍后完成且结果明确？
        YES --> [ Reliable Queue / Retry / Recovery ]
        结果未知
          --> [ 回到 D31，先确认状态 ]

  |-- D38 过载或保护层失效可能造成级联故障？
        YES --> [ Rate Limit / Admission Control / 有界并发与队列 ]
             --> [ 隔离故障依赖，按业务规则降级 ]
             --> [ 恢复时逐步放量，避免积压与重试再次压垮系统 ]

  |-- D39 是否需要 Retry？
        Transient
          --> [ 在截止时间内有限重试 + Backoff + Jitter ]
        Permanent
          --> [ 明确失败；必要时进入异常队列或人工处理 ]
        Outcome Unknown
          --> [ 回到 D31，不直接归为普通瞬时失败 ]

        统一检查：
          - 由哪一层负责重试，避免多层重试放大？
          - 次数与时间预算是多少？
          - 超过预算后由谁处理？

  条件检查：
    文件导出与外部交付
      --> [ 固定本批次流水集合，记录流水与批次关系 ]
      --> [ 完整生成并校验后发布，避免交付半文件 ]
      --> [ 稳定批次号、内容与校验值；重发按协议去重 ]
      --> [ 区分送达、受理、业务处理和最终结算 ]
      --> [ 部分失败按明细恢复；晚到流水有后续处理入口 ]
      --> [ 没有外部幂等能力时，不能单方面承诺端到端不重 ]

  最小产出：
    关键故障窗口 + 恢复动作 + 恢复责任方 + 正确性边界
  |
  v
STEP 12 | Observability   能发现问题，也能定位到业务

  |-- D40 系统上线运行？
        YES --> [ QPS / Success-Failure Rate / P95-P99 / Saturation ]
             --> [ CPU-Memory-GC / Thread Pool / Connection Pool ]
             --> [ Downstream Latency / Error / Timeout ]
             --> [ 使用业务ID与 Trace 关联关键日志，避免泄露敏感数据 ]

  |-- D41 有 Queue / MQ / Event Stream？
        YES --> [ Producer Rate / Processing Rate / Lag / 最老待处理时间 ]
             --> [ Retry / DLQ / Poison Message ]
             --> [ 有状态流处理再看 Watermark / Checkpoint / 恢复进度 ]

  |-- D42 Multi-Tenant？
        YES --> [ per-tenant QPS / Lag / Error / Quota Usage ]
             --> [ 避免整体正常掩盖单租户故障 ]

  |-- D43 系统有明确业务成功标准？
        YES --> [ 指标直接对应 STEP 1 的成功标准 ]
             --> [ Scheduler：执行延迟与漏跑 ]
             --> [ KYC：待决策积压与处理时长 ]
             --> [ Payment：未知交易与对账差异积压 ]
             --> [ File Delivery：未确认批次与明细差异 ]

    - 哪个指标异常会触发告警？
    - 告警交给谁，如何定位到具体业务和故障阶段？
    - 不在这里重新设计一遍扩容。

  最小产出：
    关键技术指标 + 业务指标 + 告警与定位入口

STEP 13 | Trade-off & Verification   解释代价，验证是否有效

  先检查实际触发的开关：
    用了 Cache？
      --> [ 用新鲜度约束、失效复杂度和内存成本，换低延迟与少回源 ]

    用了 MQ？
      --> [ 接受异步延迟、暂时不一致和恢复复杂度，换解耦与独立扩展 ]

    做了 Replication？
      --> [ 用存储、复制与协调成本，换故障恢复或读能力 ]
      --> [ 数据丢失与读取一致性取决于复制和确认方式 ]

    做了 Partition / Sharding？
      --> [ 用路由、迁移、倾斜和跨分片复杂度，换容量与吞吐 ]

    提高一致性要求？
      --> [ 用协调、延迟及部分故障时的可用性代价，换明确正确性保证 ]

    做了 Multi-Region？
      --> [ 用跨地域通信和运维成本，换地域容灾或访问体验 ]

    都没有触发？
      --> [ 说明当前规模下简单方案为什么已足够 ]

  再做最小验证闭环：
    正确性
      --> [ 选本题最关键的并发、重复、乱序或故障窗口测试 ]
      --> [ 检查 STEP 5 的业务规则是否仍成立 ]

    性能
      --> [ 相同数据量与负载下，比较基线、延迟、错误率和资源使用 ]
      --> [ 区分设计目标、压测结果与生产观测，不编造提升数字 ]

    涉及真实交付 / 上线
      --> [ 兼容变更 + 灰度 + 监控 + 回滚 / 前向修复 ]
      --> [ 已产生的数据与外部副作用，不因回滚代码自动撤销 ]

  最小产出：
    主要收益与代价 + 验证方法 + 当前方案的适用边界
```
