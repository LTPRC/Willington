## 要注意的问题<img src="./icons/didi.gif" /><img src="./icons/microsoft.gif" /><img src="./icons/paypal.gif" /><img src="./icons/kingdee.gif" /><img src="./icons/baidu.gif" />

八条原则速览（具体判断走下节"答题 SOP 决策树"：容量与热点看 STEP 7，异步与削峰看 STEP 8，故障与冗余看 STEP 11，代价权衡看 STEP 13）：

1. 提高硬件能力有上限：服务器增加到某个程度后，系统所能提供的并发访问量几乎不变，加机器不能根本解决问题。
2. 分层：横向切分，每层只承担单一职责，层与层之间有清晰边界；逻辑上分层，物理上可分可合部署以使用更多计算资源。
3. 分割：纵向切分，高内聚低耦合，先粗粒度再细粒度，利于开发维护，也利于分布式部署、提升并发与扩展。
4. 使用缓存：空间换时间，是网站优化的第一定律；CDN、反向代理、热点数据都是对缓存的使用。
5. 消息队列：解耦 + 削峰 + 异步。
6. 分布式开发：不同服务部署在不同机器节点，一个服务也可部署多台机器，利用 Nginx 负载均衡，解决单点、提高并发。
7. 分库分表：分库（读写分离）、分表（水平分表、垂直分表）。
8. 集群与冗余：集群让多台服务器提供相同服务以支撑并发；冗余保证部分服务器宕机时网站仍可正常工作，是高可用性的重要保证。

## 答题 SOP 决策树

拿到任何一道系统设计题都走这一条流程。实战案例见 [SYS401A - 微信支付系统](./SYS401A.md) 与 [SYS401B - 秒杀系统](./SYS401B.md)。

```text
START → A01

怎么用这份 SOP
  白板上始终留三行：做到哪里算完｜哪条规则不能破坏｜当前哪里扛不住。
  题目没给关键条件：先问；对方不限定，就说明假设再继续。
  每选一个组件，都在它旁边写一句“它解决什么问题”。
  后面发现问题，就改图上的那一段；已经定下来的内容不用重讲。


A｜定题与题型：确定第一张图从哪一笔开始

A01【做】写清这轮到底设计什么。
  填一句：「___发起___，系统负责___，直到___才算完成。」
  题目太大 → 选一条完整的业务链，请面试官确认。
  已指定子系统 → 保留原题给定的输入、输出和外部参与方。
  做完 → A02。

A02【选】按题型画一个起手骨架。只画职责，先不选产品。

  普通业务系统
    → 调用方 → 处理业务的服务 → 保存业务结果的地方。
      接下来要回答：谁改状态，哪里算真正成功？

  调度器
    → 保存调度规则 → 找到期任务 → 分派执行 → 记录结果。
      接下来要回答：谁找任务、谁领任务、执行者挂了谁接手？

  消息队列
    → 生产者发送 → 系统接收并保存 → 消费者读取 → 确认进度。
      接下来要回答：什么时候告诉生产者已收到？
      消费者断开后从哪接着读？

  KV 存储／缓存
    → 调用方给出 Key → 找到负责这个 Key 的节点 → 读或写。
      接下来要回答：节点怎么找？数据丢了能不能从别处重建？

  对象存储
    → 一条线保存对象内容，一条线保存对象名称、位置和状态。
      接下来要回答：内容放哪？什么时候允许别人读？

  搜索系统
    → 原始数据 → 更新索引 → 按关键词查询。
      接下来要回答：新数据多久能搜到？索引坏了从哪重建？

  实时统计
    → 事件进入 → 按统计对象分组 → 持续更新结果 → 查询。
      接下来要回答：统计哪段时间？迟到的事件还算不算？

  如果题目是业务系统，只讲它怎么使用队列、存储等组件。
  如果题目让你设计的就是该组件，才拆它的内部。
  画好骨架 → B01。


B｜接口与交互：谁调用，什么时候给答复

B01【做】把核心操作分开写。
  每个操作写一行：「谁调用｜传什么｜返回什么」。
  不把不同操作揉在一起。比如调度器里，“创建规则”和
  “到期后执行任务”是两条线：前者由用户发起，后者由系统触发。
  做完 → B02。

B02【判】这次调用必须当场拿到最终结果吗？

  必须 → 问调用方最多能等多久，把产生结果必需的步骤放在请求里。
         如果预计做不完，先移出不影响结果的工作。
         仍做不完，就把冲突说出来，请面试官确认能否延长等待时间，
         或改成先接单、后给结果。不能自行把“已接单”说成“已完成”。

  不必 → 把受理和执行画成两段：先可靠保存待办，再返回操作 ID；
         后台执行并保存结果。两段分别标上什么时候算完成。

  有后台结果要交给调用方 → B03；否则 → B04。

B03【选】调用方怎么拿后台结果？
  偶尔查一次 → 提供按操作 ID 查询的接口；需要自动刷新就定期查。
  需要服务端持续推送 → 用 SSE 单向推送；断线后还能查询当前状态。
  双方都要实时发送消息 → 用 WebSocket；说明重连后怎么补回状态。
  选定一条满足要求的路径 → B04。

B04【判】最终结果要等外部系统吗？
  不用 → 标明我方哪一步完成后就能返回最终结果。→ C01

  要等 → 保存我方操作 ID 与外部请求 ID 的对应关系。
         对方同步给出最终结果 → 收到后更新本地状态。
         对方只接单、之后会回调 → 本地先保持处理中；
             回调到来后，验证来源、找到原操作，再更新状态。
         对方不回调，但能查 → 后台按原 ID 查询，
             查到明确结果就落库；到截止时间还不明确就标为待确认。
         对方只给回执或对账记录 → 按约定时间核对，
             找不到结果就保留待确认，不猜成功或失败。
         写出结果从哪条线回来 → C01。


C｜数据与正确性：把规则放到真正写数据的地方

C01【做】从接口反推要保存的记录。
  看每个操作：下一次请求进来时，系统还得记住什么？
  写出必要的记录、ID、状态和写入者。

  两份数据不一致时 → 指定以谁为准。
  丢了不能重建的数据 → 放可靠存储，标明哪一步算写入成功。
  缓存、索引等可以重建的数据 → 写明从哪份权威记录重建。
  有租户或权限限制 → 用认证得到的身份约束查询和更新范围，
                      不直接相信请求里自报的租户 ID。
  做完 → C02。

C02【判】一个对象会有多次操作，或者一次操作会执行多次吗？
  一个对象有多次独立操作 → 对象 ID 和操作 ID 分开。
  同一次操作会重试 → 重试沿用原操作 ID；要追查每次执行才加尝试号。
  一个标识就够用 → 保留一个，不额外建记录。
  判断标准：看两条请求，你能认出它们是同一次操作，还是两次操作。
  做完 → C03。

C03【判】操作是否需要跨请求记住进度？
  需要 → 列出实际需要的状态，每次转换写：
          「谁触发｜当前必须是什么状态｜成功后改成什么」。
          有取消、超时或失败要求，才增加对应的转换。
  不需要 → 写清一次读取返回什么，或一次写入改哪些字段。
  做完 → C04。

C04【做】写一条最不能被破坏的业务规则，再决定怎么保护。
  同一个操作不能重复创建记录
    → 用业务键加唯一约束；重复请求返回原结果或处理中。

  两个请求不能同时推进同一条记录
    → 把前置状态放进更新条件；没更新成功的一方不能触发后续动作。

  旧结果不能覆盖新结果
    → 写入时检查轮次或版本；旧版本到达就拒绝更新。

  多条本地记录必须一起改
    → 放进同一个数据库事务；任一修改失败，整组一起回滚。

  这些条件可以同时成立。若同一个条件更新已经挡住并发和旧结果，
  就只讲这一个机制。写完把两个请求代进去：哪次能改，哪次不能？→ C05

C05【判】本地写成功之后，还有一件必须交给别处做的事吗？
  没有 → 不加可靠消息交接。→ D01

  有 → 问：数据库刚提交、还没通知下游，进程就挂了，
       重启后能不能找回那件没做的事？

       能从可靠记录找回 → 写清哪个进程从哪里继续读取。
       找不回 → 在同一个事务里保存业务记录和待发事件，
                由后台补发。这就是 Outbox（待发事件表）。

       补发可能重复：为每个业务效果保留稳定标识；
       消费方用它去重，去重记录和本地业务修改一起提交。
       如果效果发生在外部，说明外部是否支持同标识去重或查询。
       画完「谁写、谁发、谁接着做」→ D01。


D｜架构与正常链路：把方案画出来，拿一个请求走到底

D01【选】功能本身需要什么专用组件？命中哪条就画哪条。

  大对象要独立上传或下载
    → 内容放对象存储，业务记录只保存对象 ID、位置和状态。
      内容完整写好且校验通过，才把状态改成可读。
      检查：传到一半断了，读方会不会看到半个对象？

  必须按关键词查全文，普通查询不能满足
    → 原始数据写权威库，搜索查询走独立索引。
      更新：后台读取可重放的变更记录，按主键写入或删除索引条目；
            带上版本，防止晚到的旧更新把已修改或已删除的数据写回来。
      时限：现在问“业务提交后，最迟多久必须搜到？”
            要求秒级就持续处理变更；容许更长延迟时，可以定时更新。
            看的是“从业务提交到能搜到”的耗时，不只看消息有没有发出。
      重建：从一致性快照建立新索引，记下该快照对应的变更位置；
            重放之后的更新和删除，追平并校验，再把查询切到新索引。

  持续进事件，而且要按时间段统计
    → 按统计对象分组，后台持续更新每个窗口的结果；
      查询直接读已算好的值。说清窗口何时结束、迟到事件如何处理。
      检查：重放同一事件，统计会不会加两遍？

  都没有 → 保留起手骨架。→ D02。

D02【判】更新规则和使用规则是否是两条独立的链？
  是 → 分开画：管理端保存并发布规则版本；执行端读取规则处理请求。
       给两条线分别标职责，说明新版本何时开始生效。
       管理端叫控制面，执行端叫数据面。
  否 → 让现有服务处理，不单独拆两层。
  做完 → D03。

D03【判】多个子任务会不会共同决定一个结果？
  会 → 有依赖的按顺序做；互不依赖的可以并行。
       圈出必须等的任务，写明总截止时间。
       到时间还缺结果 → 按业务要求决定返回失败、继续等待，
                        还是允许交付部分结果。
  不会 → 按主链顺序执行，不加编排层。
  做完 → D04。

D04【判】入口多放一层，具体能省掉谁的工作？
  多个服务都在重复做入口认证、限流或路由
    → 加 Gateway。它统一接入规则，再把请求交给目标服务。
      图上写清它检查什么、转发给谁。服务仍判断调用者能否改这条数据。

  某个客户端总要调用多个服务，自己拼出一个页面结果
    → 可以加 BFF，由服务端替这个客户端调用并拼装。
      图上写出它调用哪些服务，以及一个依赖超时后还能返回什么。

  只有一次调用，也没有可独立承担的入口工作
    → 直接访问目标服务。统一入口与页面拼装可以分别判断，
      不因为用了其中一个，就自动加上另一个。
  做完 → D05。

D05【做】拿一条真实请求从入口走到结束。
  每条箭头说完整：「谁收到什么 → 读写什么 → 下一步交给谁」。
  走到后台任务时，接着讲谁取任务、谁执行、谁写最终结果。
  走到外部系统时，接着讲怎么知道它确实完成了。
  中途讲不下去，就在那条箭头上补处理者、数据或返回方式。
  走到题目要求的终点 → E01。


E｜瓶颈与扩展：先找哪里不够，再改那一段

E01【做】用一个最相关的量，检查基线能不能撑住。
  读写 → 估峰值每秒多少次；看哪段要处理这些请求。
  后台任务 → 比每秒进多少和每秒做完多少。
  存储 → 算每天新增多少、留多久，得到需要在线存多少。
  长连接 → 估同时在线多少条，以及每条连接有多少流量。
  不知道单机能扛多少，就说明是估算、需要压测，别编出精确上限。

  读卡住 → E02；写或存储卡住 → E03；
  任务积压 → E04；实例或连接卡住 → E05。
  没有足够依据说基线不够 → E06。

E02【选】读路径先解决哪个问题？
  单条查询就慢 → 先看它过滤、排序和返回什么。
                  扫了太多行就改查询或索引，再看扫描量是否下降。

  单条查询不慢，但大量请求读同一批数据，且允许短暂读旧
    → 加缓存。画出命中和没命中两条路，说明谁负责更新或失效，
      以及缓存坏了会不会让主库瞬间扛不住。

  单条查询不慢，总读量仍超过主库能力，且有些读允许副本延迟
    → 把这部分请求分给读副本。必须读到新结果的请求，
      留在能兑现新鲜度要求的路径。

  改完看读延迟、主库负载和数据新鲜度 → E07。

E03【选】写或存储先解决哪个问题？
  一次次提交的开销太大，业务允许等一会儿
    → 合并写入；设条数上限和等待上限。

  响应慢在做了调用方不必当场等的工作
    → 把这部分移到后台；原本必须当场交付的结果不变。

  一个业务 Key 的写入特别集中
    → 能拆且不会破坏业务规则，才按可独立更新的单位拆；
      否则就控制这个 Key 的并发或串行处理，不能靠分片消灭单个热点。

  在线空间主要被很少访问的历史数据占用
    → 先归档；写清哪些数据搬走、需要时如何查回。

  前面能做的调整做完，单节点仍放不下或扛不住
    → 分片。写出分片键，用一条读和一条写演示怎么找到那一片；
      交代跨片操作、热点和迁移时谁负责写。

  改完看写延迟、吞吐或在线数据量 → E07。

E04【选】有积压，业务允许等吗？
  不允许 → 控制受理量；超限就明确返回，别把排队当成满足时限。→ E07

  允许，且只是短时突发
    → 用有上限的队列缓冲。已有任务表能撑住就先复用；
      需要生产者与消费者独立缓冲和扩容时，再加消息队列。
      写清谁放、谁取、何时确认、满了怎么办。
      看峰值过去以后，积压能不能在要求时间内清完。→ E07

  允许，但长期进得比出得快
    → 先找为什么做不完。执行者不够且下游有余量，才加 Worker；
      同一分区限制并行，就检查能否按业务键独立执行；
      数据库或第三方已经满了，先减压或提高它的处理能力。
      队列只能存积压，不能解决长期产能不足。→ E07

E05【选】服务实例或连接先卡在哪里？
  业务计算耗尽单实例资源、下游有余量
    → 加实例并分流。说清哪些请求可交给任意实例，
      哪些会话或任务状态需要保存起来。

  慢连接拖住其他连接
    → 给每条连接设缓冲上限；超过上限就按协议降速或断开。
      说明重新连上后怎么补回状态。

  实际卡在共享数据库或第三方
    → 不继续加实例；限制并发并处理那个共享瓶颈。
  改完看整条链吞吐是否提高，而不是只看实例变多 → E07。

E06【判】正常服务时有跨地域要求吗？
  只有就近访问 → 说明请求怎么路由到近处、写入落在哪个地域。
  要求多地同时写 → 先定每份数据由谁写；如果同一份数据允许
                   多地修改，要说清冲突怎么裁决。
  只有地域容灾要求 → 正常读写路径先保持简单，故障切换到 F03 讲。
  没有 → 不加多地域部署。
  做完 → F01。

E07【做】只重走刚改过的那段链。
  说清改动解决了哪个已知问题，以及付出了什么代价。
  还有另一个明确瓶颈 → 处理对应分支。
  当前够用或还要靠测量才能判断 → E06。


F｜故障与恢复：挑真正危险的失败来跑

F01【做】挑一个最可能破坏业务规则的断点。
  交接中途崩溃 → 演示从哪条已保存的记录找回工作。
  工作做完但确认丢了 → 重放同一操作，演示哪里挡住第二次生效。
  旧结果晚到 → 演示哪条更新条件把它挡住。
  两个执行者抢同一任务 → 用一次原子更新只让一个领取成功。
  允许任务过期接管 → 再模拟旧执行者恢复；新执行者拿到新版本，
                     真正写结果的地方拒绝旧版本。
  只演示本题命中的故障。已有机制够用就直接拿它验证；
  不够用，就在出问题的那一步补。→ F02

F02【选】一次外部调用出错，实际结果属于哪一种？
  确认已成功 → 补记本地结果，继续后续流程，不再重做。
  确认没成功，而且属于临时故障
    → 沿用原操作 ID；指定一层负责重试，设次数、间隔和截止时间。
  结果未知 → 先记为待确认；用原 ID 查询、等通知或核对记录。
             没有安全去重约定，就不盲目重发有副作用的请求。
  确认无法恢复，或查证超过期限
    → 给出明确失败或转异常处理；写明谁接手、凭什么判断结果。

  如果慢依赖会拖住其他请求，再给它单独设并发和等待上限；
  超限时按业务允许的方式降级、拒绝或延期。
  没有外部依赖 → 跳过。→ F03

F03【选】是哪个范围失效？按题目要求回答。
  一个无状态实例挂了
    → 新请求切到其他实例；没完成的请求按原操作标识恢复或重试。

  保存关键状态的节点挂了
    → 说明谁接管、从哪份数据恢复、怎样禁止旧节点继续写。

  整个地域挂了
    → 确认最多允许丢多少数据、多久要恢复。
      关键数据按要求提前复制；可重建的数据只有在能按时重建时，
      才等切换后再建。说清接管的地域和写入归属。

  发布规则的管理端挂了
    → 旧规则仍然安全，执行端就暂时用旧版本。
      旧权限或旧所有权可能放行错误操作，就停掉受影响的请求。

  题目不要求自动接管
    → 说明会暂停什么，恢复后从哪份记录继续。

  选本题一个故障验证：系统在承诺时间内恢复了吗？
  数据丢失和重复执行有没有超出承诺？→ G01
```
