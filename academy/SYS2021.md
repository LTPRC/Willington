## 域名体系的分层

一个域名 `www.example.com.` 从右往左读是一棵树：

```text
.            根区（root zone）
└─ com.      顶级域 TLD，由某个注册局运营
   └─ example.com.   二级域，由注册人在注册商处注册
      └─ www.example.com.  由注册人在自己的权威 DNS 上自行管理
```

关键分界：**TLD 及以上的注册数据由注册局掌握，TLD 以下的子域名由注册人自己掌握。**注册局不关心你在 `example.com` 下面建了多少个子域名，它只维护 `example.com` 这一条注册记录以及它委派的 NS。这也解释了为什么"改子域名解析"和"改域名注册信息"是两条完全不同的链路——前者走你自己的权威 DNS，后者要走注册商 → EPP → 注册局。

### TLD 的分类

| 类别 | 说明 | 政策归谁管 |
| --- | --- | --- |
| gTLD | 通用顶级域，如 `.com` `.net` `.org` | ICANN 通过合同约束注册局与注册商 |
| New gTLD | 2012 年后陆续开放的新通用顶级域，如 `.app` `.shop` `.xyz` | 同上，且申请时须通过 ICANN 的技术预评估 |
| ccTLD | 国家/地区代码顶级域，如 `.cn` `.uk` `.jp` | 由对应国家/地区指定的管理机构负责，ICANN 不直接管其注册政策 |
| IDN TLD | 国际化顶级域，非 ASCII 字符，如 `.中国` | 视所属类别，走 gTLD 或 ccTLD 的管理路径 |
| 基础设施 TLD | `.arpa`，用于反向解析等技术用途 | IANA |

ccTLD 与 gTLD 的政策来源不同，这一点在工程上会有实际后果：ccTLD 的实名要求、转移规则、状态码语义可能与 gTLD 不一致，后端服务不能把 gTLD 的规则硬编码成通用假设。

## 五方职责

| 角色 | 职责 | 例子 |
| --- | --- | --- |
| ICANN | 协调 DNS 根、IP 地址分配与协议参数；认证 gTLD 注册商；与注册局签合同 | 不运营任何注册局，也不决定网站内容 |
| Registry（注册局） | 运营某个 TLD，掌握该 TLD 下全部注册数据的权威记录；运营 EPP、RDAP/WHOIS、权威 DNS、Data Escrow | `.com`/`.net` 由 Verisign 运营，`.org` 由 PIR，`.cn` 由 CNNIC |
| Registrar（注册商） | 面向注册人办理注册业务，通过 EPP 向注册局提交命令；通常还提供 DNS 托管、邮箱等增值服务 | GoDaddy、Namecheap、阿里云（万网） |
| Registrant（注册人） | 域名的持有者，决定域名指向哪里 | 个人或企业 |
| RSP（Registry Service Provider） | 为注册局提供后端技术服务，本身不面向注册人 | 见下文 |

还有两个常见但不在这条主链上的角色：

- **Reseller（转售商）**：挂靠在某个已认证注册商下面卖域名，自身不直接与 ICANN 签认证协议。
- **Privacy / Proxy 服务**：代替真实注册人出现在公开注册数据里。启用后，RDAP/WHOIS 查到的是代理方信息，这会直接影响 [SYS2024](./SYS2024.md) 里"数据可见性"的实现。

### 一次注册的完整链路

```text
注册人 → 注册商前台（下单、支付、实名）
       → 注册商后端 ──EPP create──→ 注册局 SRS（写入注册数据库）
       → 注册局 ──生成区文件──→ TLD 权威 DNS（对外可解析）
       → 注册局 ──RDAP/WHOIS──→ 公众可查询
       → 注册局 ──Data Escrow──→ 托管方
```

注意这条链上**注册人从来没有直接和注册局通信**。注册局的所有对外写接口都只对已签约的注册商开放，这是理解 EPP 鉴权模型的前提。

## RSP 到底做什么

RSP 是注册局的技术承包方。很多 TLD（尤其是 New gTLD）的申请主体是一家商业公司，它拿到运营权但并不自建后端，而是把技术能力外包给专业 RSP。

ICANN 在 New gTLD 项目的预评估阶段，对后端服务做了明确的技术功能测试，这几项恰好构成了 RSP 的工作范围：

| 关键功能 | 内容 | 本课章节 |
| --- | --- | --- |
| SRS（Shared Registration System） | 共享注册系统，即注册商并发访问的 EPP 服务，要处理会话、鉴权、并发、配额 | [SYS2022](./SYS2022.md) |
| DNS | TLD 权威区的解析服务 | [SYS2026](./SYS2026.md) |
| DNSSEC | 对 TLD 区做签名与密钥管理 | [SYS2026](./SYS2026.md) |
| Data Escrow | 注册数据的定期托管 | [SYS2025](./SYS2025.md) |

再加上注册数据目录服务（RDAP/WHOIS，见 [SYS2024](./SYS2024.md)）和商标信息交换所（TMCH）对接，就是一份完整的注册局后端职责清单。

从工程视角看，这套系统的形状并不陌生：

- **它是一个多租户写入系统**：每个注册商是一个租户，有自己的凭据、配额和审计要求。
- **它有一个强一致的注册数据库作为 Source of Truth**：区文件、查询服务、托管文件全都是这个库的派生视图。派生视图之间的一致性问题，和 [DBA2012](./DBA2012.md) 里数据库与缓存的一致性是同一类问题，只不过这里的下游是文件与 DNS。
- **它有一条对时延敏感、一条对时延不敏感**：EPP 是同步在线交易，区文件与托管是批处理。两类负载混在一个数据库上，是注册局后端最典型的资源争抢来源。

## 正确性、稳定性与合规可证明

把上面的职责清单翻译成运营目标，是三层不能混为一谈的东西：

- **正确性**：一条错误注册记录，可能让域名被错误占用、转移或删除。两个注册商争抢同一个域名，最终只能有一个合法结果——靠注册库唯一约束与原子事务保证，并发写热点见 [SYS2022](./SYS2022.md)。
- **稳定性**：EPP 要让注册商可持续办理业务，权威 DNS 要持续回答查询，RDAP 要在要求的时间窗口内提供合适的数据。三者的可用性与新鲜度目标并不相同，容量规划要分开做。
- **合规可证明**：合规不是"程序看起来正常"就算数。要按适用政策记录每一次变更、按时导出托管文件（见 [SYS2025](./SYS2025.md)）、保留校验与接收回执，失败时要有告警、重试与升级处置，事后能向 ICANN 拿出证据。

最后一条最容易被低估：**ICANN 合规不是一组可以写死在代码里的全行业固定天数。**期限、字段、政策与合同版本随 TLD 和规则变化，RSP 实现时要明确每条规则的适用范围，把期限和阈值做成配置化，并对规则本身做审计与版本控制——写死天数是合规系统最常见的设计错误。

## thin 与 thick 注册局

这是两个必须分清的模型，它决定了注册局数据库里到底存了什么：

| 模型 | 注册局存什么 | 后果 |
| --- | --- | --- |
| thin | 只存域名、状态、NS、所属注册商、关键日期；注册人与联系人信息存在注册商那里 | 查注册人信息必须先从注册局拿到 registrar，再去问注册商（referral） |
| thick | 完整存下注册人与联系人信息 | 注册局一处即可返回完整数据，转移注册商时数据随域名一起迁移 |

`.com` 早期是 thin 模型，后来迁移到 thick。工程上不能假设所有 TLD 都是同一种模型——RDAP 的重定向逻辑、转移流程要不要搬联系人数据，都取决于这一点。

## 辨析：团队叫"云解析 DNS"不等于做递归解析器

这是最容易踩的坑。DNS 领域至少有三类完全不同的服务：

| 服务 | 做什么 | 典型形态 |
| --- | --- | --- |
| 权威 DNS 托管 | 替客户保管某个区的权威数据并对外应答 | 云厂商的"云解析"产品 |
| 注册局后端 | 运营 TLD 的权威区 + SRS + 托管 + 查询服务 | 本课全部内容 |
| 递归解析器 | 替终端用户做迭代查询、缓存结果 | 运营商 DNS、公共 DNS（如 8.8.8.8） |

三者的技术栈重叠很小：权威侧关心的是区文件生成、签名、Anycast 与应答时延；递归侧关心的是缓存命中率、TTL 策略与预取。团队名称里的"DNS"通常指前两类，而不是递归解析器。

需要额外掌握的 DNS 协议层知识——递归与迭代查询的区别、委派链、DS/DNSKEY/RRSIG 与信任链验证——统一放在 [SYS2018 - DNS 解析体系](./SYS2018.md)。本课只在 [SYS2026](./SYS2026.md) 讲注册局侧的运营职责。

## 容易混淆的三组边界

1. **注册局 ≠ ICANN。**ICANN 是协调与合同方，不运营注册数据库；注册局是某个 TLD 的实际运营者。
2. **注册商 ≠ 转售商。**注册商与 ICANN 有认证关系并能直连注册局；转售商只是注册商的下游渠道。
3. **改注册信息 ≠ 改解析记录。**改注册人邮箱、NS 委派、转移状态走 EPP；改 `www` 指向哪个 IP 走注册人自己的权威 DNS。前者有政策约束与生效时延，后者通常秒级生效。
