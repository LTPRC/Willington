### 提高硬件能力、增加系统服务器

当服务器增加到某个程度的时候系统所能提供的并发访问量几乎不变，所以不能根本解决问题。

### 分层

分层是处理任何复杂系统最常见的手段之一，将系统横向切分成若干个层面，每个层面只承担单一的职责，然后通过下层为上层提供的基础设施和服务以及上层对下层的调用来形成一个完整的复杂的系统。

计算机网络的开放系统互联参考模型（OSI/RM）和Internet的TCP/IP模型都是分层结构，大型网站的软件系统也可以使用分层的理念将其分为持久层（提供数据存储和访问服务）、业务层（处理业务逻辑，系统中最核心的部分）和表示层（系统交互、视图展示）。

需要注意：

1. 分层是逻辑上的划分，在物理上可以位于同一设备上也可以在不同的设备上部署不同的功能模块，这样可以使用更多的计算资源来应对用户的并发访问；
2. 层与层之间应当有清晰的边界，这样分层才有意义，才更利于软件的开发和维护。

### 分割

分割是对软件的纵向切分。我们可以将大型网站的不同功能和服务分割开，形成高内聚低耦合的功能模块（单元）。在设计初期可以做一个粗粒度的分割，将网站分割为若干个功能模块，后期还可以进一步对每个模块进行细粒度的分割，这样一方面有助于软件的开发和维护，另一方面有助于分布式的部署，提供网站的并发处理能力和功能的扩展。

### 使用缓存

所谓缓存就是用空间换取时间的技术，将数据尽可能放在距离计算最近的位置。使用缓存是网站优化的第一定律。我们通常说的CDN、反向代理、热点数据都是对缓存技术的使用。

### 消息队列

解耦+削峰+异步。

### 分布式开发

不同的服务部署在不同的机器节点上，并且一个服务也可以部署在多台机器上，然后利用 Nginx 负载均衡访问。这样就解决了单点部署(All In)的缺点，大大提高的系统并发量。

### 分库分表

数据库分库（读写分离）、分表（水平分表、垂直分表）。

### 集群

集群使得多台服务器提供相同的服务，可以更好的提供对并发的支持。

### 冗余

各种服务器都要提供相应的冗余服务器以便在某台或某些服务器宕机时还能保证网站可以正常工作，同时也提供了灾难恢复的可能性。冗余是网站高可用性的重要保证。 

## 答题 SOP 决策树

拿到任何一道系统设计题都走这一条流程。实战案例见 [SYS401A - 微信支付系统](./SYS401A.md) 与 [SYS401B - 秒杀系统](./SYS401B.md)。

```text
  .--------------------------.
  | START | 拿到系统设计题   |
  '--------------------------'
        |
        v
  +--------------------------------------------------------------------------------+
  | 开场话术                                                                       |
  | 先确认今天真正要设计的范围; 说明会从题目一路推到                               |
  | 架构 -> 故障 -> 监控 -> 扩容 -> Trade-off                                      |
  +--------------------------------------------------------------------------------+
        |
        v
  +================================================================================+
  | STEP 1 | Scope   先把题目缩成一条核心链                                        |
  +================================================================================+
        |-- D01 题目是不是一个"大平台"?
              YES --> [ 只选一条核心业务链 A -> B -> C -> D ]
              NO  --> [ 按题目原范围设计 ]
        |-- D02 面试官已明确指定子系统?
              YES --> [ 直接围绕该子系统, 不主动扩大 Scope ]
        v
  +================================================================================+
  | STEP 2 | System Type   普通业务系统, 还是基础设施本身                          |
  +================================================================================+
        |-- D03 主要是在完成业务流程?
              YES --> [ Baseline: Client -> Application Service -> Durable Store ]
        |-- D04 题目本身就是 Cache / MQ / Scheduler / KV Store?
              YES --> [ Baseline: Client -> Target System, 不套 Business Service + DB ]
                 +--> [ 之后 Data / Failure / Observability 仍走同一条 SOP ]
        |-- D05 同时存在协调逻辑与高频执行路径?
              YES --> [ 区分 Control Plane / Data Plane ]
                 +--> [ 控制面短暂故障时, 数据面按 Last-Known-Good Metadata 继续服务 ]
        v
  +================================================================================+
  | STEP 3 | Deployment Context   Multi-Tenant 与 Region                           |
  +================================================================================+
        |-- D06 是否 Multi-Tenant?
              YES --> [ tenantId 是一等维度 ]
                 +--> [ Quota / Fairness / Isolation / Noisy Neighbor / per-tenant metrics ]
        |-- D07 Region / Geo 要求是什么?
              无要求           --> [ 不自动 Multi-Region ]
              就近访问         --> [ Routing + Home Region ]
              Region 容灾      --> [ 先判断这份状态能不能重建 ]
                              +--> [ Durable State --> Replication + Failover ]
                              +--> [ Derived State --> Failover + Rebuild / Warm-up ]
                              +--> [ (Replication 只在 RTO / Latency 明确要求时再加) ]
              多 Region 同时写 --> [ Active-Active ]
        v
  +--------------------------------------------------------------------------------+
  | STEP 4 | Sizing / SLO   固定动作, 无判断, 不占 D 编号                          |
  +--------------------------------------------------------------------------------+
        |>-- 1. 确认 Read / Write / Event Rate 与 Average / Peak
        |>-- 2. 确认 Object Size / Total Data / Retention
        |>-- 3. 确认 P95 / P99 / Availability / Freshness 容忍
        |>-- 4. 确认 Burst / Skew / Hot Key / Hot Tenant 是否明显
        |>-- 5. 没有数字 -> 声明 Working Assumptions 让面试官纠正, 再继续
        |>-- 原则: Sizing / SLO 是后续 IF -> THEN 的输入, 不为精确容量规划浪费时间
        v
  +================================================================================+
  | STEP 5 | Data / State / Identity   数据、状态和业务身份                        |
  +================================================================================+
        |-- D08 关键状态, 还是可重建数据?
              丢了不可恢复 --> [ Durable Store, 明确 Source of Truth ]
              可重建       --> [ Cache / Derived Data 可以非 Durable ]
        |-- D09 Source of Truth 与 Derived Data 并存?
              YES --> [ 明确传播方式 / Staleness Window / 失败恢复 / Rebuild ]
        |-- D10 一个业务会多次执行 / Retry / 留历史?
              YES --> [ Business Object 与 Execution / Attempt 分离 ]
        |-- D11 对象有明确生命周期?
              YES --> [ 显式 State Machine ]
        |-- D12 Retry 不能重复产生副作用?
              YES --> [ Idempotency Key ]
        |-- D13 同一业务绝对不能存在两份?
              YES --> [ Unique Constraint 兜底 ]
        v
  +================================================================================+
  | STEP 6 | Interaction Model   一次调用负责到哪里, 结果怎么回来                  |
  +================================================================================+
        |-- D14 当前 API 的执行模式?
              执行很快            --> [ Sync ]
              工作很慢            --> [ Persist + operationId + Async ]
              只是未来 Definition --> [ Sync 保存 Definition, Execution 以后再处理 ]
        |-- D15 异步结果如何返回 Client?
              不实时   --> [ Polling ]
              单向推   --> [ SSE ]
              双向实时 --> [ WebSocket ]
        |-- D16 第三方稍后才返回最终结果?
              YES --> [ Webhook ]
        v
  +================================================================================+
  | STEP 7 | Data Access / Capacity / Partitioning   读写、容量和热点              |
  +================================================================================+
        |-- D17 Read Path 容量与新鲜度要求?
              允许 stale       --> [ Cache ]
              允许 replica lag --> [ Query Optimization + Read Replica ]
              必须 latest      --> [ Primary / Leader Read ]
        |-- D18 Write Path 真的成为瓶颈?
              可合并     --> [ Batch ]
              可异步     --> [ Async 化 ]
              单节点到顶 --> [ Partition / Sharding ]
        |-- D19 总数据量 x Retention 超过单节点能力?
              YES --> [ Partition / Tier / Archive ]
        |-- D20 一旦进入 Partition?
              YES --> [ 补齐 Ownership / Rebalancing / Replica / Failover ]
        |-- D21 Hot Read?
              YES --> [ Local Cache / 多 Replica ]
        |-- D22 Hot Write?
              YES --> [ Split Counter / 改 Partition Key ]
        |-- D23 大对象不适合关系数据库?
              YES --> [ Object Storage ]
        |-- D24 需要海量全文搜索?
              YES --> [ Search Index ]
        |-- D25 Application 本身是否成为吞吐瓶颈?
              YES --> [ Stateless where possible + Horizontal Scale ]
        v
  +================================================================================+
  | STEP 8 | Async / Queue / Stream / Worker   生产与消费不同速时再引入            |
  +================================================================================+
        |-- D26 峰值远高于均值 / 产生快于消费 / 前后台容量需求不同?
              YES --> [ Frontend / API -> Queue / MQ -> Worker Pool ]
        |-- D27 系统依赖 Queue 承担大量工作?
              YES --> +-----------------------------------------+
                      | 设计时就确认消费扩展边界:               |
                      | - Producer Rate vs Consumer Rate        |
                      | - Consumer CPU / GC                     |
                      | - Partition 是否限制并行度              |
                      | - 是否可能出现 Hot Partition            |
                      | - DB / Downstream 是否成为消费瓶颈      |
                      | - Retry / Poison Message 是否造成阻塞   |
                      +-----------------------------------------+
        |-- D28 持续 Event Stream + 近实时聚合 / 排名 / 窗口统计?
              YES --> [ Event Stream -> Partition by Key ]
                 +--> [ 再经 Stateful Stream Processing 产出 Materialized View ]
        v
  +================================================================================+
  | STEP 9 | Middle Layer   每多一层都要证明为什么值得                             |
  +================================================================================+
        |-- D29 BFF / Gateway 值不值得存在?
              有聚合 / 适配 / 安全 / 路由价值 --> [ 可以加这一层 ]
              只是透传                        --> [ 不加, 避免 Pass-through Layer ]
        |-- D30 跨多个 Domain 动态取字段?
              YES --> [ GraphQL 可能有价值 ]
        v
  +--------------------------------------------------------------------------------+
  | STEP 10 | Minimal Architecture + Happy Path   固定动作, 无判断                 |
  +--------------------------------------------------------------------------------+
        |>-- 1. 只把前面真正触发的组件画进架构
        |>-- 2. 从入口开始走一次 Happy Path
        |>-- 3. 每一步说清 Owner
        |>-- 4. 每一步说清 State Change
        |>-- 5. 一直走到最终结果
        |>-- 纪律: Outbox / Retry / ACK Lost 等加固, 此时先不提前讲
        v
  +================================================================================+
  | STEP 11 | Failure Playbook   把架构图上每根箭头都假设断一次                    |
  +================================================================================+
        |-- D31 远程操作 Timeout / Response Lost 的通用语义?
              Read Timeout         --> [ 短 Timeout + Retry alternate replica / Fail Fast / Fallback ]
              Key-based 幂等 Write --> [ Retry same key / same version, 必要时读取确认 ]
              Business Create      --> [ same Idempotency Key Retry + Status Query ]
              外部副作用结果未知   --> [ UNKNOWN / PROCESSING + Query / Webhook / Reconciliation ]
        |-- D32 DB 成功但 MQ 没发出去?
              YES --> [ Transactional Outbox ]
        |-- D33 MQ 可能重复投递?
              YES --> [ Consumer Idempotency ]
        |-- D34 Worker 成功但 ACK 丢失?
              YES --> [ At-Least-Once + 幂等消费 ]
        |-- D35 多个 Node 可能同时处理同一份工作?
              YES --> [ atomic Claim -> Lease -> 长任务 Heartbeat -> 过期 Takeover ]
        |-- D36 非核心下游持续失败?
              YES --> [ Circuit Breaker + Degrade ]
        |-- D37 核心下游失败但可以稍后完成 (未产生 Outcome Unknown)?
              YES --> [ Queue / Retry / Recovery ]
                 +--> [ 已进入 Outcome Unknown 的, 回到 D31 分支, 不盲目重新执行 ]
        |-- D38 保护层失效可能触发 Cascading Failure?
              YES --> [ Rate Limit / Admission Control -> Degrade -> Safe Fallback -> Gradual Recovery ]
        |-- D39 统一 Retry Policy: 失败属于哪一类?
              Transient --> [ bounded Retry + Exponential Backoff + Jitter ]
              Permanent --> [ Fail Fast / DLQ / Manual ]
        v
  +================================================================================+
  | STEP 12 | Observability   此处不重新设计扩容方案                               |
  +================================================================================+
        |-- D40 系统上线运行 (所有在线系统都适用)?
              YES --> [ Golden Signals: QPS / Success-Failure Rate / P95-P99 ]
                 +--> [ CPU-Memory-GC / DB Connection Pool / Downstream Error ]
        |-- D41 架构里有 Queue / MQ / Event Stream?
              YES --> [ Producer / Processing Rate, Queue / Stream Lag ]
                 +--> [ Retry Rate / DLQ 与 Poison Message ]
                 +--> [ Stateful Stream 再看: Processing Lag / Watermark / Checkpoint (若使用) ]
        |-- D42 Multi-Tenant?
              YES --> [ per-tenant QPS / Lag / Error Rate / Quota Usage ]
        |-- D43 系统有明确业务成功标准?
              YES --> [ 至少加一个真正业务指标, 不要只说"日志、指标、Tracing" ]
                 +--> [ Scheduler -> Scheduling Lag / Booking -> Success Rate ]
                 +--> [ Payment -> Reconciliation backlog / Chat -> Delivery Lag ]
        v
  +================================================================================+
  | STEP 13 | Trade-off   只检查六个开关                                           |
  +================================================================================+
        |-- 用了 Cache?
              YES --> [ 牺牲新鲜度与缓存一致性复杂度, 换更低读延迟与更少 DB 压力 ]
        |-- 用了 MQ?
              YES --> [ 牺牲最终一致与更复杂失败恢复, 换削峰 / 解耦 / 独立扩展 ]
        |-- 做了 Replication?
              YES --> [ 牺牲存储成本与副本一致性复杂度, 换可用性与读能力 ]
        |-- 做了 Partition / Sharding?
              YES --> [ 牺牲路由 / Rebalancing / 跨分片复杂度, 换容量与吞吐扩展 ]
        |-- 提高了强一致要求?
              YES --> [ 牺牲协调开销 / 延迟 / 部分可用性, 换数据正确性 ]
        |-- 做了 Multi-Region?
              YES --> [ 牺牲跨 Region 复制与运维复杂度, 换低延迟与 Region 级容灾 ]
        |-- 六个一个都没有?
              YES --> [ 当前量级下简单架构已满足需求, 优先保持简单 ]
        |
        v
  +--------------------------------------------------------------------------------+
  | Trade-off 总公式 (收束这一句)                                                  |
  | 我为了 [性能 / 扩展性 / 可用性 / 正确性] 增加了 XXX,                           |
  | 代价是 [一致性 / 延迟 / 成本 / 运维复杂度]                                     |
  +--------------------------------------------------------------------------------+
        |
        v
  .---------------------------.
  | 面试官 Challenge / 追问   |
  '---------------------------'
        :
        :-- 规则 B | Baseline -> Upgrade: 某个真实指标成为瓶颈后, 只升级那个点
        :
        '---------> 回到对应 STEP 重新判断 (通常是 Step 7 容量 或 Step 11 故障)
```
