> **本章定位：**State machine。域名不是一个"有或没有"的布尔值，而是一条带多个宽限期的状态机。这一章讲清各阶段的含义与谁有权推进它，以及 EPP 状态码的分权模型——为什么一条 update 命令不能把域名改成任意状态。

## 生命周期

```text
可注册
  │ create
  ▼
addPeriod ──────► 正常注册（active）
                     │ 到期未续费
                     ▼
                autoRenewPeriod ──► 续费宽限期
                     │ 仍未续费
                     ▼ registry delete
                redemptionPeriod（可付费赎回）
                     │
                     ▼
                pendingDelete（不可恢复）
                     │
                     ▼
                  释放回可注册池
```

各阶段的实质含义：

| 阶段 | 谁在推进 | 域名能不能解析 | 能不能续费 | 典型时长 |
| --- | --- | --- | --- | --- |
| addPeriod | 注册局，create 后自动进入 | 能（前提是有 NS 委派） | 能 | 注册局政策设定，用于"创建后短期内删除可退费" |
| 正常注册 | — | 能 | 能 | 注册时选择的 period，1–10 年 |
| autoRenewPeriod | 注册局，到期自动续费后进入 | 通常仍能，但注册商可能已 hold | 能 | 0–45 天，由注册局政策决定 |
| 续费宽限期 | 注册商主导 | 通常被注册商置为 clientHold | 能，按正常价 | 常见 30 天左右 |
| redemptionPeriod | 注册局，delete 后进入 | **不能**，已从区文件移除 | 不能续费，只能走 restore | 常见 30 天 |
| pendingDelete | 注册局 | 不能 | 不能，也不能赎回 | 常见 5 天 |

上表里的时长是**行业常见值，不是常量**。具体天数由 TLD 的注册局政策与 ICANN 政策共同决定，ccTLD 与 gTLD 之间可能差异很大，不同注册局之间也不一致。后端实现上必须把这些值做成配置项，绝不能硬编码——这是跨 TLD 复用同一套注册局后端时最容易出问题的地方。

### 三个容易被忽略的点

**1. 到期不是立刻消失。**到期后注册局会先自动续费（auto-renew），进入 autoRenewPeriod。这个设计的目的是给注册商一个退费窗口：如果注册商在这期间删除域名，注册局通常会把自动续费的费用退回。所以"到期"在数据库里表现为一次**注册局主动发起的续费**，而不是状态置为过期。

**2. redemptionPeriod 不能靠 update 回去。**赎回是一条独立流程：注册商提交 restore 请求，域名转为 pendingRestore，随后还要补交一份恢复报告（RGP restore report）说明赎回的正当性，审核通过才真正回到 active。用 EPP 的 update 命令去改状态是无效的——会返回 2303（Object status prohibits operation）。

**3. 释放时刻是系统最忙的时刻。**pendingDelete 结束、域名回到可注册池的那一瞬间，全网注册商会同时发起 check + create 争抢。热门短域名的 drop 时刻是注册局后端最极端的并发热点，见 [SYS2022](./SYS2022.md) 的并发模型一节。

## 状态码的分权模型

EPP 状态码是**多个可以同时存在**的标记，不是单一枚举值。它们按"谁有权设置"分成两组，这是整章最重要的一条规则：

| 前缀 | 谁能设置 | 语义 |
| --- | --- | --- |
| `client*` | 注册商 | 注册商对自己客户域名施加的限制 |
| `server*` | 注册局 | 注册局基于政策、合规、争议施加的限制 |
| `pending*` | 注册局 | 表示某个异步流程正在进行中 |
| `ok` | — | 仅在没有任何其它状态时使用 |

完整清单：

| 状态 | 含义 | 对 DNS 的影响 | 对操作的影响 |
| --- | --- | --- | --- |
| ok | 无限制 | 正常发布 | 无 |
| inactive | 没有 NS 委派 | **不发布到区文件** | 无 |
| clientHold | 注册商要求停止解析（常见于欠费、实名未完成） | **不发布** | 无 |
| serverHold | 注册局要求停止解析（合规、法律、争议） | **不发布** | 无 |
| clientRenewProhibited | 注册商禁止续费 | 无 | renew 被拒 |
| serverRenewProhibited | 注册局禁止续费 | 无 | renew 被拒 |
| clientTransferProhibited | 注册商禁止转移（俗称注册商锁） | 无 | transfer 被拒 |
| serverTransferProhibited | 注册局禁止转移（注册局锁、争议期、60 天窗口） | 无 | transfer 被拒 |
| clientUpdateProhibited | 注册商禁止修改 | 无 | update 被拒 |
| serverUpdateProhibited | 注册局禁止修改 | 无 | update 被拒 |
| clientDeleteProhibited | 注册商禁止删除 | 无 | delete 被拒 |
| serverDeleteProhibited | 注册局禁止删除 | 无 | delete 被拒 |
| pendingCreate | 创建流程进行中（如抢注阶段） | 视实现 | 相关操作受限 |
| pendingTransfer | 转移窗口期内 | 无 | 返回 2300，禁止其它变更 |
| pendingRenew | 续费待处理 | 无 | 相关操作受限 |
| pendingUpdate | 修改待处理 | 无 | 相关操作受限 |
| pendingDelete | 待释放，不可恢复 | **不发布** | 全部禁止 |

除 EPP 基础状态外，宽限期机制还引入了一组只在特定期出现的状态：`addPeriod`、`autoRenewPeriod`、`renewPeriod`、`redemptionPeriod`、`pendingRestore`。它们同样会出现在 RDAP/WHOIS 的响应里，见 [SYS2024](./SYS2024.md)。

## 为什么不是每次 UPDATE 都能改成任意状态

这是这一章的核心问题，答案有五层，从硬到软：

### 第一层：权限分离

注册商在 update 里提交 `<domain:status s="serverHold"/>` 会被直接拒绝。**`server*` 状态只能由注册局设置，`client*` 状态只能由注册商设置。**这条边界不能靠客户端自觉，必须由服务端强制校验，否则任何一个被攻破的注册商账号都能给自己或别人的域名加解锁。

对称地：注册商**不能摘掉 `server*` 锁**。要解除注册局锁，只能走注册局侧的流程（工单、合规审查、争议结案）。

### 第二层：状态自身会阻塞命令

`clientUpdateProhibited` / `serverUpdateProhibited` 存在时，update 命令本身就被拒绝，返回 2303。这产生一个有意思的自指问题：**谁来解锁一把禁止解锁的锁？**

实践中的处理是：注册商自己加的 `clientUpdateProhibited`，允许注册商用一次 update 把它 rem 掉（锁的持有者就是注册商自己）；而 `serverUpdateProhibited` 只能由注册局解除。不同注册局对自解锁的实现细节不完全一致，接入前要看对方的技术规范。

### 第三层：政策窗口期

有一批锁定不是任何人"设置"出来的，而是政策到期时间驱动的：

| 窗口 | 触发条件 | 表现 |
| --- | --- | --- |
| 注册后 60 天 | 新注册域名 | 禁止转出 |
| 转移后 60 天 | 刚完成一次注册商转移 | 禁止再次转出 |
| 注册人变更后 60 天 | 注册人信息发生实质变更 | 禁止转出（ICANN 转移政策要求，通常允许注册人选择退出） |
| 争议期间 | 进入 UDRP / URS 程序 | 禁止转移、禁止修改、禁止删除 |

这些窗口在数据库里表现为带过期时间的 `serverTransferProhibited`，由注册局按政策自动施加与解除。**它们的解除条件是时间，不是命令**，所以注册商无论怎么发 update 都解不开。

### 第四层：引用完整性

`delete` 一个仍被 domain 引用的 host，或一个仍被引用为 registrant 的 contact，会返回 2304（Object association prohibits operation）。这是数据模型的约束而非政策约束，必须先解除引用。

### 第五层：状态叠加与优先级

多个状态同时存在时，效果是**并集而非覆盖**：任何一个 `*Hold` 都会让域名不发布，任何一个 `*TransferProhibited` 都会拒绝转移。所以"加了一个状态"从来不会放宽限制，只会收紧。

这带来一个实现上的推论：**服务端要维护状态的完整集合与每条状态的生命周期，而不是一个单值字段。**表结构上通常是 `domain_id + status + set_by + set_at + reason + expire_at`，查询时聚合成集合。同时每一次状态变更都必须留审计记录——谁在什么时间、依据什么设置了什么状态，这在争议处理时是唯一的事实来源。

## Hold 状态与区文件的关系

`*Hold` 和 `inactive` 的唯一直接后果是：**这个域名不出现在 TLD 的区文件里**，于是全网递归解析器拿到 NXDOMAIN 或无委派，域名不可访问。

```text
注册数据库（状态集合）
      │ 批处理扫描：哪些域名应当被委派
      ▼
区文件生成（排除 *Hold / inactive）
      │ 原子发布
      ▼
TLD 权威 DNS
```

两个必须理解的时延：

- **状态变更到解析生效不是实时的。**数据库改了，区文件要等下一个生成周期，权威 DNS 还要等区加载完成，下游递归解析器还要等 TTL 过期与否定缓存过期。这条链上的每一段都有延迟，见 [SYS2026](./SYS2026.md)。
- **否定结果也会被缓存。**域名被 hold 之后，递归解析器可能已经缓存了"不存在"这个答案，缓存时长受 SOA 里的最小 TTL 约束。所以"解除了 hold 但还打不开"在一段时间内是正常现象。

## 争议与锁定产品

两类常见的高保障锁定，本质都是 `server*Prohibited` 的组合：

- **注册局锁（Registry Lock）**：注册局提供的付费服务，任何变更都需要带外多因素授权（人工核验 + 一次性口令）。实现上是一组 `server{Update,Transfer,Delete}Prohibited` 叠加。
- **争议锁**：进入 UDRP（统一域名争议解决政策）或 URS（新顶级域的快速暂停系统）程序后，注册局按裁决机构通知施加锁定。URS 的结果还可能直接把域名置为 `serverHold` 使其不可解析。

对后端来说，这类锁定的关键不在于状态码本身，而在于**解锁路径必须带外且可审计**：不能有一个 EPP 命令能直接摘掉注册局锁，否则锁就没有意义。

## DDD 视角：谁修改哪份业务事实

状态机与状态码的背后，是 DDD 要回答的两个问题：**谁负责修改哪份业务事实，哪几条规则必须在同一事务里保护。**

- **Entity（实体）**靠身份判断是不是同一个东西：一个域名换了注册商，仍是同一条 Domain；判断标准是注册局分配的 domainId，不是它当前的属性值。
- **Value Object（值对象）**按值和规则判断：规范化域名（大小写、全半角、尾点统一后的形式）、注册期数这类日期范围。只要值相等即可替换，不需要单独追踪身份。
- **Aggregate / Aggregate Root（聚合 / 聚合根）**把必须在同一局部事务里保护的不变量圈起来：Domain 作为聚合根控制入口，"pendingTransfer 期间拒绝其它变更""状态集合是叠加而非覆盖"这类规则由聚合在一次提交里保护，外部不允许绕过聚合根直接改成员。
- **Bounded Context（限界上下文）**允许不同业务对同一个域名建立不同模型：注册管理上下文关心权限与生命周期；RDAP 上下文只持有为查询优化的派生视图（见 [SYS2024](./SYS2024.md)），两套模型不必长一个样。

```text
注册管理上下文                          对外查询上下文（RDAP）
    Domain 聚合根                          DomainReadModel 派生视图
       ├─ domainId：实体身份                 └─ 只为查询优化
       ├─ 规范化域名：Value Object
       ├─ 到期时间 / Registrar 归属
       └─ 状态变化规则、不变量

注册库事务提交 ─── 可靠事件 / CDC ───> 更新 RDAP 视图
```

**不要反向扩大事务**：注册数据与状态审计若在同一库，可用本地事务保护；RDAP、权威 DNS 区发布、第三方托管之间不应捆进一个巨大的长事务，而是靠稳定源数据、事件、版本与补偿完成协作。这条边界也解释了上一节"解锁必须带外且可审计"——跨上下文的动作本来就不能指望数据库事务兜底。
