> **本章定位：**Continuity。注册数据一旦丢失或不可用，受影响的是全体注册人而不是一个用户，所以它必须有一份独立于生产系统、可验证、可恢复的副本。这一章讲这条链路怎么设计，以及"失败必须可发现、可恢复、有审计"在工程上具体指什么。

## 为什么必须有托管

注册局是 TLD 注册数据的唯一权威记录方。如果它因为经营失败、技术灾难、合同终止或长期违约而无法继续运营，数据库里的东西没有任何其它地方能补回来——注册人已付费的域名、到期日、NS 委派、authInfo，全部只存在于这一份数据里。

托管（Data Escrow）就是为这个场景准备的：把注册数据定期交给一个**独立于运营方的第三方**保管，一旦运营方失效，接管方能用这份数据把 TLD 恢复起来继续服务。

对新顶级域，ICANN 还要求预先指定**紧急后端注册局运营方（EBERO, Emergency Back-End Registry Operator）**：当注册局或其 RSP 在关键功能上持续失败时，由它临时接管运营。EBERO 能接管的前提，就是它拿得到可用的托管数据。

所以托管不是"备份的另一种说法"：

| | 生产备份 | Data Escrow |
| --- | --- | --- |
| 目的 | 恢复自己的系统 | 让**别的组织**能接管运营 |
| 保管方 | 自己 | 独立第三方托管方（或按规定交付给 ICANN） |
| 格式 | 内部格式即可 | 必须是规范定义的可互操作格式 |
| 验证 | 常常不做恢复演练 | 接收方每次都要验证，且要能被第三方真正用起来 |
| 敏感数据 | 按内部标准 | 有独立的加密与密钥管理要求 |

格式、频率、字段范围、留存期这些**具体数值一律按适用规范确定**，不同 TLD、不同合同、不同时期的要求会变。后端实现上要把它们全部做成配置，不写死。

## 托管什么

范围是整个 TLD 的注册数据，不只是域名表：

| 数据 | 说明 | 敏感度 |
| --- | --- | --- |
| domain 对象 | 名字、状态集合、注册周期、到期日、NS 列表、联系人引用 | 中 |
| host 对象 | 名字、in-bailiwick 的 IP（glue） | 低 |
| contact 对象 | 注册人与各类联系人信息 | **高，含个人数据** |
| authInfo | 域名与联系人的授权码 | **最高，泄露即可劫持** |
| 注册商关联 | 域名归属哪个注册商、注册商自身信息与配额 | 中 |
| 元数据 | 托管时间、覆盖区间、对象计数、生成方标识、格式版本 | — |

对象模型见 [SYS2022](./SYS2022.md)，状态语义见 [SYS2023](./SYS2023.md)。

关键点是**元数据不是附属品**。接收方验证一份托管文件时，最先看的就是元数据：这是哪一天的、覆盖到哪个时间点、应该有多少个对象。没有元数据，就无法判断"文件是完整的但数据旧了"这种情况。

## 全量与增量

两种托管配合使用：

| 类型 | 内容 | 用途 |
| --- | --- | --- |
| 全量托管 | 某一时点的全部注册数据 | 冷启动恢复的基线 |
| 增量（差分）托管 | 自上一次托管以来发生变化的对象 | 把基线追赶到最新，减少每次的数据量 |

增量依赖一个**明确的基准点**：它必须能说清"我是相对于哪一份全量、覆盖哪一段区间"。链式的增量一旦中间缺一份，后面全部失效，只能回退到最近的全量重放。所以：

- 每一份增量都要记录它的前驱标识与覆盖区间；
- 监控要检查**链条是否连续**，而不只是检查每一份是否按时生成；
- 增量生成失败不能靠"下次补上"来掩盖，必须按截止要求处理。

## 一致性快照

托管文件必须代表**某一个时间点的完整一致状态**，不能是边写边导。

如果导出过程跨越了几十分钟，期间在线交易还在改数据，导出来的就是一个既不属于 T1 也不属于 T2 的混合体：可能出现 domain 引用了一个尚未导出的 contact，或者到期日与状态互相矛盾。这种数据在恢复时会直接产生悬挂引用。

实现上有两条路：

1. **从一致性快照读**：用数据库的一致性读能力（MVCC 快照、一致性备份接口）导出，导出过程不阻塞在线写入。原理见 [DBA1011](./DBA1011.md) 的 MVCC 与 [DBA1012](./DBA1012.md) 的一致性讨论。
2. **冻结写入导出**：停写窗口内导出。只在数据量小或允许停服时可行，注册局通常不接受。

选第一条时还要处理一件事：**快照时间点必须写进元数据**，并且增量托管的区间边界要与它对齐，否则全量与增量拼不起来。

## 交付链路

```text
① 生成      从一致性快照导出，按规范格式序列化
      ↓
② 自检      结构校验 + 对象计数 + 关键字段抽样 + 与前一份的差异合理性
      ↓
③ 保护      加密敏感内容，对文件签名
      ↓
④ 传输      通过安全通道交付给托管方
      ↓
⑤ 接收验证  托管方独立校验结构与完整性
      ↓
⑥ 回执      返回验证结果与接收标识
      ↓
⑦ 监控审计  全链路留痕，超期与失败告警
```

每一步都可能失败，而**第 ② 步和第 ⑤ 步是唯二能发现"内容不对"的地方**，其余步骤只能发现"流程没走完"。

### 密钥管理是独立问题

托管数据必须能被接管方解密，这意味着：

- **加密密钥不能只掌握在运营方手里**，否则运营方消失的同时数据也变成密文废纸；
- 密钥的分发、轮换、销毁要有独立流程，且与数据托管分开管理；
- 密钥有效期必须被监控——**证书或密钥在托管文件生成那天过期，是一个会静默潜伏很久才爆炸的故障**，因为文件生成本身是成功的。

## 失败必须可发现、可恢复、有审计

这是整章的工程核心，三条各自有明确含义：

### 可发现

| 失败点 | 表现 | 怎么发现 |
| --- | --- | --- |
| 生成中断 | 任务报错退出 | 任务状态监控（最简单的一类） |
| 生成"成功"但内容错 | 退出码 0，文件是空的 / 是旧的 / 对象数骤降 | **内容级校验**：对象计数与历史基线比对、覆盖时间点校验、与前一份的差异幅度告警 |
| 自检通过但接收方拒收 | 结构或完整性不合规 | 接收方回执必须被解析并纳入监控，不能只看 HTTP 200 |
| 增量链断裂 | 中间某份缺失 | 按前驱标识检查链条连续性 |
| 密钥/证书过期 | 加密或签名失败，或生成的文件无法解密 | 有效期提前预警 |
| 传输超时 | 未在窗口内送达 | 截止前分级预警，而不是超期后才告警 |
| 截止超期 | 已违反交付要求 | 升级流程 + 人工介入 |

最重要的一条经验：**进程成功 ≠ 内容正确。**只看任务退出码的监控，会漏掉绝大多数真正危险的失败。必须校验内容本身——对象数量、时间点、抽样字段，并与历史基线做趋势比对。

### 可恢复

- **能重生成**：任何一份托管都必须可以从其快照点重新生成，不依赖上一次的中间产物。这要求快照/导出窗口可重现，也要求生成任务是幂等的。
- **能重传**：传输失败要能重试而不产生重复交付。给每份文件一个稳定的唯一标识，接收方按标识去重。
- **不影响在线交易**：托管是重 I/O 的批处理，必须跑在读库或独立资源上，不能和 EPP 的在线路径抢同一份资源。这是注册局后端最常见的性能事故来源之一——批处理把主库拖垮，在线注册全线超时。
- **有兜底路径**：连续失败时要有降级方案（如先生成全量而非增量，或切换到备用导出通道），并且降级动作本身要记录。

超时与重试的通用纪律见 [SYS3011](./SYS3011.md)。

### 有审计

每一份托管都要留下可追溯的完整记录：

```text
文件标识 / 类型（全量或增量）/ 快照时间点 / 覆盖区间 / 前驱标识
对象计数 / 校验和 / 生成开始与结束时间 / 生成节点
加密与签名所用密钥标识 / 传输开始与结束时间 / 接收方回执与验证结果
重试次数 / 异常与处置动作 / 操作者
```

审计记录本身的留存期也按规范确定。它的价值在两个时刻体现：合规审计时证明你按时交付了，出事故时定位是哪一环、哪一天开始坏的。

## 恢复演练：没验证过的托管等于没有

托管数据可能几年都用不上一次，而这段时间里格式版本升过、数据库换过、加密算法轮换过、对象模型加过字段。**"每次接收方都验证通过"只证明文件符合格式，不证明它能被真正用起来。**

所以要定期做端到端演练：

1. 从托管方取回一份最近的托管文件；
2. 在一个隔离环境里解密、解析、装载；
3. 校验对象数量与抽样内容和生产库一致；
4. **用这份数据重建区文件**，验证能产出可用的 TLD 区（见 [SYS2026](./SYS2026.md)）；
5. 记录耗时——恢复用时本身就是个关键指标。

第 4 步最容易被省略，也最容易暴露问题：注册数据能导入不代表能正确生成区文件，两者之间的映射逻辑（哪些状态该被排除、glue 记录怎么算）可能已经悄悄变了。

## Zone 文件生成：同一类批处理

区文件生成和托管是**同源同形**的任务：都从同一份一致性快照派生，都是批处理，都要求完整性校验与原子交付，都有截止时限。差别只在消费者——一个给托管方，一个给权威 DNS。

所以它们应该共享同一套基础设施：快照获取、导出框架、校验器、交付与回执处理、监控与审计。做成两套独立实现，最后一定是两套各自的 bug。

区文件的特殊之处是它还要过一层**政策过滤**：`*Hold` 与 `inactive` 的域名不能出现在区里，见 [SYS2023](./SYS2023.md)。这意味着"数据库里有这个域名"和"区文件里有这个域名"是两个不同的判断，演练时要分别验证。

## 合规运营的整体形态

ICANN 合规不是一份文件的要求，而是一套持续运转的机制：

```text
规范（合同与技术规范定义要求）
   ↓
自评（运营方按检查项定期自查并出具报告）
   ↓
审计（第三方或 ICANN 核验，含数据与流程核验）
   ↓
整改（发现问题 → 通知 → 限期整改 → 复验）
   ↓
后果（持续违约可导致合同层面的处置，极端情况触发 EBERO 接管）
```

对后端团队来说，这套机制的实际含义是三件事：

1. **要求是可验证的，所以实现必须可观测。**每一条"必须按时交付""必须在 N 小时内可见"都对应一个需要被度量的指标。做不到度量就做不到证明。
2. **规范会变，代码不能写死。**期限、格式版本、字段范围都可能调整。把这些做成配置与版本化的 schema，而不是常量。
3. **证据要能随时拿出来。**审计时问"去年 3 月 14 日那份全量托管的接收回执在哪"，系统要能直接给出。这决定了审计日志的留存与检索能力必须在设计阶段就考虑，事后补不上。

这套思路与 [FIN2017 - 卡支付安全与合规基础](./FIN2017.md) 讲的合规形态是同构的：规范 + 可观测实现 + 可追溯证据 + 定期核验。
