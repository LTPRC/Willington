> **本章定位：**Publication。注册数据库是权威记录，但全世界能看到的只有 TLD 的权威区。这一章讲从数据库到区文件再到对外应答的这条发布链，以及 DNSSEC 签名在其中占的位置。协议层原理（递归与迭代、委派、信任链验证）见 [SYS2018](./SYS2018.md)。

## 注册局在 DNS 里的位置

```text
根区（.）           ← 由根区管理方运营，里面有各 TLD 的 NS 与 DS
   ↓ 委派
TLD 区（com.）      ← 注册局运营：NS、DS、glue
   ↓ 委派
二级域区（example.com.）← 注册人自己运营（或托管给云厂商）
```

注册局**只负责中间那一层**。它不管 `www.example.com` 解析到哪，那是注册人自己权威 DNS 的事；它也不做递归查询，那是递归解析器的事。注册局要交付的是：`example.com` 委派给哪几台 NS、它的 DS 是什么、以及 in-bailiwick NS 的 glue 记录。

## TLD 区文件里有什么

一个 TLD 区的记录种类其实很少：

| 记录 | 来源 | 说明 |
| --- | --- | --- |
| SOA | 区配置 | 主 NS、责任人邮箱、serial、刷新/重试/过期/最小 TTL |
| NS | 区配置 | TLD 自己的权威服务器列表 |
| DNSKEY | 签名流程 | 本区的 KSK 与 ZSK 公钥 |
| 每个已委派域名的 NS | 注册数据库 | 注册人通过 EPP 提交的 NS 列表 |
| 每个已委派域名的 DS | 注册数据库 | 注册人通过 EPP secDNS 扩展提交，可没有 |
| in-bailiwick NS 的 A/AAAA | 注册数据库 | glue 记录，解决循环依赖，见 [SYS2022](./SYS2022.md) |
| RRSIG | 签名流程 | 对上述每个 RRset 的签名 |
| NSEC / NSEC3 | 签名流程 | 权威地证明"这个名字/类型不存在" |

注意区文件里**没有 A 记录指向注册人的网站**（除非那是 glue）。TLD 区的作用只是把人引到下一级权威服务器，所以它的体量与域名数量成正比，与解析流量无关。

## 从注册数据库到区文件

区文件是注册数据库的一个**派生视图**，与 [SYS2025](./SYS2025.md) 的托管文件同源同形，但多了一层政策过滤：

```text
注册数据库（一致性快照）
   │
   ├─ 筛选：哪些域名应当被委派
   │     排除 *Hold（clientHold / serverHold）
   │     排除 inactive（没有 NS）
   │     排除 pendingDelete / redemptionPeriod
   │
   ├─ 展开：每个域名的 NS 列表、DS 数据、glue 记录
   │
   ├─ 序列化：生成区文件，SOA serial 递增
   │
   ├─ 自检：记录数对账、格式校验、与上一版差异合理性
   │
   └─ 原子发布：切换到新版本
```

筛选规则必须与 [SYS2023](./SYS2023.md) 的状态语义严格一致。这里最常见的 bug 是**状态集合的判断写漏了一种**：比如只判断了 `clientHold` 没判断 `serverHold`，结果被注册局暂停的域名还在对外解析；或者反过来，把处于 `autoRenewPeriod` 的域名误排除，导致大量正常到期未续的域名提前从区里消失。

由于状态是集合而非单值，正确的写法是"**存在任何一个导致不发布的状态就不发布**"，而不是"状态等于某个值"。

## 原子发布与分发

区文件不能边生成边对外服务，否则解析器会读到半成品——某些域名的 NS 已更新、另一些还是旧的，甚至读到语法不完整的区导致加载失败。

```text
生成新版本 → 完整性校验 → 签名 → 分发到全部权威节点 → 各节点加载 → 一致性确认后统一切换
```

要点：

- **SOA serial 必须单调递增**，下游靠它判断区是否变化。serial 回退或不递增会导致 secondary 不同步。
- **分发到多站点后再切换**，不能出现"一半节点是新版本、一半是旧版本"的长时间窗口。切换期间同一个查询在不同节点得到不同答案，会被下游当成解析不稳定。
- **向 secondary 的分发用 AXFR（全量）/ IXFR（增量）**。IXFR 依赖 serial 差量，链断了就回退 AXFR。
- **回滚路径要预先准备**：发现新版本有问题时，能立刻切回上一个已签名的版本，而不是重新生成一遍。

## DNSSEC 签名流水线

DNSSEC 的原理与信任链见 [SYS2018](./SYS2018.md)，这里只讲注册局侧怎么运营它。

**KSK / ZSK 双密钥模型：**

| 密钥 | 签什么 | 特征 |
| --- | --- | --- |
| ZSK（Zone Signing Key） | 区内所有 RRset（NS、DS、SOA、glue 等），但 DNSKEY RRset 除外 | 短、轮换频繁，签名开销可控 |
| KSK（Key Signing Key） | 只签 DNSKEY RRset | 长、轮换稀少，因为它的哈希要被发布到父区的 DS |

这么分的原因很直接：如果只用一把长密钥签所有记录，每条 RRSIG 都会很大，区体积和应答体积一起膨胀；如果只用一把短密钥，父区的 DS 就得跟着频繁更新，而 DS 更新要走跨组织的流程。分成两把之后，ZSK 可以随便换，只要 KSK 不动，父区的 DS 就不用变。

**签名的时机与规模：**TLD 区有数百万到上千万条委派，每次区更新都要对变化的 RRset 重新签名。实践上有两种做法：

- **离线预签名**：生成区文件后批量签名，产出已签名的区，再分发。签名是 CPU 密集操作，要放在独立资源上，不能占用在线应答节点。
- **在线签名（on-the-fly）**：权威服务器收到查询时即时签名。省存储、天然保证与数据一致，但对每节点的 CPU 和缓存设计要求高。

无论哪种，**签名都不能阻塞在线解析**。这是与 [SYS2025](./SYS2025.md) 里"托管批处理不能拖垮 EPP 在线路径"完全同构的约束。

**否定应答也要签名。**NSEC 直接给出"下一个存在的名字"，等于把整个区的内容串成一条链，攻击者可以顺着遍历（zone walking）。所以大体量公开区普遍用 **NSEC3**，把名字哈希后再串链，并可配 salt 与 opt-out 来降低遍历与签名开销。选 NSEC 还是 NSEC3、salt 多久轮换，属于区策略，要在设计阶段定下来。

## 两条 DS 链路必须分清

这是 DNSSEC 运营里最容易混的一点——同一个"DS 记录"概念，出现在两个完全不同的位置，走两条完全不同的变更路径：

| | TLD 自己的 DS | 域名的 DS |
| --- | --- | --- |
| 发布在哪个区 | **根区** | **TLD 区** |
| 谁提交 | 注册局向根区管理方提交 | 注册人通过注册商，用 EPP secDNS 扩展提交 |
| 谁签发对应的 DNSKEY | 注册局自己的 KSK | 注册人自己权威 DNS 的 KSK |
| 变更流程 | 跨组织的行政 + 技术流程，周期长 | 一次 EPP 命令，周期短 |
| 出错的后果 | 整个 TLD 的 DNSSEC 验证失败 | 单个域名的验证失败 |

**TLD 自己的 DS 出错是灾难级故障**：根区的 DS 与注册局的 KSK 对不上，全网验证型递归解析器会判定整个 TLD 不可信，其下所有域名一起变成 SERVFAIL。影响面是整个 TLD，而不是一个域名。

所以 KSK 轮换必须严格按流程走，且在过渡期内**父区同时存在新旧两条 DS**，等新 KSK 确认发布生效后再撤旧的。反过来做（先撤旧 DS 再发新 DS）会造成一段无信任链的窗口。

## 密钥轮换

| 轮换对象 | 影响范围 | 常用做法 |
| --- | --- | --- |
| ZSK | 只在区内，父区无感 | 预发布（先把新公钥放进 DNSKEY，等缓存过期再用它签名）或双签（过渡期新旧 ZSK 同时签） |
| KSK | 需要同步更新父区的 DS | 双 DS 过渡：新旧 KSK 并存 → 父区加入新 DS → 确认生效 → 停止用旧 KSK 签 DNSKEY → 父区移除旧 DS |

轮换的每一步都受**缓存 TTL 与传播时延**约束：新公钥发布后要等旧的 DNSKEY 缓存在全网过期，才能开始用它签名，否则会有解析器拿不到新公钥而验证失败。所以轮换周期不是"想多快多快"，而是由 TTL 决定的下界加上安全余量。

**密钥过期是最典型的静默故障。**ZSK 到期而轮换任务失败，区还在正常应答，但所有 RRSIG 已过期，验证型解析器全部返回 SERVFAIL——从注册局自己的监控看，"DNS 服务可用率 100%"。所以必须监控**验证成功率**，不能只监控应答成功率。

## 可用性与部署形态

TLD 权威 DNS 是全局关键基础设施，规范要求很高的可用性（新顶级域的 SLA 对此有明确规定）。常见部署：

- **Anycast**：同一组 IP 从多个地理位置宣告，BGP 把查询路由到最近的节点。单点故障自动收敛到其它站点，同时降低解析时延。
- **多站点、多运营商**：避免单一机房或单一网络路径成为共同失效点。
- **只读、可水平扩展**：权威节点不持有可写状态，区文件是它的唯一输入，因此扩容就是加节点 + 分发区。
- **抗滥用**：DNS 放大反射攻击常以权威服务器为反射源，要限制应答放大倍数、控制 ANY 查询行为、启用响应速率限制（RRL）。

## 端到端时延链

一次 EPP 修改到全世界看到结果，要穿过这么多段：

```text
EPP update 提交
  → 注册数据库提交（同步，毫秒级）
  → 下一个区生成周期（分钟级）
  → 签名（分钟级，取决于规模）
  → 分发到全部权威节点（秒到分钟级）
  → 权威节点加载并切换（秒级）
  → 递归解析器缓存过期（受 NS/glue 的 TTL 约束，可能数小时）
  → 否定缓存过期（受 SOA 最小 TTL 约束）
```

**只有第一段是实时的。**后面每一段都是延迟来源，其中最后两段完全不在注册局控制范围内。

这解释了两个常见的"故障"其实不是故障：

- 注册商改了 NS，但用户那边几小时后才生效——递归解析器的缓存还没过期。
- 域名被 hold 了，但还能访问一段时间；或者解除 hold 了，却还打不开——正向与否定缓存都还在生效。

工程上的正确做法是把这条链**每一段的时延都做成可观测指标**：区生成时延、签名时延、分发时延、各节点当前 serial、端到端探针解析结果。出问题时才能定位是哪一段卡住，而不是笼统地说"DNS 有问题"。

## 权威与递归的边界

回到 [SYS2021](./SYS2021.md) 的那个辨析，这里给出技术层面的分界：

| | 权威 DNS（注册局做的） | 递归解析器（注册局不做） |
| --- | --- | --- |
| 数据来源 | 自己保管的区 | 别人的权威服务器 + 本地缓存 |
| 应答标志 | AA（authoritative answer）置位 | 不置 AA |
| 是否缓存 | 只缓存自己的区 | 核心能力就是缓存 |
| 是否发起迭代查询 | 不发起，只回答自己的数据 | 从根开始逐级迭代 |
| 服务对象 | 全网递归解析器 | 终端用户的 stub resolver |
| 关键指标 | 应答时延、可用率、区发布时延 | 缓存命中率、解析成功率、QPS 承载 |

注册局后端岗位涉及的是左边这一列，再加上把注册数据库变成区的整条发布链。右边那一列是另一套技术栈，通常由不同的团队甚至不同的公司负责。
