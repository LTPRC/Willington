## Cache Aside 缓存模式【P0】

### 人话解释

应用自己管理缓存（Cache Aside Pattern）：读的时候先查缓存，未命中查数据库并回填；写的时候更新数据库并让缓存失效。

### 读取

```text
GET Redis
 ├─ hit → return
 └─ miss → DB → SET Redis → return
```

### 更新

常见做法：

```text
UPDATE DB
   ↓
DELETE CACHE
```

### 放回系统

MySQL 通常是权威数据源（Source of Truth），Redis 是可重建的缓存。

### 面试回答【30-60 秒】

> Cache Aside 是常见缓存模式：读取先查 Redis，未命中再查数据库并回填；更新时常见做法是先更新数据库，再让缓存失效，由后续读重新加载。因为 Redis 和 DB 是两个独立系统，所以仍要考虑并发下的短暂不一致。

## 为什么不简单同时更新 DB 和 Redis？【P0】

### 人话解释

两个独立系统没有天然原子性：

```text
Update DB success
Update Redis fail
→ 不一致
```

并发时还可能旧值覆盖新值。

### 常见思路

数据库作为 **Source of Truth（权威数据源）**，更新 DB 后删除缓存。

### 为什么常"先更新 DB，再删缓存"

如果先删缓存，再更新 DB，中间可能有读线程读取旧 DB 值并重新写回缓存（旧值回填窗口更大）。

### 但不是绝对强一致

删除缓存也可能失败，并发仍有窗口。强一致业务要设计额外机制（补偿、消息、对账等）。

### 面试回答【30-60 秒】

> MySQL 和 Redis 是两个独立系统，普通本地事务无法让两边天然原子更新。Cache Aside 常以数据库为权威数据源，先提交 DB 再删除缓存，减少典型旧值回填窗口。但它仍不是绝对强一致，对一致性要求高的业务还要考虑补偿、消息等机制。

## 缓存穿透【P0】

### 人话解释

查询的数据在 Redis 和 DB **都不存在**，所以每次请求都穿过缓存打 DB。

### 为什么危险

恶意或异常请求可持续冲击数据库。

### 方案

- 参数校验；
- 缓存空结果 + 短 TTL；
- 大规模场景可用 Bloom Filter。

**Bloom Filter**：一种空间效率很高的结构，可以快速判断"某值肯定不存在，或者可能存在"。数学实现不在本知识库 P0 范围内。

### 放回系统

```text
不存在ID → Redis miss → DB miss → cache null / reject
```

### 面试回答【30-60 秒】

> 缓存穿透是查询的数据在缓存和数据库里都不存在，导致每次都访问数据库。常见处理包括参数校验、短 TTL 空值缓存，大规模场景也可使用 Bloom Filter 减少明显不存在 Key 的请求。

## 缓存击穿【P0】

### 人话解释

一个超级热点 Key 突然失效，大量请求同时回源 DB。

```text
Hot Key expires
      ↓
大量 miss
      ↓
MySQL
```

### 核心解决思想

不要让所有请求同时重建。

### 方案

- 互斥重建：只允许一个请求去加载数据，其余等待/重试；
- 热点数据逻辑过期 + 异步刷新（不用物理 TTL，后台线程异步更新）。

### 系统位置

发生在"Redis miss → DB"这条链路。

### 面试回答【30-60 秒】

> 缓存击穿通常是高并发热点 Key 失效后，大量请求同时 miss 并访问数据库。核心是避免所有请求同时重建缓存，可以通过互斥控制只允许一个请求加载，或者对热点数据使用逻辑过期和异步刷新等方式。

## 缓存雪崩【P0】

### 人话解释

不是一个 Key，而是大量 Key 同时失效，或者 Redis 整体不可用。

### 危险

大量流量瞬间落 DB。

### 方案

- TTL 加随机抖动，避免同一时刻集中失效；
- Redis 高可用（副本、故障转移）；
- 限流 / 降级；
- DB 保护；
- 热点数据预热。

### 面试回答【30-60 秒】

> 缓存雪崩是大量缓存同时失效或缓存服务整体不可用，导致大量请求集中落到数据库。常见措施包括分散 TTL、提高 Redis 可用性，并在应用侧做好限流、降级和数据库保护。

### 秒答区分

```text
穿透：数据本来不存在
击穿：一个热点 Key 失效
雪崩：大量 Key 失效 / Redis 整体故障
```

## 资金类数据的 Source of Truth【P0++】

### 结论

**一般不应该把普通 Redis 缓存当成资金余额的唯一事实来源。**

原因：资金账务通常要求

- 强持久性；
- 明确事务语义；
- 可审计、可追溯、可恢复；
- 对账；
- 并发更新正确性。

Redis 可以做：

```text
缓存
限流
分布式协调
热点读取
临时状态
```

但"余额最终是多少"的权威记录通常应该落在可靠的账务 / 数据库 / ledger 系统。即使使用 Redis 做性能加速，最终权威状态仍应由账务存储决定。

### 面试回答【30-60 秒】

> 对资金余额这类核心账务数据，我不会把普通 Redis 缓存作为唯一 Source of Truth。Redis 可以承担热点缓存、限流或辅助状态，但账务事实需要更强的持久化、事务、审计、恢复和对账能力。即使使用 Redis 做性能加速，最终权威状态仍应由账务存储决定。

## 热点数据：Hot Key【P1】<img src="./icons/paypal.gif" />

Hot key 即热点 key，指的是在一段时间内访问量远远高于其他 key 的 redis key，导致大部分的访问流量在经过 proxy 分片之后都集中访问到某一个 redis 实例上。解决方案如下：

### 使用本地缓存

在 client 端使用本地缓存，从而降低了 redis 集群对 hot key 的访问量。但是同时带来两个问题：

- 本地缓存过大，增加系统开销。
- 本地缓存和系统的一致性。

### 利用分片算法的特性，对 key 进行打散处理

根据一个随机数使用 hot key 得到一个 tmp key，程序会优先访问 tmp key，除非得不到数据才再访问原来的 hot key 并将其内容写回 tmp key。

tmp key 的过期时间建议比 hot key 的过期时间长上一个较小的随机正整数，保证在 hot key 过期时，所有 tmp key 不会同时过期而造成缓存雪崩。

可以利用原子锁来写入数据，减小 db 的压力。

------------------------------------------------------------------------

## Big Key【P1】

Big key 即数据量大的 key，由于其数据大小远大于其他 key，导致经过分片之后，某个具体存储这个 big key 的实例内存使用量远大于其他实例，造成内存不足；同时大 key 的读写/删除也可能阻塞主线程。

处理方式：

- 对 big key 进行拆分（按字段拆 Hash、按元素拆 List/Set/Zset）；
- 删除时使用 unlink 异步释放（4.0+），避免 del 阻塞；
- 检测：redis-cli --bigkeys、MEMORY USAGE 等。

## Redis 挂了怎么办？【P0】

### 人话解释

如果 Redis 是缓存，最大危险往往是：

```text
Redis Down → 所有请求打 MySQL → DB 也被打挂
```

### 应用保护

- 限流；
- 降级；
- 防无限重试；
- 保护数据库；
- 某些场景可有本地短期缓存。

### Redis 层

生产通常还会考虑副本、故障转移、Cluster 等高可用机制（详见 [DBA2014](./DBA2014.md)）。

### 放回系统

```text
Redis Failure → Failover + Application Protection → Protect DB
```

### 面试回答【30-60 秒】

> Redis 不可用时，如果它承担缓存角色，我首先关注流量是否瞬间穿透到数据库，所以应用侧需要限流、降级和 DB 保护，不能无限重试。同时 Redis 本身通常通过副本和故障转移等机制提高可用性。

## 宕机后的降级策略【P0++】

不要统一回答"直接查 DB"，先看 Redis 用途。

### 场景 A：普通读缓存

```text
Redis 失败
↓
有限回源 DB
↓
限流 / 熔断保护 DB
```

危险：

> Redis 整体挂掉时所有流量同时回源，可能把 DB 一起打死。

所以要：

- 限流；
- 本地缓存（若适合）；
- 降级非核心功能；
- 熔断；
- 恢复后逐步放量。

### 场景 B：分布式锁

不能说：

> Redis 锁挂了，那就不加锁继续执行。

如果锁保护的是核心写操作，应考虑：

```text
fail closed
→ 暂停 / 拒绝高风险操作
```

或者切换到业务已有的其他一致性机制。

### 场景 C：Session / 临时状态

看系统是否有：

- replica / failover；
- 持久化；
- 重建能力。

### 面试回答【30-60 秒】

> Redis 宕机后的策略取决于它承担什么职责。普通缓存可以有限回源 DB，但必须同时限流和熔断，防止缓存故障把数据库打穿；如果 Redis 承担核心分布式锁，我不会直接绕过锁继续执行高风险写操作，而是优先 fail closed 或切换到经过设计的兜底机制。恢复后还要控制流量逐步回升，避免瞬间重建缓存造成二次冲击。

## Redis 线上问题排查 SOP【P0/P1】

统一框架：

```text
现象（用户/监控报什么）
↓
Metrics（哪个指标异常）
↓
排查（命令/日志定位根因）
↓
止损（限流/降级/扩容/回滚）
↓
复盘（容量与设计修正）
```

### 通用工具

- `INFO`（memory / stats / clients / replication 分片查看）；
- `SLOWLOG GET`、`LATENCY` 系列命令；
- `redis-cli --bigkeys`、`--hotkeys`、`MEMORY USAGE`；
- 监控：延迟、QPS、连接数、内存、evicted_keys、命中率。

### Redis 变慢 / Timeout

- 现象：接口 P99 上升、timeout 报错、客户端队列堆积。
- Metrics：latency、slowlog、CPU、网络 RTT、QPS 突增。
- 排查：大 key 操作（del/hgetall）、阻塞命令（keys/flushall）、fork（BGSAVE / AOF rewrite）造成的暂停、慢查询、达到 maxmemory 后频繁淘汰、swap。
- 止损：定位并消除慢命令来源、拆分 / 异步删除大 key（unlink）、错峰持久化、扩容或限流。

### Memory 暴涨

- 现象：内存曲线快速上涨，甚至 OOM / 频繁淘汰。
- Metrics：used_memory、mem_fragmentation_ratio、evicted_keys、客户端 / 复制缓冲区。
- 排查：Big Key、无 TTL key 堆积、缓冲区（client-output-buffer）、复制 backlog、COW 膨胀。
- 止损：清理无用 key、给 key 加 TTL、限制缓冲区、拆分实例。

### Eviction 增加

- 现象：evicted_keys 持续增长、命中率下降、部分 key 提前消失。
- Metrics：evicted_keys、命中率、maxmemory 配置。
- 排查：容量不足，还是策略问题（volatile-* 只能淘汰带 TTL 的 key；noeviction 会直接写失败）。
- 止损：扩容、调整淘汰策略、清理无用数据。

### Hot Key / Big Key

- 现象：单实例 CPU / 带宽打满、延迟抖动。
- 排查：--hotkeys / --bigkeys、业务监控热点维度。
- 处理：Hot Key 本地缓存 + tmp key 打散；Big Key 拆分 + unlink（见上文）。

### 连接池耗尽

- 现象：`Could not get a resource from the pool`。
- 排查：慢命令占用连接、连接泄漏（未归还）、maxTotal 过小、未设超时。
- 止损：修复慢查询、设置超时（connectTimeout / soTimeout）、修正池配置、按并发评估扩容。

### 网络 / 连接问题

- 现象：连接拒绝、超时、主从切换抖动。
- 排查：网络分区、实例故障、Sentinel / Cluster 切换事件。
- 处理：高可用配置、客户端重连与重试策略（防无限重试）。

### Redis Down / Cache Avalanche / DB 被打满

- 现象：Redis 不可用后 DB CPU、连接数暴涨。
- 链路：缓存失效 → 全量回源 → DB 打穿。
- 处理：限流、熔断、降级、本地缓存、恢复后逐步放量（见《宕机后的降级策略》）。

## 应用场景与业务案例【P1】

### 高并发抢红包<img src="./icons/alibaba.gif" /><img src="./icons/citic.gif" />

2019 年春晚，百度的抢红包活动和观众互动总次数达 208 亿次，春晚红包分为四轮，每轮大概为 40 亿次到 60 亿次之间。每次如果持续半小时的话，平均每秒要承受超过 300 万次的互动，峰值肯定超过千万。

抢红包就是一个抢购系统，有如下两个特点：

- 允许在有库存时抢购失败
- 必须快速将结果返回给用户

百度 2019 年春晚扛住了压力，未出现系统崩溃，其中 Redis 起到了至关重要的作用。使用 Redis 的原理是**先插入、后检查有效性**，具体流程如下：

把原始的大红包拆分成若干小红包，然后维护两个 Redis 队列，分别代表未消费红包和已消费红包。再用 Redis 中的一个 map 来过滤已抢到红包的用户，如果没有，则从未消费红包队列中取出一个小红包，再 push 到另一个已消费队列中，最后把用户 id 放入去重的 map 中。

### 新浪微博<img src="./icons/citic.gif" />

所有评论存储在 MySQL 的一张表中。

- Redis 使用 list 有序存储评论 id，数据键值对为 <微博id, list<评论id>>。
- Redis 使用 hash 根据评论 id 存储评论内容，数据键值对为 <微博id, hash<评论id, 评论内容>>。

用户发表评论时，评论内容存放到 MySQL 数据库，获得评论 id。评论 id push 到 Redis 的 list 中，评论内容转成 json 格式放进 Redis 的 hash 中。

用户查看评论时，按照分页数据从 list 中取出对应的评论 id，根据评论 id 从 hash 中获取评论内容。

### 秒杀【P1】

利用 Redis 队列操作的原子性实现秒杀。

```java
public class Miaosha {

    public static void main(String[] args) {    
        JedisPoolConfig jedisPoolConfig = new JedisPoolConfig();
        jedisPoolConfig.setMaxIdle(10);
        jedisPoolConfig.setMaxWaitMillis(10000);
        jedisPoolConfig.setMaxTotal(1024);

        JedisPool jedisPool = new JedisPool(jedisPoolConfig, "127.0.0.1", 6379);
        ExecutorService executor = Executors.newFixedThreadPool(30);
        for (int i = 0; i < 20; i++) {    
            executor.execute(new CustomerTask(i, jedisPool));    
        }
        executor.shutdown();    
    }
}

class CustomerTask implements Runnable {    

    private int customerId;    
    private JedisPool jedisPool;    

    public CustomerTask (int customerId, JedisPool jedisPool) {    
        this.customerId = customerId;    
        this.jedisPool = jedisPool;    
    }

    @Override
    public void run() {
        // 执行秒杀    
        Jedis client = jedisPool.getResource();
        String productId = client.lpop("str");
        if (productId != null && productId.length() != 0) {
            System.out.println("顾客" + customerId + "抢到了" + productId + "号商品");
        } else {
            System.out.println("顾客" + customerId + "没有抢到商品");
        }
    }
}
```

课堂演示级别；真实生产还需要：库存预热、原子扣减（Lua / decr 判断）、限购去重、异步下单、幂等与对账。

## 开发与接入【P2】<img src="./icons/citic.gif" />

### 命令行方式 redis-cli

redis-cli 是一个命令行接口，是一个允许从终端向 Redis 服务器发送命令、从服务器读取响应的简单程序。它通过交互模式在 Redis 服务上执行相应的 redis 命令操作。

通常的登录方式：

```bash
redis-cli -c -h host -p port -a passwd
```

### API 方式

支持 Java、Python、Ruby、PHP 等客户端，其它语言的客户端具体见官网网站：http://redis.io/clients

### Jedis (Java)

添加依赖，比如 jedis-2.10.2.jar 和 commons-pool2-2.6.2.jar

```java
Jedis jedis = null;
try {
    jedis = new Jedis("xxx.xxx.xxx.xxx", port);
    jedis.auth("PASSWORD");
    jedis.set("KEY", "VALUE");
    System.out.println(jedis.get("KEY"));
} finally {
    jedis.close();
}
```

建议使用 Jedis 2.9 版本或以上，2.9 版本提供了访问带密码的 redis cluster 的 API。

Jedis 是连接池和连接分离的 API，Jedis 类代表连接，不能多线程环境下使用。如果想在多线程环境下使用 Jedis，可以通过使用 JedisPool 获取到一个 Jedis 然后再调用它的 API，使用完毕后再通过 addShutdownHook 来关闭 JedisPool。
