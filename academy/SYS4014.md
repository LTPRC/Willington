# Rune Mexico：一个长生命周期合规案件为什么需要 Workflow

Rune Mexico 可以理解为 PayPal 墨西哥业务中的一套合规案件生命周期与 SAR（Suspicious Activity Report）披露能力。它最值得长期保留的技术价值，并不是“项目用了 Netflix Conductor”，而是它把一个很典型的企业级问题暴露得非常完整：**当一件业务不再是一次 HTTP 请求里几百毫秒完成，而是要跨越多个服务、人工审核、外部系统、超时和失败恢复时，程序应该怎样表示“这件事目前做到哪了”。**

普通 CRUD 往往可以在一次调用栈里完成：校验参数、写数据库、返回结果。合规案件不同。一个 Case 可能先被创建，再进入调查和审核，之后准备披露数据、做身份字段校验、生成报告、调用外部报送边界，最后进入 Filed；中间还可能被退回、更正、升级人工处理，或者长时间等待下一步动作。此时“业务状态”本身已经成为系统需要长期保存和推进的数据，不能只存在于某个 Java 方法的执行现场里。

```text
上游告警 / 案件来源
        │
        ▼
 Compliance Case
        │
        ▼
┌─────────────────────────────┐
│ casemgmtlifecycleserv       │
│ RUNE_MX_workFlow.json       │
│ State / Action / Transition │
│ Handler / Permission        │
└──────────────┬──────────────┘
               │
               ▼
      Review / Escalate
               │
               ▼
┌─────────────────────────────┐
│ sarcasemgmtserv             │
│ RFC / CURP Validation       │
│ Worker / Handler            │
│ RFPDisclosureClient         │
└──────────────┬──────────────┘
               │
               ▼
       外部披露 / Filing
               │
               ▼
 Filed / Correct-Amend / Escalate
```

Rune 因而是理解 Workflow、State Machine 和 durable execution 很好的现实案例。项目里公司已经存在基于 Raptor / Netflix Conductor / scm workflow 的工作流基础设施，业务团队是在这个底座上定义和交付 Mexico 的 workflow，而不是从零实现一个工作流引擎。这个 ownership 边界需要一直记住：**我做的是平台之上的业务 Workflow、Handler、Worker 和外部客户端，不是 Conductor 平台本身。**

# 为什么 `step1(); step2(); step3();` 不够了

如果一个流程只有几步，而且能在一次请求里快速完成，最简单的顺序调用通常就是最好的设计。为了“架构感”强行引入 Workflow Engine 反而会增加部署、调试和运维成本。真正需要 Workflow 的信号，是流程开始跨越一次调用的生命周期。

例如下面这种代码表面上很直观：

```java
validate();
generateReport();
callExternalSystem();
waitForReviewer();
submit();
```

问题在 `waitForReviewer()` 出现时已经很明显。人工审核可能几个小时以后才发生，不可能让一个线程、一个 HTTP request 或一个数据库事务一直等着。即使没有人工步骤，外部系统也可能 timeout，服务进程可能重启，第三步成功而第四步失败。此时程序必须回答的不再只是“这个方法抛了什么异常”，而是：前三步哪些已经产生业务事实、下一次从哪里继续、能不能安全重试、是否需要人工介入。

所以长流程真正需要的是一种**持久化的执行上下文**。流程离开当前 JVM 后仍然存在；服务重启后仍知道执行到哪；一个 Worker 挂掉后仍能判断是否重新调度。这也是 durable execution 的核心直觉：不是让线程永远活着，而是让**执行进度能够跨进程生命周期活下来**。

```text
短事务：
Request ── Java Stack ── Response
             │
          几百毫秒

长流程：
Case ── State A ── State B ── 等待 ── State C ── Failure ── Retry ── State D
  │                                                            │
  └────────────── 持久化的业务/执行状态跨越多个进程生命周期 ────┘
```

# State Machine：先把“案件怎么走”说清楚

状态机解决的是另一个很具体的问题：一个 Case 在任何时刻都应该处于一个可解释的业务状态，而不是靠几十个 boolean 和散落在 Service 里的 `if/else` 猜出来。

状态机最基本的元素是 State、Event/Action、Transition 和 Guard/Condition。State 表示当前处境，例如 REVIEW；Action 表示发生了什么，例如 APPROVE；Guard 表示这次动作是否允许，例如当前操作者必须具有相应 reviewer 权限；Transition 则定义动作成功后从 REVIEW 去哪里。

```text
              APPROVE
 REVIEW  ─────────────────► NEXT_STATE
   │                           ▲
   │ REJECT                    │
   ▼                           │
INVESTIGATION ─── RESUBMIT ────┘

Guard:
- 当前角色是否允许执行 Action
- Case 当前状态是否允许迁移
- 必要业务条件是否满足
```

Rune 的 `RUNE_MX_workFlow.json` 正是在这一层发挥作用。现有材料记录它大约 654 行，包含 13 个业务状态节点和 49 条迁移，并带有 action、permission、handler mapping 等信息。这里要特别避免一个常见误解：**13 个 state 不是“Conductor 有 13 个 Task”。** State 是 Compliance Case 的领域状态；Task/Worker 更接近工作流引擎实际调度的执行单元。二者有关联，但不是同一个维度。

# Workflow 和 State Machine 不是同一个东西

State Machine 更关心“现在是什么状态，发生什么事件后可以去哪”；Workflow 则还要处理“为了完成整个流程，需要执行哪些 Task，它们什么时候运行，失败如何重试，等待如何恢复”。

可以把两者的关注点放在一起看：

```text
Domain State Machine
--------------------
State + Action + Guard
          │
          ▼
     New State

Workflow Orchestration
----------------------
Task A → Task B → Wait → Task C
  │                  │
 retry             timeout
  │                  │
  └──── failure / recovery ────►
```

在 Rune 里，`casemgmtlifecycleserv` 的 JSON 更接近“Compliance Case 怎么走”的领域状态和迁移语义；Conductor/Raptor 一类 workflow infrastructure 更关心任务执行生命周期；`sarcasemgmtserv` 中的 Worker/Handler 则负责真正执行 disclosure 相关业务操作。理解这三层，比记住某个 Conductor API 更重要。

# 声明式 Workflow：流程规则和执行代码应该分开到什么程度

如果把所有业务流程硬编码在 Java 里，最初往往很简单：

```java
if (state == REVIEW) {
    if (canApprove(user)) {
        approve();
        if (needDisclosure(caseData)) {
            generateDisclosure();
        }
    }
}
```

真正的问题不是 `if` 本身，而是规则不断增长以后，State、Role、Jurisdiction、Action、异常路径和具体业务执行全部纠缠在一个代码结构中。要理解某个案件为什么从 A 走到 B，需要阅读很多 Java 分支；要调整流程，也可能必须修改执行代码并重新发布整个服务。

Rune 的做法是把一部分相对“流程化”的信息放入 JSON：有哪些状态、允许哪些 Action、如何 Transition、对应哪些 Handler、有什么 permission；Java 则保留真正需要代码执行的能力，例如字段校验、数据处理和外部 HTTP 调用。这样配置描述“**什么时候调用谁**”，代码描述“**被调用后具体做什么**”。

```text
RUNE_MX_workFlow.json
        │
        ├── State
        ├── Action
        ├── Transition
        ├── Permission
        └── Handler Mapping
                 │
                 ▼
          Java Handler / Worker
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
     Validate  Generate  External Call
```

声明式不等于“以后业务变化都不用改代码”。如果只是把已有能力重新组合，例如某个已有 Handler 在新的状态迁移中被调用，配置化可以降低代码耦合；但如果监管要求增加了一种全新的校验或外部调用，仍然需要新的 Java 能力。长期设计里应该追求的是**稳定能力代码化、易变编排配置化**，而不是追求“零代码”。

配置化也有自己的成本。JSON 写错可能直到运行时才暴露，Handler 名称和参数结构可能与 Java contract 漂移，复杂流程在纯文本里也可能越来越难读。所以成熟的配置驱动系统通常还需要 schema validation、引用完整性检查、transition graph 检查、版本管理和测试。这里后几项更适合作为“如果今天重新设计”的工程增强，不应倒推成 Rune 当时全部已经实现。

# Conductor：业务开发真正需要理解到哪一层

Netflix Conductor 可以先理解成一个 Workflow Orchestration Engine。业务把流程描述给它，它负责推进 Task 的执行生命周期，而真正的业务逻辑通常由 Worker 完成。对于 Rune 这种应用开发，最重要的不是研究 Conductor 源码，而是理解 Workflow Definition、Task、Worker、Task Status、Retry、Timeout 和 Workflow State 之间的关系。

```text
Workflow Definition
        │
        ▼
     Task A
        │
        ▼
     Worker A  ──► 业务系统 / DB
        │
 COMPLETED / FAILED
        │
        ▼
     Task B ...
```

Engine 必须知道一个 Task 是等待、执行中、成功、失败还是超时，才能决定下一步。Worker 则应该尽量像一个边界清楚的业务能力：输入明确、输出明确、错误可分类、重复执行尽量安全、副作用可控。

这里也能看出 Workflow Engine 和 MQ 的差异。MQ 非常适合异步解耦和事件传递，但消息队列本身并不会天然告诉业务“这个 Case 当前处于哪个领域状态、接下来允许哪个 Action、人工审核已经等待多久、失败后应该从哪个节点继续”。当然可以围绕 MQ 自己建立状态表、超时扫描、重试、补偿和可视化，但做到后面，本质上已经在自行实现一部分 Workflow Engine。

# Worker 和 Handler：不要把编排逻辑重新塞回业务代码

Worker 最适合承载相对原子的业务能力，例如 Validate、Generate、Save、Submit。它不应该重新复制一套完整流程，否则上层有一份 JSON 状态机，Worker 内部又有另一份隐式状态机，两者迟早会漂移。

Handler 则常用于状态迁移前后的领域逻辑，例如 action filtering、validation、post-processing、SLA check 或 domain condition。Rune 材料中的 `SARRuneMXPostProcess`、`SarDeferred24hAlertHandler` 就是很具体的抓手。`SarDeferred24hAlertHandler` 的资料支持 24 小时逾期判断逻辑，但真实 `sendMLROAlert()` 发送仍有 TODO，所以长期笔记里必须把“判断逻辑存在”和“完整通知链路已落地”分开。

同样，`PpBalanceMxDisclosureDataLoader` 在当前仓库材料对应版本中仍然是 mock implementation。可以理解它目标上承担披露数据加载边界，但不能反向写成“已经完成 CCDS/CCTS 的 production integration”。项目知识库里保留这种未完成状态很重要，因为几年以后最容易发生的记忆污染，就是把“当时设计目标”记成“我已经交付的事实”。

# 外部调用的 Timeout 为什么不是一个简单的数字

Rune 中 `RFPDisclosureClient` 是很好的可靠性案例。现有材料支持它使用 Java 原生 `HttpClient`，存在约 600 秒的长 timeout、有限 retry/backoff，并处理 `InterruptedException` / `InterruptedIOException`。600 秒听起来很长，但 timeout 不能脱离 downstream 的业务语义来决定。

假设监管报送请求在对端处理了很久。客户端等待到 timeout 后只能知道“我没有在规定时间内收到成功响应”，却不能推出“对端一定没有执行成功”。网络世界里完全可能发生：

```text
Client                         Server
  │                               │
  ├──────── request ─────────────►│
  │                               ├── processing
  │                               ├── business success
  │        response 丢失/过慢     │
  │◄──────────── X ───────────────┤
  │
  ├── timeout
  │
  └── retry ─────────────────────►  ← 重复副作用风险
```

所以 timeout 的真正语义是：**调用方停止等待**，而不是“远端事务失败”。这也是为什么 Timeout、Retry 和 Idempotency 必须放在一起设计。越是有业务副作用的接口，越不能把“超时就重试”当作默认答案。

# Retry：恢复瞬时故障，不是把错误多执行几遍

Retry 的第一步不是决定重试几次，而是先判断失败类型。临时网络异常、连接重置、部分 5xx、短暂 downstream unavailable 可能属于 transient failure，重试有机会成功；参数非法、RFC/CURP 校验失败、权限错误、明确业务拒绝或永久配置错误，即使执行十次也不会变好。

```text
Failure
   │
   ├── Transient ──► bounded retry ──► backoff ──► success / fail
   │
   └── Permanent ──► fail / exception path / manual intervention
```

Rune 的 RFP client 材料支持有限次数 retry 和 exponential backoff，其中“一次 retry”的证据相对较强；更具体的 backoff 秒数主要来自二次备战总结，长期知识库不必为了显得精确而死记。真正重要的是 bounded retry：监管报送有副作用，不能无限轰击 downstream。

Backoff 的意义也不仅是“等一会”。如果 downstream 正在过载，所有调用方立即同步重试，会把一次短暂故障放大成 retry storm。指数退避让后续尝试逐步拉开。大规模系统通常还会加入 jitter，避免大量客户端在同一时刻再次醒来；jitter 属于通用分布式系统知识，不应表述成 Rune 已确认实现。

# Retry 一出现，Idempotency 就跟着出现

Workflow Engine 的任务执行通常必须接受一个现实：**同一个 Task 有可能被执行不止一次。** 最典型的窗口是业务副作用已经成功，但 Worker 在向 Engine 报告 COMPLETED 之前崩溃。

```text
Worker
  │
  ├── DB write SUCCESS
  │
  ├── process crashes  X
  │
Engine
  │
  └── 看不到 COMPLETED
          │
          ▼
        Retry
          │
          ▼
     同一业务操作再次执行
```

这就是 at-least-once execution 思维。工作流层的“重试 Task”与业务层的“操作可以执行两次”完全不是一回事。真正可靠的 Worker 应该尽量 retry-safe。

通用的幂等手段包括 business key、current-state check、unique constraint、atomic conditional write、idempotency key 和 downstream idempotent API。比如一次披露可以有稳定业务键，DB 用唯一约束做最后防线；或者 downstream 接受 idempotency key，同一个请求重复到达时返回同一业务结果。

Rune 历史备战资料记录过：

```sql
INSERT ... SELECT ...
WHERE NOT EXISTS
```

作为 DB-side conditional insert 的防重思路，但新增代码 OCR 没有给它与 RFP client 同等级的直接证据，因此应保留为**待进一步代码核实的项目事实**。另外，`WHERE NOT EXISTS` 也不能脱离具体数据库、隔离级别和唯一约束就宣称“天然绝对原子”。如果今天重新设计，更稳妥的方案通常是让数据库唯一约束或其他原子条件写承担并发下的硬约束，而不是 Java 层先 `exists()` 再 `insert()`。

```java
// 典型 race condition：不要把这种 check-then-act 当成强幂等
if (!exists(businessKey)) {
    insert(record);
}
```

两个线程完全可能同时看到 `exists == false`，然后都进入 insert。**幂等不是“代码里判断过一次”，而是并发条件下仍然只能形成一个正确业务结果。**

# Partial Failure：分布式长流程不能幻想全局 rollback

普通本地事务里，我们习惯于失败就 rollback。但长流程跨服务、跨人工步骤、跨外部监管边界以后，很多动作已经成为不可撤销的业务事实。例如报告已经生成、人工审核已经完成、甚至外部报送已经被对端接受，此时再说“整个流程回滚”通常没有实际意义。

更合理的思维是先区分：哪些步骤可以安全 retry，哪些步骤需要幂等，哪些步骤可以 compensation，哪些步骤只能通过新的业务动作修正。Rune 中 `CORRECT_AMEND` 这种语义就比“把数据库恢复成昨天的样子”更符合真实合规业务：已经发生的披露事实不能假装不存在，需要通过更正/修订形成新的可审计事实。

```text
Step A ✓ → Step B ✓ → External Filing ✓ → 后续发现问题

不是：
<──────────── magical global rollback ────────────

而可能是：
                         Correct / Amend
                               │
                               ▼
                       新的业务事实与审计记录
```

这也是 Saga/Compensation 类思想真正应该理解的地方：补偿不一定是数学意义上的逆操作，更不是数据库 undo；它是业务上允许的纠正动作。Rune 本身不需要为了面试强行贴 Saga/TCC 标签，理解 partial failure 和业务补偿边界就够了。

# Java Interrupt：Cancellation 是协作式的

`RFPDisclosureClient` 的材料明确涉及 `InterruptedException`、`InterruptedIOException` 和 Sonar S2142，因此 Java interruption 是 Rune 能自然连接到的底层知识。

Java 的 `interrupt()` 不是 JVM 强制杀线程，而是向线程发出一个协作式中断信号。某些可中断的 blocking operation 收到信号后会抛出 `InterruptedException`，并可能清除 interrupt status。如果代码把异常当普通错误打印后继续运行，上层就可能失去“这个任务应该停止”的信号。

```java
try {
    doBlockingWork();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new RuntimeException("task interrupted", e);
}
```

具体向上抛什么异常取决于 API contract，但原则是不要无声吞掉 interruption。恢复 interrupt flag 可以让更上层仍然观察到取消请求。

Timeout 和 cancellation 也不是同一个概念。Timeout 表示“调用方不愿意继续等待”，cancellation 表示“希望正在执行的工作停止”。即使 timeout 后调用了 `interrupt()`，如果业务代码不检查中断、正在执行不可中断 I/O，或者吞掉了 `InterruptedException`，任务也未必马上停止。因此在有副作用的 Worker 里，**“客户端已经放弃等待”与“后台业务已经停止执行”必须被视为两件事。**

# Workflow 恢复的关键不是“重新启动”，而是知道从哪里继续

服务进程挂掉以后，真正决定系统能否恢复的不是 Kubernetes 能不能重新拉起 Pod，而是 Workflow/Task 的执行状态是否存在于进程之外。如果状态只在 JVM 内存中，Pod 拉起来只是得到一个全新的空进程；如果 Engine 持久化了 workflow state 和 task lifecycle，新的 Worker 才有可能继续接管未完成任务。

Rune 使用的 Conductor/Raptor 平台具体 HA、内部存储部署并不是个人 ownership，因此不能凭经验补成“PayPal 就是用某某数据库实现”。长期知识应该保留这个边界。可以确定的原理是：durable workflow 必须有持久化执行状态；可以确定的项目事实是公司已有 workflow infrastructure 承担了这部分平台能力；业务侧负责定义 Workflow 和实现 Worker/Handler。

Worker crash 后是否 retry，也不能只看“进程死了”。如果 Task 已经产生副作用，就要结合 task status、timeout、retry policy 和业务幂等共同判断。于是又回到了这一章最重要的闭环：

```text
Durable State
     ↓
Failure Recovery
     ↓
Retry
     ↓
Possible Duplicate Execution
     ↓
Idempotency / Side-effect Control
```

# Human-in-the-loop：人也是长流程中的一种异步依赖

Rune 和纯后台批处理 Workflow 的一个明显区别，是它包含合规人员的审核、升级和更正。人不会像 RPC 一样在 500ms 内返回，所以 human task 天然要求流程能够进入一个长期等待状态，而不是占住计算资源。

从系统设计角度看，人工审核可以被抽象成一种特殊异步步骤：系统保存 Case 当前状态和待办，用户稍后通过 UI/API 产生 Action，Action 再触发下一次状态迁移。这里的重点不是“轮询一个人有没有点按钮”，而是把等待本身建模为合法状态。

```text
Automated Task
      │
      ▼
WAITING_FOR_REVIEW
      │
      │  数小时 / 更久
      │
Human Action: APPROVE / REJECT / ESCALATE
      │
      ▼
Next State
```

这种建模也解释了为什么 Case Management 很适合状态机。人工流程最怕隐式状态：数据库里一堆字段都存在，但没人能明确回答“当前到底轮到谁做什么”。显式 State + Action + Permission 能把这个问题变成可检查的领域规则。

# SLA / Timer：等待本身也会产生业务事件

长流程进入等待状态后，还会自然出现“等多久算异常”的问题。Rune 材料中的 `SarDeferred24hAlertHandler` 就是这个方向的真实抓手：资料支持 24 小时逾期判断，但完整 MLRO notification 发送当时仍有 TODO。

从通用 Workflow 设计看，Timer 不应该理解成“让线程 sleep 24 小时”。更合理的是持久化一个 deadline，由调度机制在到期时产生 timer event 或扫描出 overdue item，再触发告警/升级逻辑。这样服务重启不会丢掉计时，也不会长期占用线程。

```text
Case enters WAITING
        │
        ├── persist deadline = T + 24h
        │
        ▼
   no thread sleeping
        │
        ▼
deadline reached
        │
        ▼
 timer / scheduler event
        │
        ▼
 overdue handling / escalation
```

这里的 timer 持久化具体由 Rune 哪一层实现，需要以代码证据为准；上图是通用系统设计模型，不应反写成项目事实。

# Workflow Versioning：运行中的老 Case 不能被新规则随意改写

只要 Workflow 可以配置化，就迟早会出现版本问题。今天的 JSON 是 v1，明天监管规则变化改成 v2，那么昨天已经运行到一半的 Case 应该按哪个流程继续？如果直接热替换所有运行中实例的定义，老 Case 可能突然发现原来的下一步不存在，或者已经完成的路径在新图里语义改变。

因此成熟的 Workflow 系统一般需要明确版本语义：新建实例使用新版本，已经运行的实例继续绑定创建时的定义或兼容的迁移策略。历史 Rune 备战材料中有“old case 保留 workflow snapshot/version、v1/v2 并行”的描述，但这部分证据不如代码级 RFP client 强，面试时应当区分“材料记录”和“我亲自实现”。

如果今天设计，一个很自然的模型是：

```text
Workflow Definition v1 ──► Case A / Case B

Workflow Definition v2 ──► New Case C / Case D
```

只有在明确设计了 migration 时，才把运行中的 Case 从 v1 迁移到 v2。Workflow Definition 本身也应该和代码一样可追踪、可回滚、可审计。

# Observability：长流程最怕“系统没挂，但 Case 不动了”

普通 API 的可观测性经常围绕 latency、error rate、QPS。Workflow 还多一个问题：系统所有服务都健康，但某个 Case 可能卡在某个状态几小时。只看服务 CPU 和 HTTP 5xx 很可能什么都发现不了。

所以长流程 observability 更适合围绕业务执行上下文建立关联：

```text
caseId
workflowId
workflowVersion
taskId / taskType
currentState
retryCount
downstreamRequestId
lastTransitionTime
```

这样才能回答“这个 Case 为什么没继续”。如果今天重新设计 Rune，我会更强调把这些标识贯穿日志、trace 和指标，并对 state age、retry exhaustion、异常 transition 等建立 dashboard/alert。这里属于今天的设计增强，不是声称当时已经完整实现 OpenTelemetry 链路。

# Workflow JSON 的测试不能只验证“能 parse”

配置驱动系统很容易产生一种错觉：JSON 能加载就代表流程正确。实际上 syntax valid 只说明括号和字段类型没问题，真正危险的是语义错误，例如迁移指向不存在的 state、Handler 名称不存在、某个状态没有任何合法出口、权限配置导致所有角色都无法推进，或者新版本意外产生环路。

所以如果今天构建一套更完整的 Workflow CI，我会把检查分成几层：schema validation 保证结构；reference validation 保证 state/handler/action 引用存在；graph validation 检查 unreachable state、dead end 和非法 cycle；contract test 验证 JSON 参数与 Java Handler contract；scenario test 则跑典型 happy path 和 rejection/correct-amend path。

```text
JSON
 │
 ├─ Syntax / Schema
 ├─ Reference Integrity
 ├─ Transition Graph
 ├─ Handler Contract
 └─ Scenario Test
        │
        ▼
     Deployable
```

这也是声明式系统的一个普遍规律：把逻辑从代码搬到配置，并没有让逻辑消失，只是把错误类型从 compiler error 部分转移成 configuration error。因此配置越强大，越需要接近代码级别的测试和治理。

# RFC / CURP：业务 Validator 为什么也值得保留

Rune 不只有 Workflow。`sarcasemgmtserv` 中的 RFC/CURP validator 是很典型的“监管规则工程化”：外部制度给出格式和校验规则，工程侧要把它变成确定、可测试、可维护的代码。

RFC 与 CURP 的具体模 11 / 模 10 加权算法在项目材料中有记录，但 SYS4014 的重点不是背墨西哥身份证算法，而是理解 Validator 在长流程中的位置：**确定性业务校验应该尽量在产生外部副作用之前失败。** 如果输入本身无效，最合理的结果通常不是让 RFP client 重试，而是 fail fast / fail close，进入数据修正或人工路径。

```text
Input Data
    │
    ▼
RFC / CURP Validation
    │
    ├── invalid ──► correction / manual path
    │
    └── valid
          │
          ▼
     Generate / Submit
```

这也再次说明“失败”不能只用技术异常分类。`SocketTimeoutException` 与“RFC 校验不通过”都可能让当前 Task 不能继续，但前者可能适合 retry，后者重复一百次仍然不会成功。可靠系统需要把 technical transient failure 和 business permanent failure 分开。

# Rune 的两个服务边界

长期复习时最容易混的是 `casemgmtlifecycleserv` 和 `sarcasemgmtserv`。可以用一句话区分：**前者更像案件生命周期的“宪法”，后者更像真正执行披露工作的“工人”。**

`casemgmtlifecycleserv` 中的个人贡献量较小但语义关键，现有材料记录 Mexico/RUNE_MX 范围约 6 commits（含 merge），涉及 `RUNE_MX_workFlow.json`、`SARRuneMXPostProcess`、`CORRECT_AMEND`、`SarDeferred24hAlertHandler` 等。`sarcasemgmtserv` 的 Java 代码贡献更重，材料记录约 57 commits，包含 RFC/CURP validation、`RFPDisclosureClient`、Worker/Handler、测试、Sonar/JDK21 等。

```text
casemgmtlifecycleserv
“Case 应该怎么走”
        │
        ▼
 State / Action / Transition
        │
        ▼
sarcasemgmtserv
“这一步具体怎么做”
        │
        ├── Validate RFC/CURP
        ├── Generate / Save
        └── RFP External Call
```

这个边界也是面试 ownership 最稳的表达方式：不需要声称自己是整个 Rune 架构 owner，但可以明确说自己既碰过 orchestration/configuration 层，也在 execution service 有实质 Java 代码贡献。

# Rune 和 GoPay 为什么不是重复项目

GoPay 和 Rune 都有“流程”，但系统设计问题的重心并不一样。GoPay 是 Merchant Onboarding/KYC，核心是商户数据收集、多维自动检查、第三方结果汇聚、准入决策、幂等和第三方依赖可靠性；Rune 是 Compliance Case Lifecycle，核心是长生命周期案件如何通过 State Machine / Workflow 推进。

```text
GoPay
Merchant Onboarding / KYC
        │
        ├── 多维检查
        ├── 第三方依赖
        ├── 异步结果汇聚
        ├── 准入决策
        └── 幂等 / 一致性 / 降级

Rune
Compliance Case Lifecycle
        │
        ├── State Machine
        ├── Workflow
        ├── Human-in-the-loop
        ├── Retry / Timeout
        └── Failure Recovery
```

所以长期面试策略也应该保持这个边界：如果问题进入高并发、DB、事务、复杂幂等、第三方治理，GoPay 是更强的主战项目；如果问题是 Workflow、State Machine、长流程、人工步骤、Task retry，Rune 才是最合适的证据。项目选择本身也是面试能力的一部分，不需要让一个项目承担所有题型。

# 三个值得长期记住的设计故事

Rune 第一个值得记住的故事，是**为什么长流程要从 Java 调用栈中“拿出来”**。Compliance Case 跨越自动任务、人工审核和外部系统，一次方法调用无法自然表达数小时等待、进程重启和 partial failure。公司已有 Conductor/Raptor 底座，Mexico 层用 JSON State/Transition 和 Java Worker/Handler 分离流程规则与执行能力。它的 trade-off 是流程更显式、恢复更自然，但配置调试、版本和 contract 治理变得更重要。

第二个故事，是 **RFP external call 的 timeout 不是失败证明**。材料支持 `RFPDisclosureClient` 有 600 秒 timeout、有限 retry/backoff 和 interruption handling。调用方超时以后，对端可能已经成功，所以不能把 retry 当作无副作用动作。这一件事自然把 timeout、retry、idempotency 三个看似独立的知识点串成了一个可靠性问题。

第三个故事，是 **Workflow retry 与业务 exactly-once 是两回事**。Worker 可能已经写库成功，却在上报 COMPLETED 前崩溃，于是 Engine 再次调度。Workflow 层允许 at-least-once execution 后，业务 Worker 就必须考虑 retry-safe。项目历史资料有 DB-side conditional insert 的防重记录，但证据等级需要保守；真正长期应该掌握的是 business key、state check、unique constraint、conditional write 和 downstream idempotency 这些通用工具。

# 如果今天重新设计 Rune，我会补什么

这部分必须明确属于今天的系统设计思考，不倒推成历史项目事实。

首先会加强 Workflow Definition 的静态验证，让 JSON 在 CI 阶段就完成 schema、reference、graph 和 Handler contract 检查，而不是等运行时才发现流程配置错误。其次会为所有有副作用的 Worker 定义统一的 idempotency contract：每个操作明确 business key，DB 侧尽量有唯一约束/原子条件写，调用 downstream 时如果支持 idempotency key 就贯穿使用。

再往后是 observability。长流程排障需要把 caseId、workflowId、taskId、workflowVersion、retryCount 和 downstreamRequestId 串起来，同时监控 state age，而不只是服务 error rate。对于 human task 和 timer，则应该让 deadline 成为持久化业务数据，避免把等待实现成线程 sleep 或单机内存定时器。

最后是版本治理。Workflow JSON 与 Java code 一样应该有明确版本，运行中的老 Case 不应被新 Definition 随意改变语义；如果确实需要迁移，要把 migration 当成显式工程动作，而不是“发布新 JSON 就自动解决”。

# 面试中的项目边界

Rune 最好的定位是 Workflow / State Machine / 长流程经验的辅助证明，不需要把它包装成个人最复杂的分布式系统。Conductor 是平台团队提供的基础设施；DataLoader 在当前材料对应版本仍有 mock；MLRO notification 的真实发送仍有 TODO；DB conditional insert 的幂等证据等级也低于 RFP client。这些边界不是项目的缺点，而是保证几年后仍能准确讲述真实 ownership 的锚点。

如果面试官继续问高并发、复杂事务、MySQL、MQ 或完整第三方治理，可以自然说明 Rune 更偏长流程编排，然后切到 GoPay；如果问题转向 AI Agent、MCP、Retrieval、Validation，则切到 Solphin。Rune 本身讲清楚“Case 怎么走、Task 怎么跑、失败怎么恢复、重试为什么要求幂等”就已经完成使命。
