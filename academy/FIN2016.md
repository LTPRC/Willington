> **本章定位：**Card System Integration。把卡系统拆成五块听懂架构讨论，重点接后端工程经验：同步/异步、幂等乱序、超时重试，以及授权链路对时效的特殊要求。

## 系统分五块

| 模块 | 负责什么 |
| --- | --- |
| 卡管理 | 开卡、激活、冻结、注销、限额、卡状态 |
| 交易处理 | 接收授权或交易事件、作出判断、管理交易状态 |
| 账户与账务 | 余额、额度、冻结、扣款、退款等资金变化 |
| 外部集成 | 对接银行、处理商及相关服务，转换接口和处理通知 |
| 对账与运维 | 核对差异、监控异常、追踪交易和处理工单 |

实际系统可以合并模块，这个划分是为了分清职责。

## 同步受理 ≠ 业务成功

对接一个外部卡服务，先确认两件事：

1. **职责与交易标识**：各方管哪一段，用什么标识把交易串起来。
2. **每个接口的语义**：哪些同步返回最终结果，哪些只是"受理成功"。例如开卡请求已受理，卡可能还没真正创建完成。

再明确错误码、限流、签名、对账数据和故障时的处理方式。"接口调用成功"和"业务处理成功"必须分开——这是读任何支付接口文档的第一反应。

## 回调重复与乱序

- **重复**：用事件标识 + 业务操作标识做幂等。
- **乱序**：用状态前置条件、版本号或外部结果校验，不能让晚到的旧通知覆盖已确认的新状态。
- 涉及资金时，同一资金操作只记账一次。

## 超时、重试与结果未知

- 网络故障、临时不可用 → 按协议重试。
- 余额不足、卡已注销这类明确业务拒绝 → 重试没意义。
- 结果未知 → 先确认对方是否已经处理（查单、对账），不能无条件生成一笔新交易。

## 授权链路为什么特殊

收银台正在等结果，授权链路有明确的响应时限：要控制依赖数量、超时和延迟，不能在实时判断里串一长串慢接口。还有个必须预先约定的业务决策——**实时授权服务不可用时，是批准还是拒绝？**这是资金风险与可用性的权衡：批准保体验但冒资金风险，拒绝保安全但伤可用性。技术超时不意味着可以默认批准所有消费。

## CaaS 是什么

Card as a Service：把发卡和卡管理等能力通过接口提供给其他产品使用。平台可能直接提供部分能力，也可能整合银行和处理商。注意边界：JD 里 CaaS 覆盖到哪一层要看团队分工；做了自己的卡产品，不等于自己取得发卡资格或直接实现了所有卡网络协议。

## 本章面试主线

> 卡系统五块：卡管理 / 交易处理 / 账户账务 / 外部集成 / 对账运维。集成三原则：受理 ≠ 成功、回调幂等防乱序、结果未知先查单。授权链路特殊在时效和失败策略（批准还是拒绝要预先约定）。CaaS 是卡能力开放，不等于拿到发卡牌照。
