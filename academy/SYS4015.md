## 1. 项目定位

CBEC 主要面向第三方支付机构、商户等 B 端主体，连接支付机构、银行内部核心/外汇/支付系统与监管体系。系统覆盖进口、出口、集中/实时购汇、集中结汇、收付汇、预购汇、文件登记、还原申报、对账、差错和预警等能力。

监管允许支付机构在跨境互联网支付场景中，通过银行代理完成小额结售汇、跨境外汇支付和监管申报。系统目标口径：**全流程、全币种、不落地**。

## 2. 进口 / 出口业务

``` text
进口：
中国消费者 → RMB → 支付机构 → 中信银行
                         ├→ 购汇 RMB→FX
                         ├→ 境外付汇
                         └→ 还原申报/国际收支申报
                                      ↓
                                  境外商户

出口：
境外消费者 → FX → 支付机构 → 中信银行
                         ├→ 收汇
                         ├→ 结汇 FX→RMB
                         └→ 监管申报
                                      ↓
                                  境内商户
```

### 进口完整业务步骤

1. 消费者在境外网站下单。
2. 订单信息进入支付机构/银行相关链路。
3. 消费者确认订单。
4. 消费者向支付机构支付人民币。
5. 支付机构与中信交换数据。
6. T+1 集中购汇。
7. 对个人购汇信息进行还原申报。
8. 中信向境外支付外币。
9. 国际收支数据还原申报。
10. 双方交换处理结果。
11. 交易完成。

面试必须区分三条线：**业务信息流、资金流、监管数据流**。

## 3. 核心业务概念

### 集中购汇

多笔消费者订单按币种聚合，再形成集中购汇交易。系统还需要保留与原始订单的关联。

支付机构收集多笔消费者订单后：

1. 按币种汇总。
2. 计算需要购买的外币金额。
3. 对每种外币发起一笔购汇指令。
4. 同时关联一批原始订单。
5. 客户资金已经进入备付金账户后才发起，因此银行无需垫资。

本质：`N 笔消费者订单 → 按币种聚合 → 1 笔集中购汇`。

### 实时购汇

更接近下单时间、粒度更细、使用实时汇率，可降低付款与实际购汇之间的汇率风险。通常关联单笔订单。

### 集中付汇

多笔订单按币种汇总后统一向境外付款。原始订单申报信息通过文件提交银行。

### 还原申报

银行面对支付机构时可能只看到聚合资金，但监管需要真实消费者、收款人、金额等明细，因此需要把聚合交易还原为原始交易主体。这也是订单文件、登记、差错、对账和申报任务大量存在的原因。

``` text
支付宝集中购汇 1000 万美元
        ↓
    不能只报一笔
        ↓
还原成消费者 A / B / C / ...
        ↓
按实际付款人、收款人、金额
        ↓
    监管申报
```

### 预购汇

历史资料存在报价、申请、T+1 交割、损益等流程；属于系统能力，当前不能说成本人主导设计。

``` text
T 日：支付机构获取报价 → 预购汇申请 → 锁定/形成交易
T+1：全额交割 / 部分交割 / 0 元交割 → 计算损益
```

笔记记录的状态机：

``` text
INITIAL → ACCEPTED ├─→ REJECTED
                    └─→ FILLED → SETTLED
```

具体失败状态存在笔记疑问，面试中不硬说。

## 6. UCP / BP Java 开发模型

UCP = Unified Channel Platform，统一渠道平台。目标是多渠道整合、统一开发框架、SOA 化、集中分层，并提供技术规范、开发规范、公共资源和基础服务。"渠道"指把客户指令送进银行业务系统的入口：网银、手机银行、电话银行、ATM、柜面、电子商务、银企直联等。

BP 是 Java Business Processing 应用。

### FO / BP / Base

``` text
                 UCP
┌────────────────────────────────┐
│   FO Frame    Base    BP Frame │
└────────────────────────────────┘
```

- **FO（Front Office）**：位于前端，封装客户端通信，基于 Web 应用框架，接收渠道请求。
- **BP（Business Processing）**：Java Application，基于 Socket Server，负责业务处理，接收 FO / 前置发来的服务请求，通过交换平台等访问银行底层能力。
- **Base**：提供组件管理、DAO、事务、日志、配置、后台任务、公共类与工具等。

### BP 核心结构

``` text
             Front / 外联 / 上游
                    │
                 TCP/IP
                    ↓
              SocketServer
                    ↓
              Service Request
                    ↓
              Thread Pool
        ┌───────────┴───────────┐
     报文处理                 异常处理
        ↓
     Context → ServiceFlow → Component Pool → DAO → Database

外围基础能力：ServiceRegistry / Communication / FTP / HSM /
Transaction / Monitor / Background Task
```

### 请求处理流程

``` text
Socket 收到请求
 → 创建业务处理执行体 → 提交线程池
 → 读取数据 → 解析通信包/分包 → 解压/解密
 → 根据 ServiceID 查 ServiceReqCfg.xml
 → 找到 ServiceFlow → 创建线程 Context → XML → Context
 → processService()
 → 业务 Component / DAO / 下游调用
 → makeEBStream() → 返回 XmlEBStream
 → 压缩/加密/分包 → Socket Response
```

### ServiceFlow 开发模式

``` text
ServiceID → ServiceReqCfg.xml → Flow Class（继承 ServiceFlow）
 → preCheck() → Validation Component
 → process() → Business Component
 → ExchangeSend / DAO
```

Flow 调用 Component，Component 再调用 DAO / 下游服务。典型 DAO 工具：BaseDAO、DBSession、IndexQueryExecutor、NameQueryExecutor、IndexUpdateExecutor、NameUpdateExecutor。

### Context

Context 是框架里非常核心的概念：平台和组件之间传递数据、Component 之间传递数据、方法之间共享当前请求上下文、保存 XML 报文/日志对象/通信服务等。典型方式 `context.put(key, value)` / `context.get(key)`。

可以类比现代系统中的 Request Context / Map 型请求上下文，但**不要说成 Spring ApplicationContext**。

### 后台任务与监控

后台任务配置在 `SYSDATA/Task.xml`，任务类型包括 once / startup / period / periodic。典型用途：日终批处理、状态同步、对账、垃圾清理、定时监控。CBEC 的例子：`GetExPaySttTask`，周期 600 秒，并配置禁止执行时间和最大并发数。

监控分两类：实时监控（记录每笔请求从读取到返回的处理耗时）和定时监控（定期记录 JVM、DB Connection Pool、Communication Token、系统状态）。

## 7. 文件批处理

跨境支付存在大批量订单、监管明细、对账、日终和原始交易还原，因此文件处理是正常工程模型：

``` text
行外应用 → 报文通知 → 外联前置 → 行外FTP GET → 行内FTP PUT → 回执 → 通知行内应用
```

行内 → 行外（对账文件、来账文件）流程反向。

不能简单把文件模式评价为"落后 API"。

## 8. 幂等、防重与状态

材料明确存在防重发流水、交易结果查询、定时状态同步。

``` text
请求 → 银行成功 → 响应丢失 → 调用方重试
```

如果没有防重，可能造成重复扣款、付汇、解付或申报。Senior 视角应串成：

`Timeout → Outcome Unknown → Query Status → Retry → Deduplication / Idempotency`

### 正确思想不是立即重做

``` text
CBEC → 核心完成资金操作 → Response 丢失 → CBEC 认为 UNKNOWN
```

处理路径：

1. 保存 UNKNOWN / PROCESSING。
2. 使用原业务流水查询下游。
3. 定时状态同步。
4. 日终对账兜底。
5. 必要时人工处理。

支付交易不是普通 HTTP GET：如果下游已经成功，盲目 retry 会再次扣款/付汇。重试必须建立在幂等业务号、防重、状态查询、下游幂等、对账之上。

### 状态机思想

跨境交易不能只用 boolean，至少存在：

``` text
INIT / PROCESSING / SUCCESS / FAIL / UNKNOWN
```

原因：下游超时不等于失败；网络失败不等于资金失败；文件交易可能异步；监管登记可能晚于资金交易；对账可能修正状态。"状态"是支付系统的核心建模对象。

### 事务边界

银行跨系统调用（本地 DB + 核心 + 外汇 + 监管 + 第三方支付机构）无法靠一个 DB Transaction 覆盖，真实系统需要组合：本地事务、业务流水、幂等、状态机、状态查询、重试、补偿、对账、人工差错处理。

一个可以用于理解、但不能冒充项目事实的通用幂等模型：

``` text
BEGIN
SELECT ... FOR UPDATE
if status == SUCCESS: return previous_result
if request_no already processed: return previous_result
execute business
update status
COMMIT
```

具体幂等算法、行锁落在哪张表哪笔交易，若无历史证据，不说成本人设计。

## 9. 对账与差错

资金系统需要比较业务记录、资金结果和外部渠道结果：

``` text
业务系统账 ↔ 核心资金账 ↔ 支付机构账
```

培训材料明确出现的跨境外汇对账：结汇结果文件、购汇结果文件、付汇结果文件（本地 DB），备付金交易明细（查询核心）。不能只相信同步 API 返回。

日终可计算：

``` text
支付机构集中外汇申报金额 - 还原申报汇总金额 = 差额
```

超过阈值则形成差错/预警数据，进入差错处理、延迟登记预警或人工处理。具体算法和本人 Ownership 仍以历史资料为准。

## 10. 交易安全

培训材料明确记录：

- 专线或 HTTPS / SFTP。
- 数字证书签名和验签。
- 文件摘要 MD5 / SHA。
- 文件 3DES + RSA 加密。
- 交易频度控制。
- 文件大小限制。
- 白名单。

理解层面：`传输安全 + 身份认证 + 完整性校验 + 内容加密 + 访问控制 + 流量/频率控制`。不要把 2018 年材料中的算法选择包装成今天的安全最佳实践。

## 11. 支付宝专项

支付宝是 CBEC 中重要的特殊接入方。相较标准版：支付宝主动询价、主动发起预购汇、交易量大、对汇率敏感、存在批量文件和自动状态同步。

### 多笔解付登记簿

需求背景：境外资金尚在途中，卖家希望尽快确定汇率/提现，单笔报文能力与多笔业务之间存在矛盾。设计中出现登记簿：

``` text
SWIFT / 来账 → 跨境电商登记簿 → 拆分 → 1 / 2 / 退 等处理
```

编号形式记录为：`时间戳 + 来账报文编号 + 序号`。这些是系统材料，不代表本人主导该设计。

## 12. Ownership

**可以说**：参与 CBEC 业务开发；做常规业务功能/CRUD；熟悉 ServiceFlow→Component→DAO；接触购结汇、收付汇、监管申报、文件、对账。

### 简历口径与待考古项

当前简历描述包括：跨境支付系统核心模块研发（订单审核、用户管理、外币结算）；升级系统消息队列架构实现内部业务模块解耦；参与支付清算系统集成，了解人民银行大小额支付、银联及网联清算流程。

## 13. 60 秒项目介绍

> 我在中信银行前半段主要参与跨境电商系统开发。系统主要服务第三方支付机构，例如进口场景下消费者先向支付机构支付人民币，支付机构把多笔订单按币种汇总后，由银行完成购汇和境外付汇。因为银行看到的可能是聚合资金，而监管需要真实消费者和订单明细，所以还要处理文件登记、还原申报、国际收支申报、状态同步和对账。技术上系统基于中信 UCP/BP Java 体系，通过外联平台接支付机构，向下连接交换平台、核心、外汇和监管系统。我个人当时主要做其中的业务功能和常规开发，不把整个架构包装成自己设计。

- 订单与结算：order-id、order-info、settlement-id、shop-id、账单/结算文件、到账通知。
- 资金：提现流水、结算流水、结售汇流水、防重发流水、备付金流水、汇入流水、外汇来账、汇率。
- 合规：集中购汇登记、集中结汇登记、国际收支申报、个人结售汇登记、文件登记。
- 通用状态：00 处理中 / 01 成功 / 02 失败 / 03 未知。

### DB2 与环境

CBEC 支付平台数据库：DB2 9.7、DB：ECDB、默认 Schema：CBECUSR。设计思想包括按应用隔离表空间、当前/历史数据分离、静态参数/动态业务数据分离。生产数据库采用 HADR 提供高可用。

版本管理使用 Firefly，环境包括 DEV / IT / FT / LT / PREDEV / POT 等多套。这反映传统大型银行环境多、测试阶段严格、发布链长、变更流程重。可以与互联网 Git + CI/CD 做对比，但不要贬低其中任一模式。

### 功能架构清单

- 内部管理：商户签约、费率维护、结售汇查询、收付汇查询、预购汇查询、手续费查询、申报差错处理、参数维护、预警查询、待解付确认。
- 外汇侧：日牌价推送、实时牌价、文件登记、集中结售汇、预购汇申请、预购汇交割、付汇、来账推送、解付。
- 人民币侧：文件登记、付款、来账推送、收款、账号同步、交易同步、查询。

### 报文与通信

FO/BP 间常用 XML 报文（XmlEBStream，结构为 stream/field/list/row）；XmlExchange 用于中间交换平台通信；XmlCreditCard 用于 FO 与信用卡前置通信。材料记录很多报文使用 GBK，这是传统银行系统常见的历史技术特征。

### BP 启动过程（历史细节）

Bootstrap.start() → 加载 lifecycle-plugins-ext.xml → 启动 CommonBPServer → 加载系统配置 → 初始化日志 → 扫描组件 → 初始化事务信息 → 初始化数据源 → 加载 ServerConfig.xml / SYSDATA → 注册基础服务 → 注册数据库连接池 → 注册通信服务 → 注册错误信息管理器 → 注册分包管理 → 注册监控 → 启动后台任务调度线程 → 启动 ServerSocket → 等待业务请求。

这与现代 Spring Boot 的思想可以类比理解，但不要说当时就是 Spring Boot。
