来自真实面试的教训：B+Tree 和倒排索引是两种索引，不要混用"倒排表"去解释 B+Tree（见 [DBA1013 索引定义的校正](./DBA1013.md)）。

# 1. 先复习：B+Tree 本质上在帮我们做什么？【P0】

例如：

```sql
SELECT * FROM user WHERE user_id = 123;
```

或者：

```sql
SELECT * FROM orders WHERE created_time BETWEEN ? AND ?;
```

B+Tree 很擅长：

```text
Key
↓
快速定位记录/范围
```

它依赖：

> **Key 的有序结构。**

所以：

```text
id = 123
age > 30
created_time between ...
```

非常自然——都是**结构化字段上按值/范围找记录**。

------------------------------------------------------------------------

# 2. 全文搜索为什么是另一类问题？【P1】

假设有三篇文档：

```text
Doc1: Java distributed system
Doc2: Python data analysis
Doc3: Java Spring interview
```

用户搜索：

```text
Java
```

真正的问题不是：

> 哪篇文档的完整内容等于 `"Java"`？

而是：

> **哪些文档里面出现过 Java？**

如果每次搜索都：

```text
扫描Doc1全文
扫描Doc2全文
扫描Doc3全文
...
扫描1000万篇全文
```

成本非常高。

因此反过来建立：

```text
Java   → Doc1, Doc3
Python → Doc2
Spring → Doc3
```

这就是倒排索引最核心的直觉。

------------------------------------------------------------------------

# 3. 为什么叫"倒排"？【P1】

普通直觉（正排）：

```text
Document
↓
它包含哪些词
```

例如：

```text
Doc1 → Java, distributed, system
Doc2 → Python, data, analysis
```

倒排：

```text
Term
↓
哪些 Document 包含它
```

变成：

```text
Java        → Doc1, Doc3
distributed → Doc1
Python      → Doc2
```

所以叫：

> **Inverted Index。**

------------------------------------------------------------------------

# 4. 两个核心结构：Dictionary + Posting List【P1】

面试生存级先记：

```text
Term Dictionary
↓
找到某个 Term

Posting List
↓
这个 Term 出现在哪些 Document
```

例如：

```text
Dictionary:
Java
Python
Spring

Java → Posting List → [Doc1, Doc3, Doc9, Doc21...]
```

Posting List 还可能记录更多信息，例如：

- 词频；

- 位置；

- 其他用于评分/检索的信息。

但不用钻 Lucene 内部编码（止损线见本章末尾）。

------------------------------------------------------------------------

# 5. 搜索 `"Java Spring"` 怎么办？【P1】

已有：

```text
Java   → [1,3,8,10]
Spring → [3,7,10]
```

如果要求同时包含：

```text
Java AND Spring
```

可以对 Posting List 求交：

```text
[1,3,8,10]
∩
[3,7,10]
=
[3,10]
```

这就是倒排索引为什么适合文本检索的重要直觉：**多关键词组合查询被转化为 Posting List 之间的交并运算**，而不是重新扫描全文。

------------------------------------------------------------------------

# 6. B+Tree vs Inverted Index【P0】

|              | B+Tree                       | Inverted Index                  |
| ------------ | ---------------------------- | ------------------------------- |
| 核心映射     | Key → Record/Range           | Term → Documents                |
| 擅长         | 精确/范围查询                | 全文关键词检索                  |
| 典型问题     | `id=123`、时间范围           | "包含 Java 的文档"              |
| 顺序结构     | Key 有序                     | Term Dictionary + Posting List  |
| 常见场景     | MySQL/InnoDB                 | 搜索引擎/Lucene/Elasticsearch 等 |

### 一句话

> B+Tree 更像"给结构化字段建立有序目录"，倒排索引更像"先给所有词建立目录，再记录每个词出现在哪些文档"。

### 30 秒面试答案【P0】

> B+Tree 和倒排索引解决的问题不同。B+Tree 主要按照结构化 Key 建立有序索引，适合等值和范围查询，比如按 ID 或时间查数据；倒排索引面向全文检索，核心是从 term 反向映射到包含它的 document list，例如 `Java → Doc1、Doc3`。所以搜索"哪些文档包含 Java"时，可以直接找到 Java 的 posting list，而不是扫描所有文档内容。Elasticsearch/Lucene 这类搜索系统会大量使用这种结构。

# 7. 为什么 `LIKE '%java%'` 不等于真正的全文检索？【P1】

例如：

```sql
WHERE content LIKE '%java%'
```

问题：

> 前导 `%` 通常难以利用普通 B+Tree 的左侧有序定位能力。

而且真正全文检索还可能需要：

```text
分词
相关性评分
多Term组合
词频
位置
语言分析
```

所以大规模搜索场景通常需要：

> 专门的全文索引/搜索体系。

注意：

> 不是说 MySQL 完全没有 Full-Text Index（InnoDB 从 5.6.4 起支持，配合 MATCH AGAINST 使用，见 [DBA1013 索引分类](./DBA1013.md)）；这里讨论的是普通 B+Tree 与倒排式全文检索思路的区别。中文分词、相关性评分、分布式检索这些工程能力，MySQL 内置全文索引和专业搜索系统之间差距很大。

# 8. Elasticsearch 和 Lucene 是什么关系？【P2｜只防守】

只需要知道：

> Elasticsearch 是一个分布式搜索与分析系统，其底层搜索能力大量建立在 Lucene 之上；Lucene 是 Java 搜索库，倒排索引是其全文检索的重要基础结构。

你的目标不是 ES 集群专家，所以不主动展开：

```text
Shard 分配算法
Segment Merge 源码
Lucene FST 源码
BM25 数学推导
```

# 9. 倒排索引为什么也有成本？【P1】

没有免费索引。

建立倒排索引意味着：

```text
写入 Document
↓
分析/分词
↓
更新 Term Dictionary
↓
更新 Posting List
```

因此：

- 占额外存储；

- 写入/更新有维护成本；

- 搜索系统还要处理索引刷新/合并等工程问题。

与数据库索引同样的思想：

> **索引是在用空间和写入成本换查询效率。**（B+Tree 与 Inverted Index 的共同点）

------------------------------------------------------------------------

# 10. hash、B+Tree、倒排索引怎么选？【P1】

面试官追问"三种索引怎么选"时，先按查询模式回答：

```text
Hash 思想
→ 更偏精确 Key 定位
→ 不天然擅长范围

B+Tree
→ 有序
→ 等值 + 范围 + 排序相关访问

Inverted Index
→ Term → Documents
→ 全文搜索
```

关键不是：

> 谁更高级。

而是：

> **访问模式决定数据结构。**

------------------------------------------------------------------------

# 11. 索引知识最终地图

```text
我要按结构化字段找数据
        ↓
B+Tree
├─ 等值
├─ 范围
├─ 排序/有序访问
└─ 联合索引

我要按文本中的词找文档
        ↓
Inverted Index
├─ Term Dictionary
├─ Posting List
├─ 多Term交并
└─ Full-text Search

共同点
↓
额外空间 + 写入维护成本
换
查询效率
```
