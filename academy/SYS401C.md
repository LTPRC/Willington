> **本章定位：**Realtime & Human-in-the-loop。SSE 只是 HTTP 上的一条单向事件流，不是消息队列；Agent 工作台的关键也不是"边生成边显示"，而是把**任务生命周期、事件流、审批与恢复**拆成四个独立边界。本章是通用设计题，适用于 RSP 运维、AI 助手和异步任务平台，**不代表 Solphin 已落地这套 SSE 实现**；Solphin 的真实 Agent 工程见 [SYS4012](./SYS4012.md)，跨天、多人、多阶段的合规流程见 [SYS4014](./SYS4014.md)。

## 1. SSE 到底是什么

**SSE（Server-Sent Events，服务器发送事件）**不是独立于 HTTP 的消息中间件，而是一种**持续返回事件的 HTTP 响应**。浏览器通常用 `EventSource` 发起 GET，服务端返回：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
```

之后服务端保持连接，按 SSE 格式持续写 UTF-8 文本：

```text
id: 101
event: text_delta
data: {"delta":"找到了"}

id: 102
event: tool_start
data: {"tool":"registry_query"}

: heartbeat

retry: 3000
id: 103
event: completed
data: {"taskId":"123"}

```

字段含义：

| 字段 | 作用 |
| --- | --- |
| `data` | 事件内容，可以多行；浏览器交给 JS 时是字符串，JSON 要自行 `JSON.parse()` |
| `event` | 事件名；省略时是默认的 `message` |
| `id` | 事件标识字符串，供重连时回传；标准不要求连续或为数字 |
| `retry` | 建议浏览器重连的等待毫秒数 |
| `:` 开头 | 注释，常用来做心跳保活 |
| 空行 | 结束并派发一个事件 |

`text_delta`、`tool_start`、`completed` 都是**业务自定义事件名**，不是 SSE 标准的一部分。SSE 只负责"服务端把文本事件推给浏览器"，不负责模型推理、任务调度或消息持久化。

## 2. 连接、重连与代理

### EventSource 的边界

- 原生 `EventSource` 通常只能发 **GET**，自定义请求头能力有限；需要鉴权时优先用 Cookie/Session，或使用短时票据。
- 断线后浏览器会自动重连，并在请求头带 `Last-Event-ID`；服务端可以用它做增量回放。
- 服务端可以用 `retry:` 建议重连间隔；浏览器不保证严格按这个值执行。
- 如果要 **POST 创建请求并直接读流**，可以用 `fetch()` 读 `ReadableStream`，但事件解析、重连、去重都要自己实现。

### 代理与超时

- 心跳：定期发送 `: ping` 注释，避免 Nginx/网关按空闲超时掐断连接。
- Nginx 缓冲：SSE 需要关闭响应缓冲（如 `X-Accel-Buffering: no`），否则事件会被攒着一起发。
- 压缩：不要对 `text/event-stream` 做 gzip 缓冲，否则增量可能被压住。
- 连接数：HTTP/1.1 下浏览器对同源连接数有限制；大量标签页/任务要复用连接或使用 HTTP/2。
- 服务端超时：Spring MVC 的 `SseEmitter(0L)` 表示不超时，但代理、负载均衡和内核仍可能断开；要有心跳和客户端重连。

Spring MVC 的最小形态：

```java
@GetMapping(value = "/tasks/{id}/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter events(@PathVariable String id,
                         @RequestHeader(value = "Last-Event-ID", required = false) String lastEventId) {
    SseEmitter emitter = new SseEmitter(0L);
    taskEventService.subscribe(id, lastEventId, emitter);
    return emitter;
}
```

WebFlux 对应的是 `Flux<ServerSentEvent<?>>`。两种实现都只是传输层，任务状态仍要落库。

## 3. SSE 不提供可靠投递

这是最容易在面试里说错的地方：**SSE 不是消息队列，`id` 不是 ACK，`Last-Event-ID` 也不是 Offset。**

- SSE 不存事件、不做 Broker、没有消费者组、没有服务端 ACK/Offset、没有重放保证。
- `Last-Event-ID` 只是浏览器"我最后看到这个 id"的提示；如果服务端没有持久化后续事件，它补不出来。
- 标准没有规定 `id` 必须连续、递增或全局唯一。要支持可靠回放，应用应自己定义**每任务单调递增的 `seq`**。
- 断线重连后，正确顺序是：**先读任务权威快照，再从事件日志按游标补增量**；不要重新跑一遍 Agent，尤其不要重放有副作用的工具。

### 缺号 103 怎么排查

假设前端收到 101、102、104，没有 103：

1. 先确认服务端是否保证**同一任务内事件 ID 连续**。如果 ID 是全局发号或跨任务混用，缺 103 可能只是别的任务的事件。
2. 如果确实按任务连续，检查服务端编号、事件过滤、并发 Worker、跨实例重放和前端处理，不要先怀疑 TCP "丢了一个完整事件"。
3. 暂存 104，让应用持有的 `lastContiguousId=102` 去补 103；补不到就 `GET /tasks/{id}` 取权威快照替换页面。
4. 前端按 `(taskId, eventId)` 去重，因为文本增量在重放时可能重复。

### 和 MQ / BigPipe 的区别

| | SSE | WebSocket | 长轮询 | Kafka / BigPipe |
| --- | --- | --- | --- | --- |
| 方向 | 服务端 → 客户端 | 双向 | 反复请求 | Broker 发布订阅 |
| 传输 | HTTP 响应 | TCP 升级 | HTTP | 自定义协议 |
| 存储/重放 | 无，应用自己补 | 无 | 无 | Broker 存储 + Offset/ACK |
| 重连 | EventSource 自动 + Last-Event-ID | 应用自己 | 应用自己 | 消费组 Rebalance |
| 典型用途 | Token 流、进度、通知 | 聊天、协同 | 兼容旧环境 | 解耦、可靠消息 |

SSE 和 MQ 不是替代关系：**MQ 负责内部可靠传递，SSE 负责把结果实时展示给浏览器**。需要可靠回放时，把事件先写进 MQ/事件表，再通过 SSE 推送。

## 4. 把 Agent 工作台拆成三个生命周期

很多设计把"创建任务、执行任务、展示结果"揉在一个请求里，浏览器一断就全部失控。正确做法是拆成三个独立生命周期：

```text
前端                     Spring Boot API              后台 Agent Worker             DB / 事件存储
 | POST /tasks                 |                              |                          |
 |---------------------------->| 校验用户、落库 PENDING       |                          |
 |<--- {taskId} ---------------| 投递/启动任务 -------------->|                          |
 | GET /tasks/{id}/events      |                              |                          |
 |==== SSE 持续连接 ==========>|<--- text_delta/tool_start ---|-- 关键状态/事件 -------->|
 |<--- approval_required ------|<--- WAITING_APPROVAL --------|-- 待审批提案 ----------->|
 | POST /tasks/{id}/approve    |                              |                          |
 |---------------------------->| 鉴权 + 参数摘要 + 状态校验 -->|-- 幂等执行工具 -------->|
 |<--- completed --------------|<--- COMPLETED ---------------|-- 最终结果 ------------->|
 |                             |                              |                          |
```

三个生命周期：

1. **HTTP 命令**：创建、批准、取消。短请求，返回 `taskId`；用客户端请求 ID 做幂等。
2. **SSE 观察**：只读事件流。浏览器断开不会杀任务；重连后按 `taskId` 查状态并续订。
3. **Worker 执行**：长任务，有自己的租约、检查点和恢复逻辑，可以比浏览器活得久。

这三个生命周期是**执行视角**；审批与恢复是横切它们的两个治理边界，合起来就是开头所说的四个边界。

任务状态机：

```text
PENDING ──启动──> RUNNING ──需要审批──> WAITING_APPROVAL
                     │                        │
                     │<──────批准─────────────┘
                     │
                     ├──成功──> COMPLETED
                     ├──失败──> FAILED
                     └──取消──> CANCELLED
```

状态迁移用数据库 CAS（`UPDATE ... WHERE status = ?`）保护；事件表追加写，SSE 只是事件表的一个视图。**状态是事实，事件是历史，SSE 是传输**，三者不要混。

## 5. 审批、权限与幂等

### 审批要绑定什么

一个审批不能只是"同意"两个字，至少要绑定：

- 用户身份与租户/注册商；
- `taskId` 与具体步骤；
- 工具名、资源 ID、**规范化后的参数哈希**；
- 风险等级、过期时间、一次性 nonce。

审批时服务端要重新鉴权、重新读任务状态，并确认参数没有被替换。批准动作本身也要幂等：重复提交返回同一个结果，不能执行两次。

### Agent 调 API 的三层权限

| 层 | 检查什么 | 例子 |
| --- | --- | --- |
| 用户身份/角色 | 当前用户本来有没有权限操作这个资源 | 注册商 A 不能改注册商 B 的域名 |
| Agent/工具白名单 | 这个 Agent 角色允许调用哪些工具 | Analyzer 只读；Reviewer 不能写；Executor 只能调用有限写工具 |
| 资源与参数 | 这次调用的对象、参数、金额、范围是否在授权内 | 只能改指定域名；DS 变更必须带审批票据 |

三层都通过才执行。把这三层落成一条 **Tool Gateway** 链路，就是四道门：

```text
Tool 白名单 → 用户对目标资源的权限 → 参数 Schema/范围 + 高风险审批 → 最小权限执行 + 审计
```

任何一道门失败都拒绝执行；审批票据只对一次具体调用有效，不能复用。**能由确定性权限系统拦住的事情，不要只写在 Prompt 里。**危险工具要有沙箱、Dry-run、参数白名单和审计；审计记录要能回答"谁批准了哪个 Agent 对哪个资源做了什么"。

### 无限循环与资源预算

ReAct 类 Agent 会循环"模型决策 → 调工具 → 看结果 → 再决策"。必须限制：

- 单任务最大轮数；
- 每类工具最大调用次数；
- 总 Deadline；
- Token/费用预算；
- 相同参数重复调用检测；
- 不可恢复错误直接终止或转人工。

这些限制要由 Worker 执行，而不是靠 Prompt 提醒模型。

## 6. 恢复与一致性

- **Worker 崩溃**：用租约/心跳判断存活；租约过期后由另一个 Worker 接管，旧 Worker 用 Fencing Token 防止继续写。
- **检查点**：保存任务状态、已完成步骤、工具输出、待审批提案和事件游标；恢复时从检查点继续，不从头重跑。
- **副作用工具**：重试前先查权威状态（是否已执行、是否已成功），并用幂等键保证重复调用不产生二次副作用。
- **事件日志**：`(taskId, seq, type, payload)` 追加写；SSE 从游标回放；前端按 `(taskId, seq)` 去重。
- **事件丢失**：用任务快照重建页面，不要伪造缺失的增量。
- **双 Worker**：任务状态 CAS + 单活租约/Fencing，避免同一任务被两个 Worker 同时执行。

一句话：**至少一次执行 + 幂等副作用 = 业务上的有效一次**。SSE 的重放只是展示层，不是业务幂等。

## 7. 安全与工程细节

- **XSS**：模型输出是不可信内容；按纯文本渲染，或用严格的白名单 Markdown 渲染，绝不能直接 `innerHTML`。
- **鉴权**：SSE 端点同样要鉴权，并校验当前用户对 `taskId` 的归属；不要用可猜测的 ID 暴露任务。
- **CSRF**：批准/取消是写操作，要防 CSRF（SameSite Cookie + Token）。
- **背压**：每个连接有有界队列；文本增量可合并/丢弃，队列满时发快照并关闭慢消费者，不能无限堆积。
- **资源上限**：限制每用户/每任务连接数、事件大小、空闲时间；心跳保活。
- **可观测性**：记录 `taskId`、`eventId`、`traceId`；监控首字延迟（TTFT）、事件滞后、工具耗时、审批耗时、失败率、每任务 Token/费用。
- **评估**：用固定评估集衡量任务完成率、工具选择正确率、事实/引用正确率、人工修改量、P95/P99 延迟和成本；不要只看"回答是否通顺"。

## 8. RSP 场景：可信事实与高风险写操作

Agent 用在注册局运维时，最重要的不是"会不会聊天"，而是**事实从哪里来、写操作谁敢批**。

**只读诊断优先。** 当前状态必须从权威系统查：SRS 注册库、政策配置、监控指标、审计流水、区文件 serial/版本、RDAP 查询视图。RAG 适合查规范、操作手册和历史故障，不替代实时状态查询。Agent 的输出应该是：证据链接、置信范围、建议动作、验证点；确定性校验交给规则引擎或 API。

**必须审批的高风险操作**至少包括：

- 批量 `serverHold` / `serverUnhold`；
- DS/KSK 变更、DNSSEC 回滚；
- 区文件回滚/切换；
- Data Escrow 重报、格式或范围变更；
- 隐私/公开可见性策略调整；
- 注册商配额、权限或白名单变更；
- 任何影响域名所有权、解析可达性或合规数据的写操作。

**如果规范本身写错了**，不要指望再加一个 Agent 就能纠正。规范要有版本、Owner、变更审核、可执行测试、Golden Cases 和生产前 Dry-run；执行前从权威系统读当前状态，比较预期与实际，超出边界就阻断。目标不是宣称"零幻觉"，而是让错误**可检测、可阻断、可恢复**。

## 9. 一页纸总结

```text
HTTP 命令：创建/批准/取消（短请求、幂等）
    │
    ├─ 任务状态（DB，CAS）──> Worker（租约/检查点/幂等）
    │                              │
    │                              ├─ 工具调用（三层权限）
    │                              └─ 高风险操作（审批票据）
    │
    └─ 事件日志（append-only）──> SSE（断线重连/游标回放）──> 前端
```

四个边界记住就不会乱：**任务生命周期、事件流、审批、恢复**。SSE 只是最后那一段传输；把它当 MQ 用，就会在断线、缺号、重复和副作用上连续踩坑。
