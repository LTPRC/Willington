> **本章定位：**Protocol。EPP 是注册商操作注册局资源的唯一标准写接口。要讲清它跑在什么之上、报文长什么样、七个命令各自的语义边界、以及它作为一个"有状态串行协议"给后端架构带来的约束。

## 协议定位

EPP（Extensible Provisioning Protocol）是注册局对外提供的**命令-响应式**协议，用于对域名、主机、联系人三类对象做增删改查。几个必须先建立的认知：

- 它是**写接口为主**的协议。公众查询注册数据不走 EPP，走 RDAP/WHOIS（见 [SYS2024](./SYS2024.md)）。
- 它的调用方**只有已签约的注册商**，不是开放 API。鉴权发生在连接建立阶段，之后整个会话都以该注册商身份运行。
- 它是**有状态**的：一次 login 建立会话，会话与 TCP 连接绑定，命令必须串行。
- 它用 **XML** 编码，通过 `<extension>` 机制扩展。DNSSEC 的 DS 数据、新顶级域抢注阶段、计费信息等都是扩展，不在基础协议里。

对应规范：基础协议 RFC 5730，host / contact / domain 三个对象映射分别是 RFC 5731 / 5732 / 5733，TCP 传输映射是 RFC 5734。

## 传输层与封帧

标准传输是 **TCP over TLS**，注册端口 **700**。服务端提供证书，实际部署中普遍要求双向 TLS（客户端证书）并叠加 IP 白名单。

TCP 是字节流没有边界，EPP 用**4 字节长度前缀**封帧：

```text
| 4 字节长度（大端，含这 4 字节自身） | UTF-8 编码的 EPP XML 报文 |
```

这正好对应 Netty 的 LengthFieldBasedFrameDecoder，四个参数依次是：

```java
new LengthFieldBasedFrameDecoder(
        maxFrameLength,  // 上限防护，超限抛 TooLongFrameException
        0,               // lengthFieldOffset
        4,               // lengthFieldLength
        0,               // lengthAdjustment：长度值已包含自身
        4);              // initialBytesToStrip：解出的帧不含长度字段
```

拆包器选型与最大帧长防护的完整讨论见 [CSE3513 - Netty](./CSE3513.md)。这里要补一条 EPP 特有的：**长度前缀是攻击面**。对端可以声称一个巨大的长度值让你预分配缓冲区，所以 maxFrameLength 必须设死，不能按 `Integer.MAX_VALUE` 放过去。

## 会话模型

```text
建立 TCP → TLS 握手 → 服务端主动下发 <greeting> → 客户端 <login> → 命令交互 → <logout> 或超时断开
```

服务端在连接建立后**立即**推送 greeting，告诉客户端自己是谁、服务器时间、支持哪些对象命名空间与扩展：

```xml
<epp xmlns="urn:ietf:params:xml:ns:epp-1.0">
  <greeting>
    <svID>epp.registry.example</svID>
    <svDate>2026-10-17T09:00:00.0Z</svDate>
    <svcMenu>
      <version>1.0</version>
      <lang>en</lang>
      <objURI>urn:ietf:params:xml:ns:domain-1.0</objURI>
      <objURI>urn:ietf:params:xml:ns:host-1.0</objURI>
      <objURI>urn:ietf:params:xml:ns:contact-1.0</objURI>
      <svcExtension>
        <extURI>urn:ietf:params:xml:ns:secDNS-1.1</extURI>
      </svcExtension>
    </svcMenu>
  </greeting>
</epp>
```

客户端用 login 提交凭据并声明自己要用哪些服务——**声明的 objURI 必须是服务端 greeting 里列出的子集**，否则直接拒绝：

```xml
<command>
  <login>
    <clID>registrar-x</clID>
    <pw>******</pw>
    <options><version>1.0</version><lang>en</lang></options>
    <svcs>
      <objURI>urn:ietf:params:xml:ns:domain-1.0</objURI>
      <objURI>urn:ietf:params:xml:ns:host-1.0</objURI>
      <objURI>urn:ietf:params:xml:ns:contact-1.0</objURI>
    </svcs>
  </login>
  <clTRID>ABC-00001</clTRID>
</command>
```

三个会话细节：

- `<hello>` 用于索取一个新的 greeting，实际充当**应用层心跳**与服务器时间同步。长时间空闲的连接会被服务端主动断开。
- `<logout>` 正常结束会话，返回 1500。
- 会话状态挂在连接上，所以**不能随便做无状态负载均衡**。TLS 必须在 EPP 节点本地终结，或者路由层要能保持连接亲和。这是注册局后端和普通无状态 HTTP 服务最大的架构差异之一。

## 第三道门：业务授权

传输层的 TLS 和 login 解决的都是"你是谁"，还没解决"你能动什么"。**登录身份 ≠ 操作授权**：注册商 A 即使 login 成功，也不能修改注册商 B 管理的域名。

服务端执行每个 domain 命令前，要在业务层核对三件事：

1. **归属**：对象的 clID 必须等于当前会话的注册商。clID 既是会话身份（见"会话模型"），也是对象上的归属字段，对不上直接 2201（无权操作该对象）。
2. **状态**：对象上的 `server*` 状态由注册局侧政策设置（如 `serverTransferProhibited`、`serverHold`），`client*` 状态由归属注册商自己设置，两者都可能禁止某类操作，违规返回 2303，见 [SYS2023](./SYS2023.md)。
3. **授权凭据**：转移等敏感操作还要额外校验 authInfo，见下文 transfer 一节。

这就是三道门的含义：**传输加密、会话身份、业务授权各管一层，任何一层失守，下一层仍能阻断。**权限判断属于业务层代码，不在 TLS 握手或 XML 解码里完成。

## 报文骨架

所有命令都是同一个外壳：一个命令元素 + 可选 `<extension>` + 可选 `<clTRID>`。所有响应也是同一个外壳：`<result>` + 可选 `<resData>` + 可选 `<extension>` + `<trID>`。

```xml
<epp xmlns="urn:ietf:params:xml:ns:epp-1.0">
  <command>
    <check>
      <domain:check xmlns:domain="urn:ietf:params:xml:ns:domain-1.0">
        <domain:name>example.com</domain:name>
        <domain:name>example2.com</domain:name>
      </domain:check>
    </check>
    <clTRID>ABC-12345</clTRID>
  </command>
</epp>
```

```xml
<epp xmlns="urn:ietf:params:xml:ns:epp-1.0">
  <response>
    <result code="1000"><msg>Command completed successfully</msg></result>
    <resData>
      <domain:chkData xmlns:domain="urn:ietf:params:xml:ns:domain-1.0">
        <domain:cd>
          <domain:name avail="0">example.com</domain:name>
          <domain:reason>In use</domain:reason>
        </domain:cd>
        <domain:cd>
          <domain:name avail="1">example2.com</domain:name>
        </domain:cd>
      </domain:chkData>
    </resData>
    <trID>
      <clTRID>ABC-12345</clTRID>
      <svTRID>SRV-98765</svTRID>
    </trID>
  </response>
</epp>
```

`<trID>` 里的两个 ID 要分清：

- **clTRID** 是客户端生成的，服务端**原样回显**。它用于客户端把响应对回到自己发出的那条命令。
- **svTRID** 是服务端生成的，是注册局侧的日志与排障主键。

**关键陷阱：clTRID 不是幂等键。**协议不要求服务端按 clTRID 去重，重发同一个 clTRID 的 create 仍然会得到 2302（对象已存在）而不是"返回上次结果"。想做幂等必须由注册商侧自己维护状态机，见下文。

## 七个命令的语义

| 命令 | 作用 | 要点 |
| --- | --- | --- |
| `check` | 批量查询对象是否可用 | 可一次带多个 name；返回 `avail="0/1"`；可用性是**瞬时**的，check 通过不代表 create 一定成功 |
| `info` | 读取对象详情 | 返回状态列表、关联对象、到期日；转移类操作需要携带 authInfo 才能看到完整数据 |
| `create` | 创建对象 | 域名要求全局唯一；对象已存在返回 2302 |
| `update` | 修改对象 | 结构是 `add` / `rem` / `chg` 三段，不是一次性全量覆盖；受状态码约束 |
| `renew` | 延长有效期 | 必须带上**当前到期日** `curExpDate`，服务端校验不一致则拒绝——这是一个乐观锁 |
| `transfer` | 转移注册商 | 带 `op` 子操作，是一个多方异步流程 |
| `delete` | 删除对象 | 域名 delete 通常不立即释放，而是进入 pendingDelete 流程（见 [SYS2023](./SYS2023.md)） |

外加两个非对象命令：`poll`（取异步通知）和 `login`/`hello`/`logout`（会话）。

### update 的三段结构

这是最容易写错的地方。update 不是 PUT 语义，不是"提交完整新对象"：

```xml
<domain:update xmlns:domain="urn:ietf:params:xml:ns:domain-1.0">
  <domain:name>example.com</domain:name>
  <domain:add>
    <domain:ns><domain:hostObj>ns2.example.net</domain:hostObj></domain:ns>
    <domain:status s="clientTransferProhibited"/>
  </domain:add>
  <domain:rem>
    <domain:ns><domain:hostObj>ns1.example.net</domain:hostObj></domain:ns>
  </domain:rem>
  <domain:chg>
    <domain:registrant>new-contact-id</domain:registrant>
  </domain:chg>
</domain:update>
```

- `add` / `rem` 作用于**集合类**字段（NS 列表、联系人关联、状态）；
- `chg` 作用于**单值类**字段（注册人联系人、authInfo）。

因为是多段增量语义，所以并发 update 之间不存在整体覆盖关系，但也意味着**不能用 update 实现"把状态设成某个值"**——状态能不能设、设了有没有效，由政策决定，见 [SYS2023](./SYS2023.md)。

### renew 为什么要求 curExpDate

`renew` 必须传当前到期日，服务端不匹配就拒绝。这是一次典型的 CAS：防止注册商基于过期快照续费，避免"两个操作员各续一年结果只续了一年"或"续在了别人已经续过的日期上"。同样的思路在 [DBA2013 - 分布式锁](./DBA2013.md) 的 owner 标识和 [SYS3015 - Distributed Lock](./SYS3015.md) 的 Fencing Token 里都出现过。

### transfer 是一个异步多方流程

```text
转入方注册商 ──transfer op=request（带 authInfo）──→ 注册局
                                                    ↓
                              域名置为 pendingTransfer，开始计时
                                                    ↓
转出方注册商 ──op=approve / op=reject──→ 注册局
                              （不响应则到期自动通过）
                                                    ↓
              注册局改 registrant 所属，并通过 poll 通知双方
```

子操作一共五个：`request`（发起）、`approve`（同意）、`reject`（拒绝）、`cancel`（发起方撤回）、`query`（查进度）。

三个必须理解的点：

1. **authInfo 是转移的授权凭据**，俗称转移码 / EPP Auth Code。它由注册人从转出方取得，转入方在 request 里提交。authInfo 泄露等于域名可被劫持，所以它在库里必须加密存储，在日志与查询响应里必须脱敏。
2. **窗口期内域名处于 pendingTransfer 状态**，这个状态本身会禁止其它变更操作（对应结果码 2300 Object pending transfer）。
3. **结果通过 poll 异步送达**，不是同步返回。转入方发出 request 得到的是 1001（action pending），不是最终结果。

## 对象模型：domain / host / contact

三类对象之间有引用关系，删除受约束：

```text
contact（联系人，有 id 与 authInfo）
   ↑ 被引用为 registrant / admin / tech / billing
domain（域名，有 name、period、ns、status、authInfo、到期日）
   ↓ 引用
host（主机，即 NS 的名字，有 name，可能带 addr）
```

### in-bailiwick 与 glue record

host 分两种，这是注册局数据模型里最容易被忽略的细节：

| 类型 | 含义 | 注册局要不要存 IP |
| --- | --- | --- |
| out-of-bailiwick | NS 名字不在本 TLD 下，如 `ns1.other.net` 之于 `.com` | 不存。解析时由对方区自己负责 |
| in-bailiwick | NS 名字在本 TLD 下，如 `ns1.example.com` 之于 `.com` | **必须存**，否则产生循环依赖 |

循环依赖是这样形成的：要解析 `example.com` 得先问 `ns1.example.com`，而要解析 `ns1.example.com` 又得先知道 `example.com` 的 NS——鸡生蛋。解法是父区（TLD 区）在委派的同时**粘一条 A/AAAA 记录**，这就是 glue record。

工程后果：in-bailiwick host 的 IP 变更必须通过 EPP 提交到注册局并等区文件发布，不能只在自己权威 DNS 上改；而且**被 domain 引用的 host 不能直接 delete**，会返回 2304（Object association prohibits operation）。

### contact 的 disclose 机制

contact 对象上有一组 `disclose` 标志，声明哪些字段允许公开（姓名、邮箱、电话、地址）。它和注册局的公开政策、隐私代理服务共同决定了 RDAP/WHOIS 里最终能看到什么，见 [SYS2024](./SYS2024.md)。

## poll：异步通知队列

EPP 没有服务端主动推送。所有异步事件——转移完成、注册局主动改了你的域名状态、即将到期提醒——都进一个**每个注册商独立的 poll 队列**：

```xml
<poll op="req"/>                     <!-- 取队首消息，返回 1301 -->
<poll op="ack" msgID="12345"/>       <!-- 确认出队 -->
```

取消息只是"读到"，**必须显式 ack 才会出队**，否则同一条消息会一直被读到。这是一个 at-least-once 语义的队列，消费端要做幂等处理。注册商如果长期不消费 poll 队列，就会漏掉转移完成通知，这是真实运维事故的常见来源。

## 结果码分类

响应码分三段，语义边界很清晰：

| 段 | 含义 | 代表码 |
| --- | --- | --- |
| 1000–1001 | 成功；1001 表示**动作仍在进行中** | 1000 成功、1001 成功但待完成 |
| 1300–1500 | poll 与会话类成功 | 1301 取到消息待 ack、1500 会话结束 |
| 2000+ | 失败 | 见下表 |

常见失败码，按"该谁修"来分组更有用：

| 码 | 含义 | 归属 |
| --- | --- | --- |
| 2001 / 2002 / 2003 / 2004 / 2005 | 报文语法错、命令用法错、缺必填参数、取值越界、参数语法错 | 客户端代码 bug |
| 2100 / 2102 / 2104 | 对象服务、命令、扩展未实现 | 客户端声明了服务端不支持的能力 |
| 2200 / 2201 / 2202 | 认证失败、无权操作该对象、authInfo 无效 | 凭据或授权问题 |
| 2301 / 2302 | 对象不存在 / 对象已存在 | 业务状态问题 |
| 2300 | 对象正在转移中 | 业务状态问题 |
| 2303 | **对象状态禁止该操作** | 政策约束，见 [SYS2023](./SYS2023.md) |
| 2304 | 对象关联禁止该操作 | 引用完整性约束 |
| 2305 / 2306 | 参数违反政策 / 数据管理政策冲突 | 注册局政策 |
| 2400 / 2500 / 2501 | 失败并关闭连接 | 连接级故障 |

区分 2303 与 2304 很重要：**2303 是"状态不允许"，2304 是"还有别的对象引用着它"**。前者改状态或等窗口期，后者要先解除引用。

## 幂等与"结果未知"

EPP 没有幂等键，重试必须自己设计：

| 场景 | 能不能直接重试 | 原因 |
| --- | --- | --- |
| 收到 2xxx 明确失败 | 视码而定 | 语法错重试无意义；2302 说明已存在，应转 info 确认 |
| 连接在响应到达前断开 | **不能盲目重试** | 请求可能已经提交成功，结果未知 |
| 收到 1001 | 不能当成完成 | 动作仍在进行，需 poll 或 info 追结果 |

正确的处理姿势是：**任何"结果未知"都用 `info` 查询去收敛，而不是重发写命令。**这和 [SYS3011 - Distributed Systems Fundamentals](./SYS3011.md) 里"超时不等于失败"、以及 [FIN2014 - 交易异常与售后](./FIN2014.md) 里支付超时不能直接判失败是同一个原理：跨网络的写操作，在拿到明确结果之前，只能查不能猜。

对注册局后端来说，还需要在应用层补一层：给每条写命令记录 clTRID + svTRID + 请求摘要 + 最终结果，形成可回放的审计流水。这样即使注册商侧重试，也能识别出"这是同一个意图的第二次尝试"。

## 并发模型与容量

EPP 的并发模型是**每连接串行**：一条连接上同时只能有一个命令在飞。所以吞吐量取决于：

```text
总吞吐 ≈ 在线会话数 × 单会话命令速率
```

由此推出注册局后端的几个硬约束：

- **连接数是核心资源**。每个注册商通常有并发连接数上限，服务端要按 clID 做配额与限流，而不是全局一个池子。
- **会话有状态，不能随意摘除节点**。滚动发布一个 EPP 节点会掐断该节点上所有注册商会话，触发大面积重连。重连风暴下如果没做退避，会把服务二次打垮——这一点与 [CSE3513](./CSE3513.md) 里长连接服务的断线恢复纪律完全一致。
- **check 与 create 的争抢在删域名释放时刻最激烈**。热门域名到期释放的瞬间，多家注册商同时 check + create，落到数据库上是对同一个唯一索引的并发写。这是注册局后端最典型的热点场景，需要专门的排队或限速策略。

## 扩展机制

`<extension>` 出现在 command 和 response 两侧，用于携带基础协议之外的数据。常见的几类：

| 扩展 | 用途 |
| --- | --- |
| secDNS（RFC 5910） | 在 domain 对象上增删 DS 记录，是 DNSSEC 委派的入口 |
| launch phase | New gTLD 开放初期的 sunrise / landrush 阶段申请 |
| fee | 查询与传递价格、溢价域名费用 |
| 注册局私有扩展 | 各家自定义，如实名认证材料、配额信息 |

服务端在 greeting 的 `<svcExtension>` 里声明支持哪些；客户端 login 时声明要用哪些。**协商不上的扩展应当被明确拒绝，而不是静默忽略**——静默忽略会让注册商以为 DS 已经写入而实际上没有，直接导致 DNSSEC 链断掉。
