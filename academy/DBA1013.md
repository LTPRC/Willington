# 1. 索引是什么？【P0】<img src="./icons/netease.gif" /><img src="./icons/baidu.gif" /><img src="./icons/mashibing.gif" /><img src="./icons/gupao.gif" /><img src="./icons/alibaba.gif" /><img src="./icons/citic.gif" /><img src="./icons/microsoft.gif" /><img src="./icons/bytedance.gif" />

## 定义

索引（Index）是对数据库表中一列或多列的值进行**排序**的一种**数据结构**，它们包含着对数据表里所有记录的引用指针，是帮助数据库高效获取数据的。更通俗的说，索引就相当于目录。

<img src="./images/DBA101020.png" />

> **【校正】** 老笔记中"把创建了索引的列的内容进行排序，对排序结果生成倒排表然后拼上数据地址链"的表述有误：InnoDB 的 B+Tree 索引和全文检索的倒排索引（Inverted Index）是**两种不同的数据结构，解决两类不同问题**。B+Tree 是"有序 Key → 记录/范围"；倒排索引是"Term → 包含它的文档列表"。倒排索引的内容见 [DBA1014 - 全文检索与倒排索引](./DBA1014.md)。本章只讲 B+Tree。

索引是在存储引擎层实现的，而不是在服务器层实现的，所以不同存储引擎具有不同的索引类型和实现。

## 为什么需要（磁盘视角）<img src="./icons/mashibing.gif" /><img src="./icons/alibaba.gif" />

**磁盘**的维度有两个指标：

- 寻址：ms级，比内存慢10W倍
- 带宽（单位时间通过的数据量）：M/G级

**内存**的维度有两个指标：

- 寻址：ns级
- 带宽（单位时间通过的数据量）：更大

**I/O buffer**的成本问题：一个扇区有512Byte，扇区越小，索引的成本越大。所以真正使用硬盘的时候并不是以512Byte作为一次的读写量，操作系统无论读多少，磁盘一般默认最少4K。数据库有很多data page，大小就是4k（InnoDB 页默认 16K，见 [DBA1011](./DBA1011.md)）。

关系型数据库建表必须给出schema，声明每一列的类型以及字节宽度，然后倾向以行为单位进行存储。

正如随着文件变大Linux读取文件的速度会变慢，随着数据量变大数据库操作数据的速度也会变慢，这都是因为硬盘I/O成为了瓶颈。

只有建索引能够通过减少磁盘IO让速度加快，前者存的是4k的数据行，而后者存的是特定的某一列数据，每一个数据项指向不同的行。

核心价值一句话：

> **索引的本质是减少查询需要读取的数据量（页数）。**

## 优点

- 可以大大减少服务器需要扫描的数据量。

- 帮助服务器避免排序和临时表。

- 将随机IO变成顺序IO。

## 缺点

- 时间方面：创建索引和维护索引要耗费时间，当对表中的数据进行增加、删除和修改的时候，索引也要动态的维护，会降低增/改/删的执行效率；

- 空间方面：索引需要占物理空间。

## 局限性<img src="./icons/mashibing.gif" />

当表变大时，如果此时索引能够全部被硬盘存下，进行少量查询操作依然会很快，但是在高并发的时候可能会受硬盘带宽影响从而变慢。

## 使用方式<img src="./icons/citic.gif" />

如果表的记录少（两个页面之内），且不强制使用索引，则一律全表扫描。

如果没有索引，则全表扫描。

先选择主键，再选择尺寸最小的索引。

### 面试回答

> 索引本质上是数据库为提高查询效率额外维护的数据结构，核心价值是减少扫描的数据量。InnoDB 常见索引底层使用 B+Tree。索引会占空间并增加写入维护成本，所以需要结合真实查询模式设计，不是越多越好。

# 2. 为什么是 B+Tree？【P0】<img src="./icons/netease.gif" /><img src="./icons/paypal.gif" /><img src="./icons/alibaba.gif" /><img src="./icons/kaikeba.gif" /><img src="./icons/bytedance.gif" /><img src="./icons/microsoft.gif" /><img src="./icons/meituan.gif" /><img src="./icons/baidu.gif" />

数据库最怕树太深导致多次存储访问。B+Tree "矮而宽"：一个 16KB 的节点（页）能容纳很多 Key，几层就能覆盖大量数据，把磁盘 IO 控制在常数次。同时叶子节点按 Key 有序并串成链表，天然适合范围查询和排序。

## B树<img src="./icons/bytedance.gif" /><img src="./icons/qq_25940921.gif" /><img src="./icons/paypal.gif" /><img src="./icons/iqiyi.gif" /><img src="./icons/bbbbzxlb.gif" /><img src="./icons/baidu.gif" /><img src="./icons/kaikeba.gif" />

一颗m阶的B树（B-tree）定义如下：

1. 每个节点**最多有m-1个**key；
2. 根节点至少有1个key；
3. 非根节点**至少有Math.ceil(m/2)-1个**key；
4. 每个节点中的key都按照从小到大的顺序排列，每个key的左子树中的所有key都小于它，而右子树中的所有key都大于它；
5. 所有叶子节点都位于同一层，即根节点到每个叶子节点的长度都相同。

2-3树就是3阶的B树，2-3-4树就是4阶的B树。

如下图是一棵4阶B树（2-3-4树）：

<img src="./images/DBA101022.png" />

### B树的优点

多路查找树的数据结构，用在内存读取外存的场景下，可以减少磁盘的IO次数，因为在高阶的情况下，树不用很高就可以标识很大的数据量了。

由于B树的每一个节点都包含key和value，因此经常访问的元素可能离根节点更近，因此访问也更迅速。

## B+树<img src="./icons/bytedance.gif" /><img src="./icons/tuling.gif" /><img src="./icons/pingan.gif" /><img src="./icons/qq_25940921.gif" /><img src="./icons/paypal.gif" /><img src="./icons/iqiyi.gif" /><img src="./icons/bbbbzxlb.gif" /><img src="./icons/baidu.gif" />

B+树在B树的基础上做了优化，它与B树的差异在于：

1. 有 k 个子节点的节点**必然有 k 个**key；
2. 非叶子节点仅具有索引作用，跟记录有关的信息均存放在叶子节点中。
3. 树的所有叶子节点构成一个有序链表，可以按照key排序的次序遍历全部记录。

即，B和B+树的区别在于，B+树的非叶子结点只包含导航信息，不包含实际的值，所有的叶子结点和相连的节点使用链表相连，便于区间查找和遍历。

<img src="./images/DBA101023.png" />

### B+树的优点

由于B+树在内部节点上不包含数据信息，因此在内存页中能够存放更多的key。数据存放的更加紧密，具有更好的空间局部性。因此访问叶子节点上关联的数据也具有更好的缓存命中率。

B+树的叶子结点都是相连的，因此对整棵树的遍历只需要一次线性遍历叶子结点即可。而且由于数据顺序排列并且相连，所以便于区间查找和搜索。而B树则需要进行每一层的递归遍历，相邻的元素可能在内存中不相邻，所以缓存命中性没有B+树好。因此InnoDB选择了B+树作为索引结构，解决了元素遍历效率低下的问题。

### 面试回答

> B+Tree 节点能容纳较多 Key，使树保持较低高度，从而减少存储访问次数；叶子节点又按 Key 有序并形成顺序链表，因此既适合等值查询，也适合范围查询和排序场景。相比之下 B 树非叶节点也存数据，单页能放的 Key 更少、树更高，且范围遍历要回到上层。

# 3. 聚簇索引与二级索引【P0】

## InnoDB：聚簇索引

InnoDB支持聚簇索引和非聚簇索引。一个表只能有一个聚簇索引，即主键。主索引的叶子节点data域记录着完整的数据记录。

**InnoDB 的主键选择规则**（没有显式主键时）：

1. 如果设置了主键，InnoDB选择主键作为聚集索引；
2. 如果没有显式定义主键，则InnoDB选择第一个不包含NULL值的唯一索引作为主键索引；
3. 如果也没有这样的唯一索引，则InnoDB选择内置6字节长的ROWID作为隐含的聚集索引（ROWID随着行记录的写入而递增）。

<img src="./images/DBA101024.png" />

索引和数据都在ibd文件里。

<img src="./images/DBA101025.png" />

### 自增主键 vs 非自增主键

**自增主键**：每次插入新的记录，记录就会顺序添加到当前索引节点的后续位置，主键的顺序按照数据记录的插入顺序排列，自动有序。当一页写满，就会自动开辟一个新的页。

**非自增主键**：例如身份证号或学号等，由于每次插入主键的值近似于随机，因此每次新纪录都要被插到现有索引页的中间某个位置，此时MySQL不得不为了将新记录插到合适位置而移动数据，甚至目标页面可能已经被回写到磁盘上而从缓存中清掉，此时又要从磁盘上读回来，这增加了很多开销，同时频繁的移动、分页操作造成了大量的碎片，得到了不够紧凑的索引结构，后续不得不通过OPTIMIZE TABLE来重建表并优化填充页面。

> 这是"推荐自增整型主键"的根本原因：插入顺序 = 主键顺序，避免页分裂与碎片。

## 二级索引与回表

二级索引叶子通常保存"索引列 + 主键"，而不是完整行：

```text
name='Alice'
 → idx_name 找到 PK=100
 → 主键索引（聚簇索引）
 → 完整 Row
```

第二次查主键索引就是**回表**。

<img src="./images/DBA101029.png" />

> "走索引"不等于一定快；如果命中几十万条并大量回表，总代价可能高于全表扫描，优化器也正是基于这个成本模型决定走不走索引。

## MyISAM：非聚簇索引

MyISAM支持非聚簇索引，值都记录在辅助索引的叶子节点的data域，因此在使用辅助索引进行查找时，需要先从辅助索引查找到主键值，然后再到主索引中进行查找。

<img src="./images/DBA101026.png" />

索引存放在MYI文件，表数据存放在MYD文件。

<img src="./images/DBA101027.png" />

（MyISAM 细节已 Appendix 化，见 [DBA1015](./DBA1015.md)。）

### 面试回答

> InnoDB 的聚簇索引把索引组织和行数据结合在一起，主键索引叶子节点直接保存完整行，按主键查一次就能取整行；二级索引叶子保存索引列和主键，如果查询还需要索引外的字段，就先通过二级索引得到主键再回聚簇索引取整行，这就是回表。所以二级索引列加上主键尽量覆盖高频查询字段，可以省掉回表。

# 4. 覆盖索引【P0】<img src="./icons/mashibing.gif" /><img src="./icons/paypal.gif" />

索引覆盖指：如果要查询的字段都建立过索引，那么引擎会直接在索引中查询并返回，而不需要回表访问原始数据行。

有 `(name,age)` 索引，查询 `SELECT name,age FROM user WHERE name=?` 可能直接从索引得到结果（EXPLAIN Extra 显示 `Using index`）。

不要想着为每个字段建立索引，因为索引的优势就在于其体积小。

### 优点

- 索引条目通常远小于数据行大小，如果只需要读取索引，那么mysql就会极大地减少数据访问量。

- 因为索引是按照列值顺序存储的，所以对于IO密集型的范围查询，会比随机从磁盘读取每一行数据的IO少得多。

### 存储引擎差异

- 由于InnoDB的聚簇索引，覆盖索引对InnoDB表特别有用。

- 一些存储引擎如MyISAM在内存中只缓存索引，数据则依赖于操作系统来缓存，因此要访问数据需要一次系统调用，这可能会导致严重的性能问题。

- Memory存储引擎不支持覆盖索引。

### 面试回答

> 覆盖索引指查询需要的字段都能直接从索引获得，不需要再根据主键回表。它可以减少额外访问，EXPLAIN 里对应 Using index。但也要权衡索引大小和写入维护成本，不是见查询就加宽索引。

# 5. 联合索引与最左前缀【P0】

`INDEX(a,b,c)` 是先按 a 排，a 相同再按 b，最后按 c，类似电话簿先按姓再按名。

这个顺序决定了数据库能如何利用索引的有序性：通常 `(a)`、`(a,b)`、`(a,b,c)` 能利用其左侧有序结构；完全跳过 a，不能像从 a 开始一样高效定位。

```sql
-- 容易利用
WHERE a=?
WHERE a=? AND b=?
WHERE a=? AND b=? AND c=?

-- 需要警惕
WHERE b=?                 -- 跳过最左列
WHERE a>? AND b=?         -- a 是范围后，b 的有序利用受限
```

联合索引要结合 `WHERE / ORDER BY / SELECT` 的真实访问模式设计。

### 面试回答

> 联合索引有明确列顺序，例如 `(a,b,c)` 先按 a 排，再按 b、c。因此查询通常从索引左侧列开始才能充分利用有序结构，这就是最左前缀原则。设计时把等值条件、高选择性的列放在左边，并尽量让索引同时服务过滤和排序。

# 6. 索引分类【P1】<img src="./icons/alibaba.gif" /><img src="./icons/paypal.gif" /><img src="./icons/meituan.gif" /><img src="./icons/jd.gif" /><img src="./icons/gupao.gif" /><img src="./icons/bytedance.gif" /><img src="./icons/netease.gif" />

## 主键 Primary key

是表中的一个或多个字段，它的值用于唯一地标识表中的某一条记录。主键是一种特殊的**唯一索引**，且要求**非空**，MySQL会自动为所有表的主键进行索引。

建表的时候可以直接在列名后面增加主键约束：

```sql
ID char(5) primary key
```

对已经建表的列增加主键约束：

```sql
alter table 表名 add constraint 约束名 primary key (ID)
```

## 普通索引 Normal Index

也叫非唯一索引，是最普通的索引，没有任何的限制。

## 唯一索引 Unique Index

唯一索引表明此索引的每一个索引值只对应唯一的数据记录。一张表可以有多个唯一索引。

## 全文索引 Fulltext Index

主要用来查找文本中的关键字，配合**MATCH AGAINST**操作使用。InnoDB 在 MySQL 5.6.4 版本开始支持全文索引。（全文检索与倒排索引的完整讨论在 [DBA1014](./DBA1014.md)。）

## 联合/组合索引 Union Index

MySQL中的索引可以以一定顺序引用多列，这种索引叫作联合索引。

## 外键

外键用于与另一张表的关联，保持数据的一致性。

使用条件：两个表必须是InnoDB表；外键字段必须由用户进行明确的索引；两个表的列必须是数据类型相似。

> **实践口径**：互联网业务里外键约束很少用，一致性由应用层/事务保证——外键会带来额外锁和级联开销。知道概念即可。

## 哈希索引<img src="./icons/alibaba.gif" /><img src="./icons/paypal.gif" />

<img src="./images/DBA101028.png" />

通过Hash算法将数据库字段数据转换成定的Hash值，与这条数据的行指针一并存入Hash表的对应位置。如果发生Hash碰撞，则在对应Hash键下以链表形式存储。

### 缺点

- 哈希索引适合等值查询，但是无法进行范围查询。
- 哈希索引没办法利用索引完成排序。
- 哈希索引不支持多列联合索引的最左匹配规则。
- 如果有大量重复键值的情况下，哈希索引的效率会很低，因为存在哈希碰撞问题。

### 存储引擎

InnoDB 存储引擎有一个特殊的功能叫"自适应哈希索引"：当某个索引值被使用的非常频繁时，会在 B+Tree 索引之上再创建一个哈希索引，让 B+Tree 索引具有哈希索引的一些优点，比如快速的哈希查找。

Memory引擎可以使用哈希索引。

## 空间数据索引【P2】

MyISAM 存储引擎支持空间数据索引（R-Tree），可以用于地理数据存储。必须使用 GIS 相关的函数来维护数据。

# 7. 索引利用问题：不要背口诀【P0】<img src="./icons/baidu.gif" /><img src="./icons/alibaba.gif" /><img src="./icons/jd.gif" /><img src="./icons/pingan.gif" /><img src="./icons/bbbbzxlb.gif" />

> **【校正】** 老笔记里"XX 一定使索引失效"式的清单是面试高危答案。**最终以 EXPLAIN 执行计划为准**——优化器基于成本（统计信息、基数、选择性、回表代价）做决定。下面每条都理解为"风险点"，不是"必然失效"。

先理解机制，再看风险清单：

- 对索引列做函数/计算：破坏了索引列原有的可直接查找性，例如 `upper(col)=?`、`col+1=?`；

- 联合索引使用方式不合理：跳过最左列、范围条件之后的列利用受限；

- `LIKE '%abc'` 前导模糊：无法利用 B+Tree 左侧有序定位；

- 隐式类型转换：**不是所有隐式类型转换都会导致索引失效**。经典场景是 VARCHAR 索引列拿数字去比较，例如 `varchar_col = 123`，MySQL 会进入数值比较，字符串列的索引可能无法用于快速查找；反过来 INT 列和 `'123'` 这样的字符串常量比较，通常可以把常量转换成数字，索引仍然可以使用。核心看类型转换是否破坏了索引列原有的可直接查找性；

- 返回数据比例过高时：优化器可能认为全表扫描更便宜（大范围 + 回表的代价可能超过整表顺序读）。

补充的老笔记条目（同样以执行计划为准）：

- 搜索一个索引而在另一个索引上做 order by：`where A=a order by B`，只使用A上的索引，因为一条查询通常只用一个索引（可用联合索引 `(A,B)` 解决）；

- or 的利用：`where A=a1 or A=a2`（同一列，可用 index merge 或 IN 改写）；`where A=a or B=b`（不同列，索引利用通常变差）；

- 索引列不能是表达式的一部分或者函数参数，`!=`、`not in` 等写法利用索引的能力通常受限（仍取决于优化器成本判断）。

### 面试回答

> 我一般从 B+Tree 有序性和优化器成本理解索引问题。常见风险包括函数计算、联合索引使用不合理、前导模糊、类型转换和返回比例过高。但我不背"某写法一定失效"的口诀，隐式类型转换也是分方向的——varchar 列和数字比较才容易出问题，int 列和字符串常量比较通常没事。最终都用 EXPLAIN 验证。

# 8. EXPLAIN【P0】<img src="./icons/bbbbzxlb.gif" /><img src="./icons/alibaba.gif" />

使用**EXPLAIN**关键字可以模拟优化器执行SQL查询语句，从而知道MySQL是如何处理SQL语句的。这可以帮助分析查询语句或是表结构的性能瓶颈。通过EXPLAIN命令可以得到：

- 表的读取顺序

- 数据读取操作的操作类型

- 哪些索引可以使用

- 哪些索引被实际使用

- 表之间的引用

- 每张表有多少行被优化器查询

## 先记五个字段【P0】

```text
possible_keys → 候选索引
key           → 实际索引
type          → 访问方式
rows          → 预计检查行数
Extra         → 额外执行信息
```

SQL 慢不能靠猜，需要知道 MySQL 准备怎么访问数据——EXPLAIN 就是 SQL 的"执行路线图"。

放回系统：

```text
慢SQL → EXPLAIN → 执行计划 → 优化 → 再验证
```

## type 怎么看【P0】

```text
const → ref → range → index → ALL
```

- **const**：非常精确的唯一值访问（主键/唯一索引等值）；

- **ref**：常见索引等值匹配（非唯一）；

- **range**：索引范围扫描；

- **index**：扫描整个索引；

- **ALL**：全表扫描。

> type 帮助判断访问方式，但实际优化必须结合 rows、key、Extra 和数据量，不能只看 type。

## key / rows / Extra【P0】

- `key`：实际选择的索引（possible_keys 多而 key 为 NULL 时要注意）；

- `rows`：预计检查的数据量——最直接的规模信号；

- `Using index`：常见于覆盖索引，不回表；

- `Using filesort`：需要额外排序过程；

- `Using temporary`：使用临时表处理某些操作（如 group by/distinct 的中间结果）。

> **【校正】** 看到 filesort 或 temporary 不应该机械判定"很差"——小数据量下的 filesort 完全无害；数据量大时才是优化对象。判断标准回到 rows 和真实耗时。

### 面试回答

> EXPLAIN 用于查看 SQL 执行计划。我重点看 type、实际索引 key、预计扫描行数 rows，以及 Extra 中的额外排序、临时表等信息，用它验证优化器实际怎么执行，而不是凭 SQL 外观猜。看到 filesort 或 temporary 我会先看数据规模再决定要不要处理。

# 9. 慢 SQL 排查 SOP【P0】

不要第一反应"加索引"。

```text
定位慢SQL和参数（监控/慢查询日志）
 → EXPLAIN
 → type/key/rows/Extra
 → 表结构/索引
 → 扫描/回表/排序/锁等待
 → 优化
 → 验证
```

## 展开为可口述的步骤

1. **先确认瓶颈在 DB**：API 慢不一定是 SQL——先看链路（网关/服务/连接池/DB），确认 DB 是瓶颈后再进入 SQL 分析；连接池打满也会表现为"SQL 慢"；

2. **定位具体 SQL 和参数**：慢查询日志 / APM / `show processlist`；拿到真实参数，因为执行计划跟绑定值强相关；

3. **EXPLAIN 看执行计划**：type、key、rows、Extra，判断是全表扫、回表过多、filesort 还是 temporary；

4. **结合表结构与数据量**：有没有匹配查询模式的联合索引、区分度如何、返回量多少；

5. **排除非执行计划因素**：锁等待（`SHOW ENGINE INNODB STATUS`）、缓冲池命中率、其他会话的长事务；

6. **优化后验证**：用相同数据规模验证执行计划（EXPLAIN）和真实耗时（profile / 监控），不是"改完就走"。

## 例子

GoPay 某 KYC 查询慢：先看是否存在匹配查询条件的联合索引、返回量、回表量，也要排除锁等待和连接池问题。

### 面试回答

> 我会先通过监控或慢查询日志定位具体 SQL 和参数，先确认瓶颈确实在数据库而不是连接池或上游；再用 EXPLAIN 看访问方式、索引、扫描行数和 Extra，结合数据量、表结构判断是扫描、回表、排序还是锁等待的问题；优化后用相同数据规模验证执行计划和真实耗时。第一反应不是加索引。

# 10. ORDER BY 原理【P1】<img src="./icons/bbbbzxlb.gif" /><img src="./icons/paypal.gif" /><img src="./icons/jd.gif" />

## 使用场景

当我们使用order by将查询结果按照某个字段排序时，如果该字段没有建立索引，那么执行计划会将查询出的所有数据使用**外部排序**（将数据从硬盘分批读取到内存使用内部排序，最后合并排序结果），这个操作是很影响性能的，因为需要将查询涉及到的所有数据从磁盘中读到内存，更无论读到内存之后的排序了。

如果对该字段建立索引 `alter table 表名 add index(字段名)`，那么由于索引本身是有序的，直接按照索引的顺序和映射关系逐条取出数据即可。如果分页，只用取出索引表某个范围内的索引对应的数据，而不用取出所有数据进行排序再返回某个范围内的数据。（从磁盘取数据是最影响性能的）

## 全字段排序

<img src="./images/DBA101030.png" />

## RowId排序

<img src="./images/DBA101031.png" />

如果MySQL实在是担心排序内存太小，会影响排序效率，才会采用**rowid排序**算法，这样排序过程中一次可以排序更多行，但是需要再回到原表去取数据。

如果MySQL认为内存足够大，会优先选择**全字段排序**，把需要的字段都放到sort_buffer中，这样排序后就会直接从内存里面返回查询结果了，不用再回到原表去取数据。

这也就体现了MySQL的一个设计思想：如果内存够，就要多利用**内存**，尽量减少**磁盘**访问。对于InnoDB表来说，rowid排序会要求回表多造成磁盘读，因此不会被优先选择。

可以通过设置**联合索引**，不通过排序就能得到正确的结果。这样对系统的消耗会小很多，语句的执行时间也会变得更短。

# 11. 分页与深分页【P1】<img src="./icons/jd.gif" /><img src="./icons/paypal.gif" /><img src="./icons/baidu.gif" />

## 假分页 vs 真分页

**假分页**：第一次就取出全部数据，点击下一页的时候只是展示的不一样而已，而不是再次和后台交互。

**真分页**：即后台分页，每一次动态从后台获取数据，分页参数也作为一个查询参数，一起传回到后台。

MySQL使用关键字limit来进行分页：`limit offset, size` 表示从多少索引去查多少位。

```mysql
-- 例如：查找按条件排序的第6至10行。
select * from 表 order by 查询字段 desc limit 5, 5;
```

Oracle的分页要采取三层嵌套查询的思路。

## 深分页问题

`LIMIT 1000000, 20` 的代价：MySQL 需要取出并丢弃前 100 万行（若走二级索引还要回表 100 万次），offset 越大越慢。

常见优化：

```text
1. 游标/Keyset 分页：WHERE id > 上次最大id ORDER BY id LIMIT 20
   （利用索引定位，不扫描丢弃行；要求有稳定排序键）
2. 延迟关联：先覆盖索引查出主键，再回表取整行
   SELECT t.* FROM t JOIN (SELECT id FROM t WHERE ... ORDER BY x LIMIT 1000000, 20) tmp ON t.id = tmp.id
3. 产品层限制：禁止跳转到任意深页，只允许下一页
```

> **面试提示**：深分页是"覆盖索引 + 回表代价"的最好应用题——先在索引上完成定位和分页，最后只对 20 行回表。

# 12. 索引优化实践【P1】<img src="./icons/mashibing.gif" /><img src="./icons/baidu.gif" /><img src="./icons/paypal.gif" />

## 避免回表查询<img src="./icons/mashibing.gif" /><img src="./icons/road5858.gif" />

**回表查询**指的是使用普通索引查询时先扫描一遍普通索引找到主键值，再扫描一遍主键找到行记录。

- 使用主键查询，而不是其他索引，可以避免触发回表查询。

- 覆盖索引：查询字段都在索引中，直接在索引中返回，不访问原始数据。

## 索引下推 ICP（Index Condition Pushdown）<img src="./icons/mashibing.gif" />

将"使用索引查找数据→筛选符合条件的数据"的过程，精简为"使用索引查找符合条件的索引→查找数据"，减少需要回表查询的全行数据。

### 启动方式

mysql默认启用索引下推，可以通过修改系统变量optimizer_switch的index_condition_pushdown标志来控制：

```sql
SET optimizer_switch = 'index_condition_pushdown=off';
```

### 使用条件

- 索引下推只能用于InnoDB的二级索引，因为主键索引树叶子结点上保存的是全行数据，索引下推并不能减少查询全行数据的效果。

- 索引下推不要求select列有联合索引的字段，但要求有多个查询条件，且查询条件子句（where/order by）字段全是联合索引。

## 使用前缀索引

语法：`index(field(?))`，使用字段值的前?个字符建立索引，默认是使用字段的全部内容建立索引。前缀长度的选取需要根据索引选择性来确定。

对于 BLOB、TEXT 和 VARCHAR 类型的列，必须使用前缀索引。

## 更新频繁的字段上不宜建立索引

索引更新会变更B+树，频繁更新会大大降低数据库性能。

## 索引列的顺序

让选择性最强的索引列放在前面。索引的选择性是指：不重复的索引值和记录总数的比值。最大值为 1，此时每个记录都有唯一的索引与其对应。选择性越高，每个记录的区分度越高，查询效率也越高。

例如性别这类区分不大的属性，建立索引是没有意义的，不能有效的过滤数据，一般区分度在80%以上的时候就可以建立索引，区分度可以使用 `count(distinct(列名))/count(*)` 来计算。

## 使用场景

### WHERE

对比没有索引的字段执行WHERE语句，效率有明显提升。

如果一个字段被定义了多个索引，在执行WHERE语句时，只调用主键索引。

<img src="./images/DBA101021.png" />

### JOIN

对Join语句匹配关系（on）涉及的字段建立索引能够提高效率。

# 13. 数据库文件【P2】<img src="./icons/kaikeba.gif" />

MySQL的每个数据库都对应存放在一个与数据库同名的文件夹中，该文件夹由MySQL配置文件 /etc/my.cnf 定义，其中datadir=/var/lib/mysql指定存放位置。

```sql
SHOW VARIABLES LIKE '%datadir%';
```

### 表结构文件

不论表使用的哪一种存储引擎，MySQL都会为表生成一个.frm为后缀名的表结构文件。（MySQL 8.0 起 .frm 已被移除，表结构并入数据字典。）

### InnoDB数据文件

采用表空间 (tablespace) 来管理数据，存储表数据和索引：

- .ibd文件：独享表空间，一张表对应一个ibd文件。
- .ibdata文件：共享表空间，所有表共同使用一个或者多个ibdata文件。

### MyISAM数据文件

- .myd文件：存储表数据信息。
- .myi文件：存储索引数据树。
