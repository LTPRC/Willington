> **本章定位：**Query。EPP 是注册商的写通道，RDAP/WHOIS 是公众的读通道。两者服务同一份注册数据，但设计年代差了三十年，能力差异全部集中在"结构化"和"访问控制"两点上。

## 一个词先立住：RDDS

ICANN 用 **RDDS（Registration Data Directory Service，注册数据目录服务）**统称对外提供注册数据查询的所有服务，WHOIS 和 RDAP 都在这个伞下。规范里说"必须提供 RDDS"，指的是这组能力，而不是某个具体协议。

## WHOIS：1980 年代的设计

协议本体极简（RFC 3912）：

```text
客户端 ──TCP 连接 43 端口──► 服务端
客户端 ──发一行查询 + CRLF──►
       ◄──回一段自由文本，然后关闭连接──
```

```bash
$ whois -h whois.registry.example example.com
Domain Name: EXAMPLE.COM
Registrar: Example Registrar Inc.
Creation Date: 1995-08-14T04:00:00Z
Domain Status: clientTransferProhibited
Name Server: NS1.EXAMPLE.NET
```

它的能力边界就是这段文本的样子。四个结构性缺陷：

| 缺陷 | 后果 |
| --- | --- |
| 无结构 | 输出格式由各家注册局/注册商自定义，字段名、顺序、日期格式都不统一，机器解析只能靠正则硬啃，且随时会碎 |
| 无鉴权 | 服务端不知道请求者是谁，因此**无法做分级可见性**——要么全公开，要么全不公开 |
| 无国际化 | 协议假定 ASCII，IDN 与本地化信息表达困难 |
| 无标准限流 | 43 端口上没有任何标准的速率控制约定，抓取与滥用只能靠服务端自己封 IP |

**thin 注册局下的 referral 也是个约定而非协议**：查 `.com` 的 WHOIS，返回里会带一行 `Registrar WHOIS Server: whois.registrar.example`，客户端自己去再查一次拿注册人信息。这条链路没有标准化的错误处理，任何一跳不可用整个查询就断了。thin/thick 的区别见 [SYS2021](./SYS2021.md)。

## RDAP：HTTP + JSON

RDAP 的设计目标就是逐条补上 WHOIS 的缺陷。规范族：RFC 7480（HTTP 用法）、7481（安全）、7482（查询格式）、9082（JSON 响应格式）、9224（bootstrap 注册表更新）。

### 查询路径

以注册局分配的 base URL 为根，按对象类型分路径：

| 路径 | 查什么 |
| --- | --- |
| `/domains/{name}` | 域名 |
| `/nameservers/{name}` | 主机 |
| `/entity/{handle}` | 实体（注册人、注册商、联系人） |
| `/help` | 服务能力说明 |
| `/domains?name={pattern}` | 域名模糊搜索 |
| `/entities?fn={pattern}` | 按名字搜实体 |
| `/entities?handle={pattern}` | 按 handle 搜实体 |

响应媒体类型是 `application/rdap+json`。

### bootstrap：客户端怎么知道该问谁

WHOIS 时代要记住一堆 whois 服务器地址。RDAP 用 **bootstrap 注册表**解决：IANA 发布一份 JSON，把每个 TLD（以及 IP 段、ASN）映射到对应的 RDAP base URL。客户端本地查这张表，直接找到该问谁，不需要中央服务器转发。

服务端也可以在发现自己不是权威方时返回 **302 重定向**到正确的 RDAP 服务，两条路径并存。

### 响应结构

```json
{
  "rdapConformance": ["rdap_level_0"],
  "objectClassName": "domain",
  "handle": "2138514_DOMAIN_COM-VRSN",
  "ldhName": "example.com",
  "status": ["client transfer prohibited"],
  "entities": [
    {
      "objectClassName": "entity",
      "handle": "9999",
      "roles": ["registrar"],
      "vcardArray": ["vcard", [
        ["version", {}, "text", "4.0"],
        ["fn", {}, "text", "Example Registrar Inc."]
      ]]
    }
  ],
  "nameservers": [
    { "objectClassName": "nameserver", "ldhName": "NS1.EXAMPLE.NET" }
  ],
  "secureDNS": { "delegationSigned": true },
  "events": [
    { "eventAction": "registration", "eventDate": "1995-08-14T04:00:00Z" },
    { "eventAction": "expiration",   "eventDate": "2027-08-13T04:00:00Z" },
    { "eventAction": "last changed", "eventDate": "2026-08-14T07:01:44Z" }
  ],
  "links": [
    { "rel": "self", "href": "https://rdap.registry.example/domain/example.com",
      "type": "application/rdap+json" }
  ],
  "port43": "whois.registry.example"
}
```

几个字段的含义值得单独拎出来：

- **`objectClassName`**：区分 domain / nameserver / entity / ip network / autnum，客户端靠它决定怎么解析这个对象，而不是靠路径猜。
- **`ldhName` 与 `unicodeName`**：前者是 ASCII 兼容编码（Punycode）形式，后者是 Unicode 原形。IDN 域名两个都有，这解决了 WHOIS 的国际化缺陷。
- **`status`**：复用的就是 EPP 状态码语义，但字面形式改成了 IANA RDAP JSON Values 注册表里的小写空格分隔写法。`clientTransferProhibited` → `"client transfer prohibited"`，`active`/`ok` 也有对应映射。**后端必须维护这张映射表，不能直接透传 EPP 的驼峰值**，否则响应不合规。状态语义见 [SYS2023](./SYS2023.md)。
- **`events`**：把注册、到期、最后变更、转移等时间点结构化，而不是散在文本里。
- **`secureDNS`**：说明这个域名是否做了 DNSSEC 委派，可携带 DS 数据，与 [SYS2026](./SYS2026.md) 对接。
- **`port43`**：告诉客户端同一份数据的 WHOIS 服务器在哪。这个字段本身就是过渡期的产物。
- **`rdapConformance`**：服务端声明自己实现了哪些 profile 与扩展，客户端据此判断能用哪些能力。

联系人信息用 **jCard**（vCard 的 JSON 形式，RFC 7095）表达，嵌在 entity 对象的 `vcardArray` 里。

### 错误响应

沿用 HTTP 语义，不用自造错误码：

| HTTP 状态 | 场景 |
| --- | --- |
| 400 | 查询语法错 |
| 404 | 对象不存在 |
| 405 | 方法不允许 |
| 422 | 查询能解析但无法执行（如搜索模式过长） |
| 429 | 触发限流 |
| 500 | 服务端错误 |

响应体是 `{"errorCode": 404, "title": "Not Found", "notices": [...]}` 这样的标准结构，与成功响应共用一套外层。

## 分级可见性：RDAP 真正的分水岭

这是 WHOIS 结构上做不到的事。因为 RDAP 跑在 HTTP 上，它天然继承了整套 HTTP 鉴权能力（TLS 传输、Basic/Bearer/OAuth 等认证方案），于是**同一份数据可以按请求者身份返回不同的字段集**：

```text
匿名请求          → 只返回技术性字段：域名、状态、NS、时间、注册商 handle
已认证注册商      → 额外可见自己名下域名的完整注册人与联系人信息
已认证特定角色    → 按政策与授权可见更完整的披露数据
```

后端实现上这不是一个开关，而是一条**字段级授权链**：

```text
认证 → 得到调用方身份与角色
     → 查出该域名对应的授权关系（是不是本注册商名下？是不是注册人本人？）
     → 按策略对响应对象做字段裁剪与脱敏
     → 记录一次访问审计日志
```

字段裁剪必须在**序列化层统一做**，不能散在各个接口的业务代码里。任何一条新加的查询路径漏掉了裁剪，就等于一次数据泄露。

## 数据脱敏与隐私

公开注册数据的可见范围受两股力量影响，要分清：

- **隐私代理服务（Privacy / Proxy）**：商业服务，由代理方作为公开可见的注册人出现，真实注册人信息不入库公开视图。这是**注册人主动选择**的。
- **法规驱动的脱敏**：GDPR 之后，自然人注册人的姓名、邮箱、电话、地址在公开 RDDS 中被大面积隐去。这是**注册局/注册商强制**的，与注册人是否愿意无关。

两者叠加的结果是：今天的公开查询数据比 WHOIS 全盛期少得多。需要非公开数据的第三方（知识产权权利人、执法机构）要走各 TLD 自己的申请与授权流程，而这套流程在不同 TLD 之间并不统一。

对后端来说，脱敏带来一个具体要求：**访问个人数据的行为本身要留审计**——谁、什么时候、查了哪个域名、看到了哪些字段、依据什么授权。这既是合规要求，也是数据泄露追责的唯一线索。

## 两套协议的关系

| 维度 | WHOIS | RDAP |
| --- | --- | --- |
| 传输 | TCP 43，明文 | HTTPS |
| 编码 | 自由文本 | JSON（`application/rdap+json`） |
| 结构 | 无标准 | 由规范定义，含 `objectClassName` |
| 鉴权 | 无 | HTTP 鉴权，支持分级可见性 |
| 国际化 | 弱 | ldhName + unicodeName + jCard |
| 服务发现 | 靠人工记地址与 referral 约定 | IANA bootstrap 注册表 + 重定向 |
| 错误语义 | 文本里自己找 | HTTP 状态码 + 标准错误体 |
| 搜索 | 各家语法不一 | 标准化的 `?name=` / `?fn=` 等参数 |

ICANN 已要求 gTLD 的注册局与注册商提供 RDAP，并推进 WHOIS 的退役。**具体时间点、适用范围与是否仍需并行提供 WHOIS，以 ICANN 现行规范为准**——这类过渡期要求会变，实现上应当把"哪些通道对外可用"做成配置而不是写死。

工程上的务实结论：**两套服务共用同一个数据访问层与同一套授权裁剪逻辑**，只在最外层的编码器上分叉（文本渲染 vs JSON 序列化）。如果做成两套独立实现，脱敏策略一定会在其中一边漏掉。

## 查询服务的工程要点

RDDS 是注册数据库的一个**派生只读视图**，它的问题形状和缓存一致性同源（见 [DBA2012](./DBA2012.md)）：

**一致性时延有上限要求。**规范对"注册数据变更后多久必须在查询服务可见"有明确约束。这意味着不能无脑加长缓存 TTL 来扛流量——缓存策略必须服从一致性预算，并且这个预算要被监控（对比源库与查询服务的数据，度量真实滞后）。

**缓存失效要有可靠链路。**RDAP 查询视图和 Redis 都是派生数据，SRS 注册库才是 Source of Truth。EPP 写事务提交后，不能靠"应用里顺手删一下缓存"来保证一致，因为删缓存可能失败、消息可能丢、旧读还可能把旧值回填。更稳的做法是：

```text
EPP 写事务提交
   → 同事务写 Outbox / 或 CDC 捕获 binlog
   → 可靠投递到 RDAP 视图更新消费者
   → 更新查询视图 + 失效对应缓存
   → 监控滞后水位与失败重试
```

要点：

- **先提交数据库，再可靠通知**；不要为了删缓存把数据库事务拉长。
- **缓存 key 要区分视图**：匿名、注册商、授权角色看到的字段不同，不能共用一个只按域名做 key 的缓存。
- **隐私/披露规则变更也要触发失效**：只按域名数据变更失效还不够，注册人隐藏/公开字段、disclose 策略变化后，旧缓存可能继续暴露本应隐藏的数据；规则变更要广播失效或提升视图版本。
- **允许的滞后要量化**：用"源库变更时间 vs 查询视图可见时间"做指标，超过预算告警；不能只监控缓存命中率。
- **旧值回填**：删除缓存后，一个早先开始的读可能把旧值写回；用版本号/更新时间做条件回填，或设置短 TTL 兜底。
- **Redis 整体故障**：限流 + 有界回源，保护 SRS；不能把所有请求无保护地打回注册库。

Outbox/CDC 的通用机制见 [SYS3012](./SYS3012.md)，缓存穿透/击穿/雪崩见 [DBA2012](./DBA2012.md)。

**搜索是最容易被滥用的入口。**模糊搜索如果直接落到 `LIKE '%x%'` 上就是全表扫描。必须限制模式最小长度、限制返回条数、限制通配符位置、限制每调用方的搜索频率。否则一个循环脚本就能把查询服务打死。

**限流是必需项而不是可选项。**公开无鉴权的查询端点是抓取目标，429 与 IP/AS 级封禁要常态化，且限流本身要能区分匿名流量与已签约注册商流量——注册商的控制台依赖 RDAP，被误限会直接变成生产事故。

**响应结构是对外契约。**RDAP 的 JSON 结构被大量第三方工具依赖，字段增删要走兼容性评估，最好有 schema 校验的契约测试挡在发布流程里。这一点和 [SYS3115](./SYS3115.md) 里 Schema Registry 保证 Producer/Consumer 独立发版是同一类问题。

**bulk access 是另一条通道。**批量获取整个 TLD 的区文件走的是专门的申请与授权机制，不通过 RDDS。如果有人拿 RDDS 逐条爬全站，说明限流与搜索约束没做好。
