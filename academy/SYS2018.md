> **本章定位：**Resolution。[SYS2012](./SYS2012.md) 的"解析域名"一节讲了记录类型与层级，这一章补齐协议层的三块：谁在解析（递归与权威的分工）、怎么委派（NS 与 glue）、以及怎么证明答案可信（DNSSEC）。

## 三类角色

DNS 里没有"一种服务器"，而是三种职责完全不同的参与者：

| 角色 | 持有什么数据 | 做什么 | 应答里的 AA 标志 |
| --- | --- | --- | --- |
| stub resolver（存根解析器） | 几乎没有，只有一份递归解析器地址 | 把应用的查询转发出去，等最终答案 | — |
| recursive resolver（递归解析器） | 缓存，不是权威数据 | 代客户端逐级迭代查询，缓存并返回结果 | 不置位 |
| authoritative server（权威服务器） | 自己负责的区（zone） | 只回答自己权威的数据，不代为查询别处 | **置位** |

**AA（Authoritative Answer）**是区分两者的关键标志：权威服务器对自己区内的数据置 AA=1，表示"这是事实来源"；递归解析器返回的是缓存副本，AA=0。

一个常见误解是"权威服务器也会递归"。它不会——如果查询的名字不在它的区里，它返回 REFUSED 或 referral，而不是替你去别处问。反过来，递归解析器对自己缓存的数据也不具备权威性。

## 递归查询与迭代查询

这是两种查询模式，不是一种查询的两个阶段：

| | 递归查询 | 迭代查询 |
| --- | --- | --- |
| 含义 | "你给我最终答案，我不管你怎么查" | "你知道多少告诉我多少，剩下的我自己去问" |
| 应答 | 最终结果，或明确的失败 | 可能是结果，也可能是 **referral**（下一级该问谁） |
| 发生在哪 | 客户端 → 递归解析器 | 递归解析器 → 各级权威服务器 |
| 报文标志 | 请求置 RD=1，应答置 RA 表示服务端支持递归 | 请求 RD=0 |

为什么这样分工：

- **权威服务器不愿为陌生客户端承担递归开销**。它只对自己的区负责，代查全网会让它变成开放解析器，也就是现成的放大攻击源。
- **缓存集中在递归解析器上效率最高**。全网递归解析器数量有限、缓存命中率高；如果每个客户端都自己迭代，根服务器的负载会高几个数量级。

### referral 长什么样

迭代查询得到的中间应答，Answer 段是空的，线索在 Authority 段和 Additional 段：

```text
;; ANSWER SECTION:      （空）
;; AUTHORITY SECTION:
example.com.        172800  IN  NS   ns1.example.com.
example.com.        172800  IN  NS   ns2.example.com.
;; ADDITIONAL SECTION:
ns1.example.com.    172800  IN  A    192.0.2.1
ns2.example.com.    172800  IN  A    192.0.2.53
```

Authority 段给出"下一步该问谁"（NS），Additional 段给出"那些 NS 的地址"（glue）。递归解析器据此继续下一跳。

## 完整解析过程

```text
应用 → stub resolver
         │ 递归查询（RD=1）
         ▼
      递归解析器 ── 命中缓存？──► 直接返回（AA=0）
         │ 未命中
         │ 迭代查询（RD=0）
         ├─► 根服务器        → 返回 .com 的 NS + glue
         ├─► .com 权威       → 返回 example.com 的 NS + glue
         └─► example.com 权威 → 返回 A 记录（AA=1）
         │
         ├─ 写入缓存（按 TTL）
         └─► 返回给 stub resolver → 应用
```

注意根服务器返回的是"去哪里问"，不是"答案是什么"。整条链上只有最后一跳的应答是权威的。

`dig +trace example.com` 可以把这条迭代链完整打出来，是理解本节最直接的实验手段。

## 报文结构

DNS 报文分四段，Header 之后依次是：

| 段 | 内容 |
| --- | --- |
| Question | 查询的名字、类型（A/AAAA/NS/MX/DS/DNSKEY…）、类（IN） |
| Answer | 直接回答查询的 RRset |
| Authority | 权威信息，referral 时放 NS，否定应答时放 SOA |
| Additional | 附加信息，通常放 NS 对应的 A/AAAA（glue） |

Header 里几个必须认识的标志：

| 标志 | 含义 |
| --- | --- |
| QR | 0 = 查询，1 = 应答 |
| AA | 应答方对该数据是否权威 |
| TC | 应答被截断，需要用 TCP 重发 |
| RD | 请求方希望递归 |
| RA | 应答方支持递归 |
| AD | 应答数据已通过 DNSSEC 验证 |
| CD | 请求方要求服务端**不做** DNSSEC 验证 |
| RCODE | 响应码 |

### RCODE 与一个高频误读

| RCODE | 含义 |
| --- | --- |
| NOERROR (0) | 查询成功 |
| FORMERR (1) | 报文格式错 |
| SERVFAIL (2) | 服务端无法完成查询（依赖的权威不可达、DNSSEC 验证失败等） |
| NXDOMAIN (3) | **这个名字不存在** |
| NOTIMP (4) | 未实现该操作 |
| REFUSED (5) | 拒绝服务（如向权威服务器查它不负责的区，或不允许递归） |

**NOERROR ≠ 有答案。**`RCODE=NOERROR` 且 Answer 段为空，叫做 NODATA：域名存在，但没有你问的那种类型的记录。比如域名有 A 记录但你查 AAAA，得到的是 NOERROR + 空 Answer，而不是 NXDOMAIN。把 NODATA 读成"域名不存在"是排障时的常见误判。

三者要分清：

- **NXDOMAIN**：整个名字不存在。
- **NODATA**：名字存在，该类型记录不存在。
- **SERVFAIL**：查不出来，原因在服务端或链路上，与域名是否存在无关。

## UDP 与 TCP

DNS 用 53 端口，UDP 与 TCP 都用：

| 场景 | 用什么 |
| --- | --- |
| 普通查询 | UDP（无连接，一个来回，开销最小） |
| 应答超过 UDP 上限（TC=1） | 客户端改用 TCP 重试 |
| 区传输 AXFR / IXFR | 必须 TCP（数据量大且需要可靠有序） |
| 传统 UDP 载荷上限 | 512 字节，EDNS(0) 可以协商更大的值 |

加密传输只覆盖**客户端到递归解析器**这一段：DoT（853 端口）、DoH（走 443 的 HTTPS）。权威侧的迭代查询在现实中仍以明文 UDP/TCP 为主，它的可信性靠 DNSSEC 而不是靠传输加密——这是两条独立的机制，解决的是不同的问题（机密性 vs 真实性）。

## 缓存与 TTL

缓存分三层：浏览器 → 操作系统（含 hosts 文件）→ 递归解析器。任何一层命中都不会往下走。

TTL 是权威服务器为每条记录设定的缓存时长，递归解析器按它决定缓存多久。几个必须理解的性质：

**改 TTL 不会立刻生效。**TTL 只约束"从此刻起新的缓存能存多久"，已经躺在各级缓存里的旧记录仍然按它们被缓存时拿到的 TTL 存活。所以要变更一个高频访问的记录，标准做法是**提前把 TTL 降下来，等旧缓存全部过期后再改**。临时降 TTL 再立刻改数据，等于没降。

**否定应答也会被缓存。**NXDOMAIN 和 NODATA 会被递归解析器缓存，时长受该区 SOA 记录里 minimum 字段的约束。这解释了一个反直觉现象：域名刚注册好、或者刚从 hold 状态解除，但外部一段时间内仍然解析不到——之前的"不存在"还在缓存里。

**hosts 文件优先于 DNS。**操作系统解析顺序里 hosts 在前，这是本地调试手段，也是本地劫持的攻击面。

## 委派与 glue

DNS 的树状结构靠**委派（delegation）**连接：父区在自己的区里放一条 NS 记录，指向子区的权威服务器，从此子区的解析责任就交出去了。

```text
根区：      com.          IN NS a.gtld-servers.net.
            a.gtld-servers.net. IN A  192.5.6.30     ← glue
.com 区：   example.com.  IN NS ns1.example.com.
            ns1.example.com.  IN A 192.0.2.1         ← glue
example.com 区： www.     IN A 192.0.2.80            ← 最终答案
```

### 为什么需要 glue

当子区的 NS 名字本身就在子区下面时，会出现循环依赖：要解析 `example.com` 得先问 `ns1.example.com`，而要解析 `ns1.example.com` 又得先知道 `example.com` 的 NS。

解法是**父区在委派的同时把 NS 的 IP 地址也粘一条下来**，这条 A/AAAA 记录就叫 glue record。它不是权威数据，只是为了让委派链不断掉。

由此产生一个经典故障：**glue 与权威数据不一致**。NS 的真实 IP 改了，但父区的 glue 还是旧的，于是递归解析器拿着旧 IP 去连，连不上或者连到了错误的服务器。所以 in-bailiwick 的 NS 改地址时，父区的 glue 必须同步更新——在域名注册场景下，这意味着要通过注册商走 EPP 提交给注册局，光在自己的权威 DNS 上改是不够的（见 [SYS2022](./SYS2022.md)）。

如果 NS 名字在别的区下（out-of-bailiwick，比如用云厂商的 `ns1.dns-provider.net`），就不需要 glue，也就没有这个一致性问题。

## DNSSEC

### 它解决什么问题

DNS 的原始设计里，应答**没有任何来源认证**。递归解析器收到一个应答，无法判断它是真的权威服务器发的，还是链路上伪造的。这就是缓存投毒的基础：伪造一个"某银行域名指向我的 IP"的应答，让递归解析器缓存下来，之后所有用户都被导向假站点。

注意 [SYS2012](./SYS2012.md) 里提到的 HTTPS 也救不了这种情况：解析阶段就被劫持，之后建立的 TLS 连接是跟假 IP 建立的。DNSSEC 补的正是这一环。

### 机制

DNSSEC 用非对称签名给每条数据附上可验证的来源证明：

| 记录 | 作用 |
| --- | --- |
| **DNSKEY** | 发布区的公钥，分 KSK 与 ZSK 两种 |
| **RRSIG** | 对某个 RRset 的签名，用对应私钥生成 |
| **DS** | 子区 KSK 公钥的哈希，发布在**父区**里，为子区的密钥背书 |
| **NSEC / NSEC3** | 权威地证明"某个名字或类型不存在"，防止伪造 NXDOMAIN |

**KSK / ZSK 分工**：ZSK 签区内所有 RRset，KSK 只签 DNSKEY RRset。因为只有 KSK 的哈希要发布到父区的 DS 里，所以 KSK 可以做得长且很少更换，ZSK 可以短而频繁轮换，签名体积和轮换成本都可控。

### 信任链

```text
信任锚（根区 KSK，预置在验证型解析器里）
   │ 用根 KSK 验证根区的 RRSIG
   ▼
根区的 DS（.com 的 KSK 哈希）
   │ 验证 .com 的 DNSKEY
   ▼
.com 区的 DS（example.com 的 KSK 哈希）
   │ 验证 example.com 的 DNSKEY
   ▼
example.com 区的 RRSIG
   │ 验证 A 记录
   ▼
可信的答案 → 应答置 AD=1
```

链条从预置的信任锚开始，逐级用父区的 DS 验证子区的 DNSKEY，再用子区的 ZSK 验证具体记录。**任何一级断掉，该级以下全部不可验证。**

DS 是这条链的关键衔接点，也因此产生一个容易混淆的地方：域名的 DS 记录发布在父区（TLD 区），要改它必须通过注册商提交给注册局，而不是在自己的权威 DNS 上操作。两条 DS 链路的完整区分见 [SYS2026](./SYS2026.md)。

### NSEC 与 zone walking

DNSSEC 必须能证明"不存在"，否则攻击者可以伪造 NXDOMAIN。NSEC 的做法是把区内所有名字按字典序串成一条链，每条 NSEC 记录声明"我后面存在的名字是 X"，于是"介于两者之间的名字都不存在"这个结论就带上了签名。

副作用是任何人都能顺着这条链把整个区遍历出来（zone walking）。NSEC3 用哈希后的名字串链，并支持 salt 与 opt-out，让遍历结果无法直接还原成真实域名，同时减少需要签名的记录数。

### 验证失败会怎样

**返回 SERVFAIL，而不是 NXDOMAIN。**这个区别至关重要：域名可能好好存在着，只是解析器无法证明它。排障时看到 SERVFAIL 应该先怀疑 DNSSEC 链（DS 与 DNSKEY 不匹配、RRSIG 过期、时钟偏差），而不是怀疑域名不存在。

几个相关细节：

- **AD 标志**表示应答数据已通过验证。它由验证型解析器设置，不是权威服务器设置的。
- **CD 标志**由客户端设置，要求解析器"别验证，把原始数据给我"，常用于诊断 DNSSEC 故障——CD=1 能查到而 CD=0 查不到，就说明问题在签名链上。
- **未签名的区不受影响**。DNSSEC 是逐区可选的，某一级没签名，验证就在那一级停止，不会导致失败。
- **签名过期是最常见的自伤故障**。RRSIG 有有效期，密钥轮换任务失败或签名流水线停摆，区还在正常应答，但所有签名已过期，全网验证型解析器一起返回 SERVFAIL。所以监控必须盯**验证成功率**，只盯"应答成功率"是发现不了的。

## 常见攻击与故障

| 类型 | 原理 | 缓解 |
| --- | --- | --- |
| 缓存投毒 | 向递归解析器伪造权威应答 | 随机化查询 ID 与源端口、DNSSEC |
| 放大反射 | 用小的查询触发大的应答，反射到受害者 | 权威侧不开放递归、限制 ANY 查询、启用响应速率限制（RRL） |
| DNS 劫持 | 运营商或本地篡改解析结果 | DoT/DoH 保护客户端到递归这一段 |
| zone walking | 顺 NSEC 链遍历全区 | NSEC3 + salt |
| 委派单点 | NS 全部不可达或全在同一网络 | 多个 NS、分布在不同网络、Anycast |
| glue 失配 | 父区 glue 与子区真实 IP 不一致 | 变更时同步更新父区 |
| 签名过期 | 密钥轮换失败，RRSIG 全部失效 | 密钥有效期监控 + 验证成功率监控 |

## 权威与递归的技术分界

| | 权威服务器 | 递归解析器 |
| --- | --- | --- |
| 数据来源 | 自己保管的区文件 | 别人的权威服务器 + 本地缓存 |
| 是否发起迭代查询 | 不发起 | 核心行为 |
| 是否缓存 | 只持有自己的区，不缓存别处 | 核心能力就是缓存 |
| AA 标志 | 置位 | 不置位 |
| 服务对象 | 全网递归解析器 | 终端用户的 stub resolver |
| 关键指标 | 应答时延、可用率、区发布时延 | 缓存命中率、解析成功率、QPS |
| 典型故障 | 区加载失败、签名过期、glue 失配 | 缓存投毒、上游不可达、命中率骤降 |

两套技术栈的重叠面很小。域名注册行业里，注册局运营的是 TLD 的**权威区**以及把注册数据库变成区文件的发布链，不做递归解析——这条业务侧的边界与职责划分见 [SYS202 - Domain Name Registry Services](./SYS202.md)。

## 排查命令

```bash
dig example.com A                    # 单次查询，看完整应答
dig +trace example.com               # 从根开始打印整条迭代链
dig +dnssec example.com              # 要求返回 RRSIG，看 AD 标志
dig +cd example.com                  # 关闭验证，用于判断是否 DNSSEC 问题
dig @8.8.8.8 example.com             # 指定用哪个递归解析器
dig example.com NS +short            # 看委派给谁
dig example.com SOA                  # 看 serial 与最小 TTL（否定缓存时长）
dig DS example.com                   # 看父区里的 DS（需向父区权威查询）
dig DNSKEY example.com               # 看区的公钥
dig AXFR example.com @ns1.example.com # 区传输，生产环境通常被拒绝
```

排障的顺序建议：先 `dig` 看 RCODE 分清 NXDOMAIN / NODATA / SERVFAIL；SERVFAIL 就加 `+cd` 判断是不是 DNSSEC；怀疑缓存就换不同的 `@` 递归解析器对比；怀疑委派就 `+trace` 走一遍完整链，看是哪一跳断的。
