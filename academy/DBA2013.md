## 为什么需要分布式锁？【P0】

### 人话解释

`synchronized` 只能协调一个 JVM。多实例部署时，各机器的本地锁互相不知道。

### 为什么需要

如果多个实例要争抢同一个跨进程资源，需要共享协调机制。

### 图

```text
Server A ─┐
Server B ─┼→ Redis Lock → Critical Section
Server C ─┘
```

**Critical Section（临界区）**：希望同一时刻只有一个执行者进入的代码区域。

### 放回系统

并不是所有并发问题都该用 Redis 锁；数据库唯一约束、乐观锁、幂等有时更合适。

### 面试回答【30-60 秒】

> Java 本地锁只能协调单 JVM 线程，多实例部署后需要跨进程协调时才可能使用分布式锁。Redis 因为提供原子命令和 TTL，是常见实现之一。但工程上我会先判断能否用数据库约束、乐观锁或幂等解决，避免滥用分布式锁。

## Redis 分布式锁基础实现【P0】

概念命令：

```text
SET lock_key unique_value NX EX/PX timeout
```

术语：

- `NX`：Key 不存在才设置成功；
- `EX/PX`：带过期时间；
- `unique_value`：标记锁属于谁（owner 标识）。

### 为什么必须 TTL

持锁服务崩溃后，锁不能永久存在。

### 为什么 unique value

释放时必须确认"锁还是我的"。

### 面试回答【30-60 秒】

> 基础实现会使用带 NX 和过期时间的 SET，使"判断不存在并写锁"原子完成，value 使用唯一 owner 标识。TTL 防止实例崩溃造成永久占锁。释放时要确认锁仍属于自己，并原子删除。

------------------------------------------------------------------------

## 为什么不能直接 DEL 解锁？【P0】

场景：

```text
A 拿锁
→ A 执行太久
→ 锁过期
→ B 拿到新锁
→ A 结束后直接 DEL
→ 把 B 的锁删了
```

所以：

```text
if value == myUniqueValue:
    delete
```

"比较 + 删除"也必须原子完成，常见用 **Lua 脚本**。这里 Lua 只需理解为 Redis 可以把一小段判断和删除逻辑原子执行。

### 面试回答【30-60 秒】

> 不能直接 DEL，因为旧锁可能已经过期并被其他实例重新获得。释放时必须比较 owner 标识，再删除，而且比较和删除要原子完成，常见使用 Lua 脚本。

## 锁还没执行完就过期怎么办？【P0｜历史失分】

### 人话解释

锁 TTL 10 秒，业务执行 30 秒，第 10 秒另一个实例就可能进来。

### 两类方案

- 执行时间可预测：设置合理的 TTL；
- 执行时间不可预测：自动续期。

### Watchdog

Watchdog（看门狗）就是：

> 持锁任务还活着时，后台持续给锁续期。

### 图

```text
Acquire → Business Running ↔ Watchdog Renew → Done → Unlock
```

### 面试回答【30-60 秒】

> 如果业务耗时超过锁 TTL，锁会提前释放导致互斥失效。执行时间可预测时可以设置合理 TTL；不可预测时可使用自动续期机制。像 Redisson watchdog 会在持锁任务仍有效时持续续期。不过关键业务仍应有幂等或数据库约束兜底。

## Redisson / Watchdog【P0/P1｜历史失分】

### 人话解释

Redisson 是 Java Redis 客户端和高级分布式工具库，封装了分布式锁等能力。

### 为什么需要

手写锁很容易漏掉：原子加锁、owner 标识、安全释放、续期、重入等细节。

### Watchdog

在合适的锁使用方式下（不显式指定 leaseTime），持锁任务仍运行时自动延长锁有效期。

### 系统位置

```text
Java Service → Redisson API → Redis
```

### 面试回答【30-60 秒】

> Redisson 是 Java 生态常用的 Redis 客户端和分布式工具库，封装了分布式锁等高级能力。Watchdog 可以理解为锁的自动续期机制，在持锁任务仍有效时延长 TTL，避免业务没执行完锁就提前失效。没有实际生产深度经验的部分我会明确说明。

## 分布式锁完整答案【P0++】

一口气串起来：

```text
SET key ownerId NX PX ttl
↓
只有一个客户端成功
↓
业务执行
↓
Lua：只有 value == ownerId 才 DEL
↓
业务超过 ttl？
→ 续期 / Watchdog
↓
客户端崩溃？
→ TTL 最终释放
```

但还要知道：

> Redis 锁不是所有一致性问题的唯一答案。

GoPay 自动 KYC 决策真实用的是：

```text
DB row lock + decision gate
```

不是 Redis lock。

------------------------------------------------------------------------

## 边界：什么时候不用 Redis 锁【P0++】

- 能用数据库唯一约束、乐观锁（version/CAS）、幂等设计解决的，优先用数据库语义，避免引入 Redis 锁的额外失败模式；
- 资金余额类数据的权威记录不落在普通 Redis 缓存上（见 [DBA2012 - 资金类数据的 Source of Truth](./DBA2012.md)）；
- Redis 锁不可用时（宕机），核心写路径应 **fail closed**（拒绝/暂停高风险操作），而不是"锁没了就裸奔"（见 [DBA2012 - 宕机后的降级策略](./DBA2012.md)）。

### 面试回答【30-60 秒】

> 我会先评估问题是否真的需要分布式锁：数据库唯一约束、乐观锁、幂等能解决的就不上 Redis 锁。确需 Redis 锁时，用 NX + TTL + owner 标识 + Lua 安全释放 + 续期；Redis 不可用时核心写操作 fail closed，而不是绕过锁。

## 常见追问【P2】

- **可重入**：Redisson 提供可重入锁；手写需要维护重入计数。
- **获取锁超时 / 等待**：避免无限等待，设置 tryLock 超时。
- **主从切换丢锁**：锁写在 master，故障转移后新 master 可能没有该锁，出现两个客户端同时持锁。工程上通常用幂等/fencing 思路兜底；Redlock 的争论不在本知识库 P0 范围（见 P2 止损）。

以上属于 P2 深度，面试给出结论性回答即可。
