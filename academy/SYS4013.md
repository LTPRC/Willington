# GoPay Onboarding 到底是什么系统

GoPay 这里指 PayPal China 的 RMB Repatriation（RR）Onboarding。业务背景是 PayPal Singapore（内部常称 C2）的中国商户或个人卖家，需要进入 GoPay China / PPCN（C3）体系，完成中国本地的身份与合规审核，之后才能使用境内人民币相关的收款、提现能力。

如果只看页面，它很像一个注册流程：填企业信息、填法人、填受益所有人、上传证件、提交审核。但从后端角度看，它其实是一个很典型的 **long-running stateful workflow**。一次 onboarding 会跨越多个页面、多个服务、多个第三方 Vendor 和人工审核系统，整个过程可能持续很久；部分检查同步返回，部分检查异步返回，还有结果可能失败、超时、重复甚至永远不回来。系统真正要解决的不是“怎么把表单存进数据库”，而是这些不确定事件最终怎样可靠地收敛到一个确定、可审计、可恢复的业务状态。

```text
PayPal Singapore / C2 Merchant
             │
             │ Consent + SSO
             ▼
       GoPay China / C3
             │
             ▼
      Onboarding Portal
             │
   ┌─────────┴──────────┐
   │                    │
Business              Individual
   │                    │
BE → LR → PAU/BO        │
   └─────────┬──────────┘
             ▼
          Submit KYC
             │
      Sync + Async Checks
             │
         processKYC
             │
      Auto Decision Layer
       /       |        \
    PASS      FAIL     Manual Review
                         │
                   PASS/DCLN/RTND
```

我在这个项目里的职责边界要一直记清楚：我是核心开发，参与 LLD，重点做过自动 KYC 决策和状态机相关实现，也参与过 API 契约层面的字段、message schema、错误码等设计和 review。整个 GoPay 不是我一个人设计的，gRPC/Protobuf 等底层基础设施也不是我从零搭的。系统设计面试里可以深入讲自己真正做过的部分，但不要把团队系统能力变成个人 ownership。

# 为什么 Onboarding 要做成状态机

企业商户不是一次请求就能完成 onboarding。用户可能今天填完企业信息，明天才继续法人信息；某一步可能因为校验失败被挡住，也可能在人工审核后被 Return To User，修改资料再重新提交。如果只在数据库里放几个 `isFinished`、`isReviewed` 之类的布尔字段，很快就会出现大量非法组合，而且不同 API 很难判断当前到底允不允许执行。

GoPay 因此把流程显式建模成状态。Business 路径可以概括为：

```text
INIT
  │ submit business entity
  ▼
BUEN / BUSINESS_INFO
  │ submit legal representative
  ▼
LERP / LEGAL_REPRESENTATIVE
  │ optional PAU / BO collection
  ▼
PAUR / BEOF
  │ submit KYC
  ▼
SBMT / SUBMITTED
  │
  ├──────────► PASS
  ├──────────► DCLN
  └──────────► RTND ─────► 修改资料后重新提交
```

Individual 路径短得多，大体是 `INIT → SBMT → PASS / DCLN / RTND`。这里最关键的不是背缩写，而是理解状态机承担了几件事：它限制步骤顺序，防止用户跳过必要信息；让后端知道某个 API 在当前状态是否合法；让前端能够根据状态恢复到正确页面；也给人工审核、重提和审计提供了统一语义。

状态机还有一个很容易被忽略的价值：**业务状态本身就是并发控制的一部分**。例如账户已经进入 `SBMT` 后，再次执行同一类 submit 操作就不应该被当成一次全新的业务。真正可靠的幂等通常不是只靠一个 requestId，而是业务唯一键、当前状态和原子更新共同决定“这个操作现在还能不能发生”。

# Draft 和 Main：审核中的数据不能直接当正式数据

Onboarding 阶段的数据天然是不稳定的。用户可能只填了一半，也可能被人工审核退回后修改；最终甚至可能被拒绝。如果每次填写都直接覆盖正式 Party 数据，那么“用户当前填写的内容”和“已经通过审核的正式内容”就混在一起了，后续很难回答一个简单的问题：**现在系统里哪一份才是经过 KYC 确认的事实？**

GoPay 使用 Draft/Main 的思路隔离这两类数据。Onboarding 期间的信息进入 `PARTY_KYC_DRAFT` 等草稿结构，KYC 通过后才执行 Apply Draft to Main，把审核后的内容正式化到 `PARTY`、`MERCHANT_ADDL_INFO`、`PERSON_ADDL_INFO` 等正式数据中。

```text
User Input / Vendor Result
           │
           ▼
     PARTY_KYC_DRAFT
           │
      可修改 / 可退回
           │
       KYC PASS
           ▼
   Apply Draft to Main
           │
    ┌──────┼────────┐
    ▼      ▼        ▼
 PARTY  MERCHANT  PERSON...
```

这种模式的本质不是“多建一张表”，而是把 **mutable onboarding state** 和 **approved source of truth** 分开。类似思路也常见于内容发布、合同审批、配置变更：只要业务存在“编辑中的版本”和“已生效版本”，Draft/Main 都是值得考虑的模型。

它的代价也很现实。两套数据意味着字段演进要同步考虑，Apply Draft 逻辑要保证完整性，人工审核还需要看到正确版本。如果未来业务允许一个用户同时存在多次修改，甚至还要进一步引入 version，而不能只靠一份 Draft。

# KYC 为什么天然是一个异步编排问题

GoPay 的 KYC 不是调用一个接口得到 true/false。不同检查负责不同维度，例如工商信息、OCR、身份核验、MCC、行政处罚、风险与合规、URL、Liveness、Pinyin 等。历史材料里不同版本出现过不同的检查数量，所以长期知识库里不要机械背“9 个”“11 个”或“12 个”；准确的说法是系统会聚合多个 KYC / Risk 检查维度。

原始设计里能看到 Qixinbao、Tencent OCR、eKYC Vendor、RCL/CRR、MCC、Administrative Punishment、URL Check 等能力。它们的调用模型也不同：有的适合同步完成，有的需要异步等待结果。于是整个 KYC 最核心的工程问题变成了：**这些结果什么时候算齐？谁有权做最终决策？如果它们乱序回来怎么办？**

如果每个 callback 收到结果后直接自己修改 KYC 最终状态，系统会迅速变得不可控。RCL callback 可能认为应该 PASS，而 URL result 几毫秒后又发现需要人工；两个线程还可能同时创建 case、发送事件。更合理的方式是让 callback 只负责持久化“新事实”，然后统一进入一个决策收敛点。

```text
RCL Result -----------┐
                      │
URL Result -----------┼────► processKYC(accountId)
                      │             │
24H Timeout Batch ----┘             ▼
                              Read Current Facts
                                     │
                                     ▼
                              Auto KYC Decision
```

这就是 GoPay `processKYC()` 最值得记住的地方。它把“某个检查刚刚返回了什么”转换成“基于当前所有已知事实，现在是否已经足够做最终决定”。这种 **fan-in / convergence point** 的思路比某个具体框架更重要，在订单聚合、风控、多渠道支付、异步任务编排里都能复用。

# 自动决策和副作用为什么要分开

从现有材料看，`processKYC()` 负责汇聚状态并推动后续流程，而 `makeAutoKycDecision()` 一类逻辑承担的是根据当前检查结果计算 decision。长期理解上，可以把它们看成两个不同职责：一个处理 orchestration、事务、幂等和 side effect；另一个尽量只关心“这些检查结果意味着什么”。

不要把这里过度包装成严格意义上的函数式编程 pure function，因为目前没有必要证明实现绝对没有读取时间、配置或其他依赖。真正值得保留的是 **decision calculation 与 side effect 分离** 这个设计思想。这样规则变化更容易 review 和测试，调用方也更容易控制“什么时候真正写状态、建人工 case、发事件”。

业务上可以抽象出几类结果：检查明确通过时进入 PASS；出现明确拒绝条件时可能 FAIL；自动系统无法可靠判断时进入人工审核；异步结果尚未齐全、又仍在允许等待窗口内时，则可以把它理解成一种抽象的 WAIT/PENDING 状态——它不是最终业务结论，只表示“现在还不能决定”。

这里要特别区分“项目事实”和“便于理解的抽象”。现有原始材料能确认 `auto_kyc_decision`、异步 callback、`processKYC()` 和 24 小时 timeout；历史备战资料把 WAIT 进一步抽象成显式 decision。复习时可以用 WAIT 帮助理解，但如果面试官追问源码 enum，不要在没有代码证据时把它说死。

# 多个异步触发同时到来，为什么一个 null-check 不够

RCL 和 URL result 完全可能接近同时返回，timeout batch 也可能恰好在同一时间触发。于是同一个 account 会有多个线程同时进入 `processKYC()`。原始材料可以确认 callback 在 `auto_kyc_decision == null` 时持久化结果并继续调用 `processKYC()`，也可以确认 timeout batch 使用同一个 decision 字段作为筛选条件。

但只写下面这种代码并不能解决并发问题：

```java
if (autoKycDecision == null) {
    autoKycDecision = makeDecision();
    save();
}
```

两个线程可能同时读到 null，然后都做 decision 和副作用。这是典型的 check-then-act race。可靠实现需要把“检查尚未决策”和“写入第一次决策”放进同一个原子并发控制边界。可以使用数据库悲观锁、条件更新/CAS、唯一约束或其他能够保证 single winner 的机制。

历史备战资料将 GoPay 的具体实现还原为 `SELECT ... FOR UPDATE + auto_kyc_decision null-check`。这个方案在逻辑上成立：同一 account 的并发线程先串行化，后进入者拿到锁后重新读取状态，发现 decision 已经存在就直接返回。不过当前手头原始 LLD 对 `auto_kyc_decision` 有直接证据，对具体 `SELECT FOR UPDATE` 代码还需要继续用源码确认，所以长期笔记里把它记成 **“当前还原方案，具体代码待确认”**，不要把推测升级成亲手验证过的事实。

如果今天重新设计，也可以考虑条件更新：

```sql
UPDATE party
SET auto_kyc_decision = ?
WHERE account_id = ?
  AND auto_kyc_decision IS NULL;
```

受影响行数为 1 的线程赢得 decision ownership，0 行则说明其他线程已经完成。悲观锁和 CAS 没有绝对优劣，要看临界区复杂度、冲突概率、数据库访问模式和后续副作用怎么组织。

# 24 小时 Deadline：异步系统不能相信 callback 一定回来

异步系统最危险的假设之一是“对方迟早会回调”。现实里消息可能丢失，Vendor 可能故障，callback consumer 也可能失败。如果系统没有 deadline，一个账户就可能永远停在 `SBMT`，而且因为它不是明显报错，反而很容易长期没人发现。

GoPay 对这一点有非常具体的设计。提交 KYC 时记录 `time_kyc_submitted`，并增加 `auto_kyc_decision` 字段；XX-job 每 10 分钟扫描满足下面条件的账户：

```text
kyc_status = SBMT
AND auto_kyc_decision IS NULL
AND time_kyc_submitted 已超过 24H
```

找到以后再次调用 `processKYC()`，让同一个统一决策入口处理 timeout 场景，而不是在 batch 里重新写一套业务规则。这里体现了一个很好的原则：**触发机制可以有很多种，业务决策入口尽量只有一个。**

```text
normal callback ─────┐
                     ├──► processKYC
24H timeout batch ───┘
```

原始 LLD 还明确提到，如果未来用户量增长，可以考虑用 RabbitMQ 处理 24H timeout、降低 batch scan 的压力。所以真实历史方案是 **10 分钟 batch + DB scan**；RabbitMQ timeout 是 future consideration。Temporal/Conductor 之类 durable timer 则属于今天重新设计时可以评估的方案，不是 GoPay 当时已经采用或原 LLD 明确提出的方案。

这也说明定时扫描并不天然“低级”。如果业务量适中、deadline 是 24 小时而不是 100 毫秒，十分钟级扫描已经足够满足业务语义，简单方案的开发和运维成本反而更低。系统设计不是组件越多越高级，而是复杂度要和真实约束匹配。

# Auto Decision 和 Manual Review 是两层决策

自动系统只应该在证据足够时自动做结论。合规场景尤其不能因为 Vendor 超时就把结果默认成 PASS，否则技术降级会直接变成业务风险。GoPay 因此把自动决策和人工审核做成两层。

```text
KYC Checks
    │
    ▼
Auto Decision
 ┌──┼─────────────┐
 │  │             │
PASS FAIL   NEED_MANUAL_REVIEW
                  │
                  ▼
              CSP / Ops
             /    |     \
          PASS   DCLN   RTND
```

人工审核里的 RTND（Return To User）很有代表性。它不是最终失败，而是“资料存在可修正问题”。原始流程里 RTND 会把 KYC 状态改成 RTND，并把 `auto_kyc_decision` 清回 null，通知用户修改后重新提交。也就是说，这个状态机不是简单的一次性 DAG，而是允许形成业务循环。

这类 human-in-the-loop 设计的意义在于：自动化系统负责处理确定性强、规则明确的部分；人工系统负责不确定、异常和需要判断的部分。自动化率不是越高越好，尤其在支付、合规、风控里，**正确地把不确定性暴露出来**往往比强行给出结论更重要。

# PASS 以后并没有结束

KYC PASS 只是“审核通过”，并不等于整个 onboarding 已经完成。原始流程里 PASS 后还会涉及 Phone / National ID Mapping、Apply Draft to Main、通知 RCL、发布 `KycStatusChangeEvent` 和 `OnboardingFinishEvent`。之后 `finishOnboardingFlow` 再继续处理 C2/C3 的 GI Binding、Account OPEN 和通知等动作。

```text
KYC PASS
   │
   ├─ Phone / National ID Mapping
   ├─ Apply Draft to Main
   ├─ Notify RCL
   ├─ KycStatusChangeEvent
   └─ OnboardingFinishEvent
             │
             ▼
      finishOnboardingFlow
             │
       ┌─────┼──────────┐
       ▼     ▼          ▼
 GI Binding  OPEN   Email/SMS/Web
```

不同历史整理材料对 PASS 内部某些动作的精确先后顺序曾有不一致，因此长期复习时更应该掌握 **事务边界和依赖关系**，而不是死背每一步序号。原始 LLD 的 PASS sequence 明确显示 Phone Mapping 在 Apply Draft to Main 之前，这一点也引出了下面一个非常真实的分布式一致性问题。

# Phone Management：本地事务无法回滚远程副作用

Phone Management 是这个项目里最适合用来理解分布式一致性的真实案例之一。`kycReviewOnComplete` 的本地数据库更新可以放在事务里，但流程中还会调用外部服务 Reserve National ID - Phone Mapping。远程系统一旦已经成功，本地数据库后续再发生异常并 rollback，数据库事务并不能穿越网络把远端操作一起撤销。

```text
Local Transaction
      │
      ├── update local KYC state
      │
      ├── RPC: reserve phone mapping ─────► SUCCESS
      │
      ├── later local operation
      │           │
      │           └── EXCEPTION
      ▼
   DB ROLLBACK

最终可能出现：
Local KYC 没成功，但 Remote Phone Mapping 已成功
```

这比一句“分布式事务很难”更具体。问题本质是 **local ACID boundary 和 remote side effect boundary 不一致**。远程调用不是数据库语句，本地 rollback 对它没有任何魔法作用。

GoPay 的实际材料没有显示这里强行引入 XA 或复杂 Saga，而是承认这种 middle state 的可能性，通过 Grafana alert 暴露 `kycReviewOnComplete` 异常，再由 PD 排查和修复。这种设计看起来不够“自动化”，但它是现实系统里很常见的 trade-off：如果异常概率低、业务量可控、人工修复成本可以接受，那么“可观测 + 可修复”可能比建设一套复杂补偿框架更经济。

如果规模和故障成本上升，今天重新设计时可以考虑把跨服务副作用进一步事件化，配合 Outbox、幂等 worker 和 reconciliation。但 Outbox 也不是分布式事务魔法：它主要解决 **本地 DB 状态已经提交，但事件可能没有可靠发布** 的窗口；远端业务执行以后仍然需要幂等、重试和必要的对账/补偿。

# Timeout 不等于 Failure，所以 Retry 必须和 Idempotency 一起设计

调用第三方服务时，timeout 只能说明“调用方没有在 deadline 内拿到结果”，并不能证明远端没有执行。网络可能在响应阶段丢包，也可能远端已经完成业务但调用方超时。如果这种操作带副作用，调用方看到 timeout 就直接重试，可能把一次业务执行两遍。

所以可靠的 Retry 一定要先回答几个问题：操作是否幂等？失败属于瞬时网络问题还是业务拒绝？重试是否会把已经过载的 Vendor 再压一遍？能不能先查询最终状态？

对于纯查询，有限次数重试通常风险较小；对于创建、扣款、注册、状态迁移等有副作用操作，应该有稳定的 business id / idempotency key，让服务端能够识别“这是同一件事的再次尝试”。重试本身还应该有 backoff 和 jitter，避免大量请求同时失败后又在同一时间重试形成 retry storm。

```text
Timeout
  │
  ├─ Read-only / Idempotent ? ──► bounded retry
  │                               + backoff
  │                               + jitter
  │
  └─ Side Effect / Unknown Outcome
                  │
                  ├─ query status if possible
                  ├─ stable idempotency key
                  └─ retry only when safe
```

Retry Budget 也是一个有用的概念。假设正常请求已经把下游打到容量边缘，如果每个失败请求再自动重试三次，相当于故障时主动制造更多流量。可以限制“额外重试请求占正常流量的比例”，让 retry 成为恢复手段而不是故障放大器。

# Circuit Breaker 和 Bulkhead 解决的是不同问题

第三方持续故障时，继续每个请求都等到 timeout 会浪费线程、连接和用户时间。Circuit Breaker 的目标是当失败率或慢调用持续超过阈值时，暂时停止真实调用，快速失败或进入业务 fallback，过一段时间再试探性恢复。它保护的是 **不要反复调用一个已经明显不健康的依赖**。

Bulkhead 解决的是另一件事：即使某个 Vendor 很慢，也不能让它把整个服务的线程池、连接池或并发额度耗尽。可以为不同 Vendor 使用独立 client pool / concurrency limit，或者至少保证一个依赖的排队不会吞掉全局资源。它保护的是 **故障隔离和 blast radius**。

```text
                     gopay-merchant-serv
                       /      |       \
                      /       |        \
              Vendor A    Vendor B    Vendor C
              Pool A      Pool B      Pool C
                │           │           │
             timeout     timeout     timeout
             breaker     breaker     breaker
```

是否使用 Hystrix/Resilience4j 或某个具体库是实现细节。系统设计里先讲清楚 timeout、retry、breaker、bulkhead、fallback 各自解决什么问题，比背框架注解更重要。

# KYC 的降级不能改变业务语义

普通推荐系统挂了可以返回热门列表，但 KYC 服务挂了不能“为了可用性”默认审核通过。系统设计里的 degradation 必须守住业务安全边界。

GoPay 很自然的业务 fallback 是：自动系统拿不到足够证据时，不做确定性 PASS，而是等待异步结果，超过 deadline 后进入 Manual Review。换句话说，可用性并不等于“任何情况下都返回成功”，而是系统在依赖失败时仍然能够给业务一个 **安全、可解释、可继续处理** 的结果。

这个原则在支付、风控、权限和安全系统里都适用。降级之前首先要问：这个功能失败时，fail-open 还是 fail-closed？错误地提高可用性，有时会直接破坏系统最重要的业务约束。

# MQ 可靠性：先分清 Producer、Broker、Consumer 三段

GoPay 确实使用 RabbitMQ 发布状态变化和 OnboardingFinish 等事件，但现有材料不足以证明所有 producer 都采用了哪一种 publisher confirm / retry 配置，因此不要把某个具体 MQ 可靠性实现说成历史事实。长期需要掌握的是消息可靠性问题本身。

一次异步消息至少有三个边界：Producer 是否真的把消息交给 Broker；Broker 是否可靠保存；Consumer 业务处理成功以后是否正确 ack。只说“用了 MQ”并不能保证可靠。

```text
Producer
   │  publish
   ▼
Broker
   │  deliver / redeliver
   ▼
Consumer
   │
   ├─ business DB commit
   └─ ACK
```

在 at-least-once 语义下，重复投递是正常现象，所以 consumer 必须能够幂等。反过来，如果 consumer 在业务提交之前先 ack，进程随后崩溃，就可能真正丢业务。实际设计通常让 ack 跟随业务成功，同时接受“业务成功但 ack 丢失 → redelivery”这个窗口，再用幂等消化重复。

如果本地 DB 更新和事件发布必须保持最终一致，Transactional Outbox 是一个常见设计：业务状态和 outbox row 在同一个本地事务里提交，后台 worker 再可靠发布 outbox。这样不会出现“DB 已提交，但应用在 publish 前崩溃导致事件永远没发”的不可恢复窗口。不过 outbox 仍需要处理重复 publish，consumer 仍然需要幂等。

# 如果消息突然大量积压，先找生产消费速率差

MQ backlog 的本质通常是：

```text
produce rate > consume rate
```

排查时先确认是所有 queue 都积压还是某个 queue/partition/consumer group；再看生产速率是否突然增加、consumer 实例是否减少、单条消息处理时间是否变长、下游 DB/Vendor 是否拖慢 consumer。很多时候 MQ 只是症状，真正瓶颈在 consumer 后面的数据库或 RPC。

短期止血可以扩 consumer、降低非核心生产流量、暂停高成本任务，但前提是下游还有容量。如果数据库已经满负载，盲目增加 consumer 只会让数据库更快崩掉。还要观察 oldest message age，而不只是 queue depth：一百万条每秒可处理十万条的 backlog 和一万条已经积压两小时的 backlog，业务严重程度完全不同。

# 线上接口突然变慢，先判断 Blast Radius

线上排障最忌讳一上来就猜“是不是 GC”或者“是不是数据库索引”。第一步应该先回答故障范围：一个接口慢，还是整个服务慢？只有某个租户/商户慢，还是所有请求都慢？错误率升高还是单纯 latency 上升？是从某次发布后开始，还是随着流量逐渐恶化？

一个稳定的排查顺序可以记成：

```text
Impact / Blast Radius
        ↓
Recent Change
        ↓
Golden Signals
        ↓
Trace / Dependency
        ↓
Resource Saturation
        ↓
Mitigation
        ↓
Root Cause + Prevention
```

Golden Signals 可以看 latency、traffic、errors、saturation。Latency 不要只看平均值，平均 100ms 完全可能掩盖一批 10 秒请求，P95/P99 更容易暴露 tail latency。Saturation 则看 CPU、heap/GC、线程池 queue、DB connection pool、HTTP client pool 等资源是不是已经接近上限。

GoPay 这种多 Vendor 系统尤其适合用 trace 分解延迟：请求到底花在本地计算、DB、queue wait，还是某个外部 KYC provider。如果某个 Vendor P99 从 1 秒变成 20 秒，而应用 thread pool 又没有隔离，很快就可能从“一个依赖变慢”扩散成“整个 onboarding API 都慢”。

# 线程池堆积不是“线程不够”，而是吞吐失衡

线程池 queue 持续增长意味着任务进入速度大于完成速度。最常见的错误反应是立即把线程数调大，但如果线程都在等同一个慢 Vendor 或等数据库连接，更多线程只会制造更多并发，把下游压得更严重。

排查时要同时看 active threads、queue size、task latency 和线程栈。如果大量线程停在 HTTP client read、DB connection acquire 或某个锁上，真正问题就在那个等待点。只有确认任务本身 CPU 可并行、下游也有容量时，增加线程才可能提高吞吐。

这里可以用 Little's Law 建立直觉：系统内平均并发量大约等于吞吐率乘平均停留时间。外部调用从 200ms 变成 5s，即使 QPS 不变，为维持同样吞吐所需要占用的并发资源也会急剧增加，所以慢依赖很容易转化为 thread/connection exhaustion。

# DB 变慢时，不要只会说“加索引”

数据库问题首先要判断是单条 SQL 变慢还是整个数据库都变慢。如果只有某个 query，可以看 execution plan、扫描行数、索引选择、排序/临时表和数据量变化；如果整个库都慢，则还要看 CPU、IO、连接数、lock wait、长事务和 buffer pool 等。

应用侧也不能忽略。DB connection pool 被占满时，用户看到的是 API latency 上升，但真正的等待可能发生在“获取连接”而不是 SQL 执行。一个慢事务持有锁，也可能让大量本来很快的请求排队。

GoPay 的 24H batch 还提供了一个很具体的设计点：为了扫描 `kyc_status = SBMT` 的账户，原始 LLD 明确给 PARTY 的 `kyc_status` 增加了索引。Batch scan 不是“写个定时任务就完了”，查询条件、索引、扫描频率和数据规模都要一起设计，否则一个用于兜底的任务本身也可能成为数据库负担。

# CPU 100% 怎么定位

Java 服务 CPU 打满时，目标是从“哪个进程”一路定位到“哪个线程、哪段调用栈”。常见做法是先确认 Java process，再找到高 CPU thread，把 OS/native thread id 映射到 JVM thread dump，观察对应线程正在执行什么。

```text
Host CPU high
   ↓
Java process?
   ↓
High CPU thread
   ↓
native tid ↔ JVM thread
   ↓
Thread Dump / stack
   ↓
hot loop / serialization / regex / lock spin / GC ...
```

同时必须看 GC，因为高 CPU 可能不是业务线程，而是 JVM 正在频繁回收。排障时不要只采一份 thread dump，连续采样几次更容易区分“刚好采到”与“持续卡在这里”。

# OOM 先看是哪一种 OOM

“Java OOM”不是一个单一故障。`Java heap space`、Metaspace、Direct Buffer Memory、`unable to create new native thread` 的原因和排查方法完全不同。Heap OOM 才重点看 heap dump、Dominator Tree、GC Root 和对象 retained size；native thread OOM 反而更可能是线程数量、线程栈和系统资源问题。

Heap OOM 的排查思路通常是：先看 heap 使用趋势和 GC 是否还能回收，再获取 heap dump，用 MAT 一类工具找 retained size 最大的对象以及为什么它仍被 GC Root 引用。最后还要区分是真正 memory leak，还是业务流量/缓存容量增长导致 heap 本来就配置不足。

# 一次线上事故怎么讲得像 Senior

系统设计面试经常把项目问题变成：“线上出了这个故障你怎么处理？”一个成熟回答不应该只讲最终 root cause，而应该体现从影响控制到长期预防的全过程。

可以自然按下面的顺序组织：

```text
Impact
  ↓
Detection
  ↓
Mitigation / Stop the bleeding
  ↓
Root Cause
  ↓
Permanent Fix
  ↓
Prevention
```

例如 Vendor latency 暴涨，先确认影响了哪些 API 和多少请求；通过 metrics/trace 发现外部依赖延迟；短期用 timeout、限流、breaker 或人工审核 fallback 保护主系统；再分析 Vendor 或自身 client pool 的根因；长期补隔离、容量、告警和 failure drill。Senior 的区别不在于“会不会看日志”，而在于能不能控制 blast radius、明确 trade-off，并让同类故障下一次更容易发现、更容易恢复。

# Observability 应该围绕业务状态，而不只是 JVM

GoPay 这类长流程系统如果只监控 CPU、memory 和 error rate 是不够的。服务完全可能“技术上没报错”，但大量账户已经卡在 `SBMT` 两天，这仍然是严重故障。

因此监控至少要分两层。技术层看 API latency/error、JVM、线程池、DB pool、MQ backlog、Vendor success rate 和 Vendor P95/P99；业务层看不同 KYC 状态的数量、SBMT age、自动 PASS/FAIL/Manual 的比例、timeout account 数、RTND 数，以及是否存在异常中间态。真正有价值的告警往往是两层结合，例如：

```text
SBMT age > expected window
AND auto_kyc_decision IS NULL
```

或者：

```text
Phone Mapping succeeded
BUT local onboarding state inconsistent
```

日志则应该能用 accountId / payerId / traceId 把一次 onboarding 的跨服务调用串起来。合规系统还要注意敏感信息不能为了排障直接明文打进日志，observability 和 data protection 必须一起设计。

# 系统设计题里怎么估算 GoPay 的容量

项目历史材料没有可靠的 QPS、DAU、P99 等数字，所以不能为了面试效果虚构。但如果面试官把它改造成 system design case，可以明确告诉对方：“我先不引用历史生产数字，我们按假设规模估算。”然后从 daily onboarding、峰值倍数、每个 onboarding 触发多少次 API / Vendor call / MQ event 推导流量。

例如假设每天有 N 个新 onboarding，峰值集中在若干小时，那么用户填写阶段的 QPS 通常并不会像广告系统那样夸张；真正要关注的可能反而是第三方 SLA、异步 backlog、数据库状态扫描和人工审核容量。系统设计的容量规划应该由业务 workload 决定，而不是默认所有系统都需要百万 QPS。

这也是 GoPay 很适合面试的原因：它提醒我们 **复杂系统不等于高 QPS 系统**。状态、一致性、失败恢复、合规和跨系统协作，同样可以构成很深的系统设计问题。

# 如果今天重新设计这套系统

如果业务规模和流程复杂度维持原水平，我不会为了“架构现代化”把所有东西重写。显式状态机、统一 `processKYC` 收敛、Draft/Main、24H deadline、Manual Review 这些核心思想仍然成立。

真正可能演进的是几个局部。第一，timeout account 数量大到 DB scan 成本明显时，可以从 batch scan 演进到 durable timer / delayed message，但要考虑 timer 的可靠持久化、重复触发和恢复；原始 LLD 自己首先提出的是 RabbitMQ 方向。第二，DB 状态变化和异步事件之间如果要求更强的最终一致，可以引入 Transactional Outbox。第三，Phone Management 这类跨服务副作用如果中间态越来越多，可以增加自动 reconciliation，而不是长期完全依赖人工。第四，对 Vendor 增加更系统的 timeout、retry budget、breaker、bulkhead 和 per-provider observability。

如果流程继续扩张到几十个状态、更多国家/tenant、更多人工节点和 timer，才值得认真评估 Temporal / Conductor 一类 workflow engine。引入 workflow engine 的理由应该是“durable execution、timer、retry、history、workflow visibility 的复杂度已经值得平台化”，而不是因为状态机看起来不够高级。

# 这个项目能沉淀出的系统设计方法

GoPay 最值得长期留下来的不是某个内部 API 名字，而是几条可以迁移到其他系统的思路。

一个长流程先把业务状态建模清楚，再谈接口；可修改数据和正式数据最好有明确边界；异步结果不要让每个 callback 自己决定终态，而要汇聚到统一 convergence point；异步系统必须有 deadline，因为 callback 永远可能不回来；幂等不能只靠“先查一下”，check 和 update 需要原子性；本地事务无法回滚远程副作用，所以跨服务一致性最终要依赖幂等、事件、补偿或 reconciliation；第三方故障的降级不能破坏核心业务语义；监控也不能只看机器健康，要监控业务状态是否真正向终态收敛。

把这些原则串起来，可以得到一条比较完整的系统设计思路：

```text
Business Invariant
      ↓
State Model
      ↓
Data Ownership / Draft vs Main
      ↓
Sync vs Async Boundary
      ↓
Convergence Point
      ↓
Idempotency / Concurrency
      ↓
Deadline / Recovery
      ↓
External Side Effects
      ↓
Observability / Reconciliation
      ↓
Scale only where needed
```

这条链比背一个“系统设计八股模板”更有用。遇到订单、支付、审批、风控、合规、工作流类系统时，很多问题都会重新落回这些基本约束。

# Appendix：事实边界和待确认项

这部分不是正文知识，而是为了防止以后复习久了，把“合理推导”误记成“项目事实”。

**KYC 检查数量**在不同历史材料中出现过 9、11、12 等口径，可能来自版本、子检查拆分方式和 Business/Individual 差异。长期统一说“多个/十余个检查维度”，除非当场明确自己的计数口径。

**WAIT** 可以稳定理解成“结果没齐且仍在 deadline 内，因此暂不形成最终 decision”的抽象业务状态；目前不要无证据坚持它一定是源码中的正式 enum。

**`SELECT FOR UPDATE`** 是现有备战资料还原出的并发控制实现，逻辑合理，但具体代码仍待原始源码/LLD 进一步确认。已经能确认的是多个 trigger 会汇聚 `processKYC`，并使用 `auto_kyc_decision` 判断是否已经完成自动决策。

**RabbitMQ publisher confirm / retry** 属于应该掌握的 MQ 可靠性知识，但现有材料不足以把具体配置说成 GoPay 已确认历史实现。GoPay 可以确认使用 RabbitMQ/event；24H timeout 的实际实现是 batch，RabbitMQ 是原 LLD 的 future consideration。

**Phone Management** 的正确一致性案例是：远程 Phone Mapping 可能已经成功，而后续本地操作异常导致本地事务 rollback，从而出现远端成功、本地失败的 middle state。不要再讲成“DB 已 commit 后调用 user-serv 失败”。

**PASS 内部精确顺序**历史整理曾有差异。原始 LLD sequence 支持 `KYC PASS → Phone Mapping → Apply Draft to Main → events`；长期更应该记住依赖和事务边界，不必为了面试死背全部步骤序号。

**历史用户迁移**不要描述成“我把所有 PayPal China 老用户 100% 批量迁移”。现有校准口径更接近新平台承接新的 C2 onboarding / migration flow，而不是传统意义的全量历史数据搬迁。

**项目规模数字**没有可靠原始证据时不使用。系统设计题需要容量估算，可以现场声明假设后计算，但不要把假设包装成生产事实。
