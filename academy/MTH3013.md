## O(1) 的 set / get / setAll<img src="./icons/microsoft.gif" />

**LeetCode：无完全一致题。**

### 题目

设计一个 Key-Value 数据结构：

```java
void set(K key, V value);
V get(K key);
void setAll(V value);
```

`setAll(v)` 把当前已经存在的所有 key 的值统一修改成 `v`。之后如果某个 key 又被单独 `set`，则以新的值为准。要求三个操作平均都为 O(1)。

### 思路

不要真正遍历整个 Map。每个 key 记录自己的 value 和最后修改版本号；全局 `setAll` 也记录 value 和版本号。`get` 时比较两者的版本，谁更新得更晚就使用谁。

### 掌握程度：A 级

代码很短，而且是典型的数据结构设计题，建议能从空白编辑器基本手写。真正要记住的是：**单 Key 有自己的版本，全局 setAll 也有版本，get 时比较谁更新得更晚。**

### 伪代码

```text
状态：

每个 key 各自记两样东西：当前的值、最后一次被修改时的版本号。
全局也记两样东西：setAll 的值、setAll 发生时的版本号，初始版本号记为 -1。
另外维护一个只增不减的时钟，初始为 0。


set(key, value)：

    把时钟加一。
    把这个 key 的值记下来，版本号盖上当前时钟。


setAll(value)：

    把时钟加一。
    把全局值记下来，全局版本号盖上当前时钟。


get(key)：

    key 不存在，返回 null。
    key 自己的版本号比全局版本号大，说明它在最近一次 setAll 之后又被单独改过，返回它自己的值。
    否则返回全局值。
```

真正要记住的是：`set / setAll` 都只是在记录「谁最后更新」；`get` 再判断最后一次更新来自单 Key 还是全局 setAll。

### Java 答案

```java
import java.util.HashMap;
import java.util.Map;

public class SetAllMap<K, V> {
    private static class Entry<V> {
        V value;
        long version;

        Entry(V value, long version) {
            this.value = value;
            this.version = version;
        }
    }

    private final Map<K, Entry<V>> map = new HashMap<>();
    private long clock = 0;
    private V globalValue;
    private long globalVersion = -1;

    public void set(K key, V value) {
        map.put(key, new Entry<>(value, ++clock));
    }

    public V get(K key) {
        Entry<V> entry = map.get(key);
        if (entry == null) {
            return null;
        }
        return entry.version > globalVersion
                ? entry.value
                : globalValue;
    }

    public void setAll(V value) {
        globalValue = value;
        globalVersion = ++clock;
    }
}
```

复杂度：

```text
set     O(1) average
get     O(1) average
setAll  O(1)
space   O(n)
```

面试一句话：这是 Lazy Update。`setAll` 不真的批量更新，而是记录一次全局版本；读取时比较单 key 版本和全局版本。

## LRU Cache + TTL<img src="./icons/microsoft.gif" />

**LeetCode 基础题：LC 146 — LRU Cache。TTL 为工程扩展。**

### 题目

实现：

```java
V get(K key);
void put(K key, V value, long ttlMillis);
```

要求固定容量；命中后更新为最近使用；容量满时淘汰 Least Recently Used；每个 key 有独立 TTL，过期后 `get` 必须 miss；支持多线程；基础 `get / put` 平均 O(1)。

本题使用 **lazy expiration**：过期 entry 在被访问或正常 LRU 淘汰时删除。如果要求「过期后立即主动回收」，通常需要额外 Min-Heap / DelayQueue / background cleaner。

### 思路

标准结构是「HashMap（从 key 直接定位到链表节点）+ 双向链表（维护使用顺序）」。Node 增加 `expireAtNanos`。因为 `get()` 命中后要移动节点，所以它也是写操作。第一版直接用一把 `ReentrantLock` 保护 HashMap 和链表的一致性。

### 掌握程度：A 级

基础 LRU 要能手写，TTL 要能现场加上。不需要死背 `System.nanoTime()` 或 `TimeUnit.MILLISECONDS.toNanos()` 的拼写，但应该能把这几个逻辑从零写出来：`HashMap + 双向链表`、命中后移动到头部、超容量淘汰尾部、TTL 过期后删除，以及第一版用一把锁保护整体一致性。

### 伪代码

```text
数据结构：

一张 HashMap，从 key 直接找到它在链表里的节点。
节点除了 key、value，还带一个过期时间和前驱、后继两个指针。
链表用虚拟头节点和虚拟尾节点夹住：头部是最近使用，尾部是最久未使用。
再准备一把全局锁。


get(key)：

    加锁。
    key 不存在：解锁，返回 null。
    已经到了过期时间：把这个节点从链表和 Map 里删掉，解锁，返回 null。
    把节点挪到链表头部。
    解锁，返回它的 value。


put(key, value, ttl)：

    先算好过期时间：当前时间加上 ttl。
    加锁。
    key 已存在：更新 value 和过期时间，把节点挪到链表头部，解锁，返回。
    新建节点放进 Map，插到链表头部。
    超过容量：把链表尾部那个最久未使用的节点，从链表和 Map 里一起淘汰。
    解锁。


把节点挪到头部，就是先把它从链表里摘下来，再插到虚拟头节点后面。
```

并发 Follow-up 只需要能说清：`get()` 命中后也会修改 LRU 顺序，所以它不是纯读操作。最简单正确方案是一把锁保护 `map + linked list`。如果锁竞争太高，可以按 key hash 分 Segment，各自维护 LRU 和锁；代价是不再是严格全局 LRU，而是每个 Segment 内部的 LRU。

### Java 答案

```java
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class LruTtlCache<K, V> {
    private class Node {
        K key;
        V value;
        long expireAtNanos;
        Node prev;
        Node next;

        Node(K key, V value, long expireAtNanos) {
            this.key = key;
            this.value = value;
            this.expireAtNanos = expireAtNanos;
        }
    }

    private final int capacity;
    private final Map<K, Node> map = new HashMap<>();
    private final Node head = new Node(null, null, 0);
    private final Node tail = new Node(null, null, 0);
    private final ReentrantLock lock = new ReentrantLock();

    public LruTtlCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException();
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public V get(K key) {
        lock.lock();
        try {
            Node node = map.get(key);
            if (node == null) {
                return null;
            }

            if (System.nanoTime() >= node.expireAtNanos) {
                remove(node);
                map.remove(key);
                return null;
            }

            moveToHead(node);
            return node.value;
        } finally {
            lock.unlock();
        }
    }

    public void put(K key, V value, long ttlMillis) {
        if (ttlMillis <= 0) {
            throw new IllegalArgumentException();
        }

        long expireAt = System.nanoTime()
                + TimeUnit.MILLISECONDS.toNanos(ttlMillis);

        lock.lock();
        try {
            Node node = map.get(key);

            if (node != null) {
                node.value = value;
                node.expireAtNanos = expireAt;
                moveToHead(node);
                return;
            }

            node = new Node(key, value, expireAt);
            map.put(key, node);
            addToHead(node);

            if (map.size() > capacity) {
                Node victim = tail.prev;
                remove(victim);
                map.remove(victim.key);
            }
        } finally {
            lock.unlock();
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addToHead(node);
    }

    private void addToHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}
```

Follow-up：`get` 不能简单用 ReadLock，因为它会修改 recency。若一把锁 contention 太高，可以按 key hash 分 segment；代价是得到分片 LRU，而非严格全局 LRU。

## Per-Key Ordered Executor<img src="./icons/microsoft.gif" />

**LeetCode：无完全一致题。**

### 题目

实现：

```java
void submit(K key, Runnable task);
```

如果提交：

```text
A1, A2, B1, A3, B2
```

必须保证：

```text
A1 → A2 → A3
B1 → B2
```

同一个 key 严格按提交顺序执行，但不同 key 可以并行。不能直接用一个全局 `SingleThreadExecutor`。

### 思路

每个 key 维护一个自己的先进先出任务队列，外加一个「是否已经有人在跑」的标记；所有 key 共享底层线程池。同一个 key 同时只能有一条调度链在运行。

真正的 race 是：worker 发现 queue 空准备退出，同时另一个线程 submit 新任务。因此「确认 queue 空」和「清除 running 标记」必须在同一个临界区完成。

### 掌握程度：B 级

需要会写核心骨架，不要求背完整线程池 API。这道题真正考的是：同一个 Key 为什么必须串行、不同 Key 怎么并行、谁负责调度同 Key 的下一个任务，以及 Worker 退出与新 Submit 同时发生时会不会把任务永远留在队列里。

需要能写出「key → 串行队列」这张表，以及 submit() 和「取下一个任务」的主流程。底层线程池可以假设已经存在。

### 伪代码

```text
全局：

一个已经存在的普通共享线程池。
一张表：从 key 找到属于这个 key 的串行队列。


每个串行队列：

一个先进先出的任务队列。
一个「是否已经有调度链在跑」的标记。


submit(key, task)：

    找到这个 key 的串行队列，不存在就新建一个。
    把任务排到队尾。


入队的时候：

    锁住这个串行队列。
    任务进队尾。
    如果当前没有调度链在跑：把它标记为在跑，让共享线程池去执行「取下一个任务」。
    解锁。


取下一个任务：

    锁住这个串行队列。
    从队头取一个任务。
    队列已经空了：把「在跑」的标记清掉，解锁，退出。
    解锁，执行这个任务。
    不管任务成功还是失败，都让共享线程池再执行一次「取下一个任务」。
```

最关键的 Race Condition 是：Worker 看见队列空了准备退出，同时另一个线程 Submit 新任务。所以「确认队列为空」和「清除在跑标记」必须在同一把锁保护的临界区里完成。这样新任务要么被当前 Worker 看到，要么在标记清掉之后到达并重新启动调度链。

### Java 答案

```java
import java.util.ArrayDeque;
import java.util.Map;
import java.util.Queue;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.Executor;

public class PerKeyOrderedExecutor<K> {
    private final Executor backend;
    private final Map<K, SerialQueue> queues =
            new ConcurrentHashMap<>();

    public PerKeyOrderedExecutor(Executor backend) {
        this.backend = backend;
    }

    public void submit(K key, Runnable task) {
        if (key == null || task == null) {
            throw new IllegalArgumentException();
        }

        SerialQueue q = queues.computeIfAbsent(
                key, k -> new SerialQueue());
        q.enqueue(task);
    }

    private class SerialQueue {
        private final Queue<Runnable> tasks =
                new ArrayDeque<>();
        private boolean running = false;

        synchronized void enqueue(Runnable task) {
            tasks.offer(task);

            if (!running) {
                running = true;
                backend.execute(this::runNext);
            }
        }

        private void runNext() {
            Runnable task;

            synchronized (this) {
                task = tasks.poll();

                if (task == null) {
                    running = false;
                    return;
                }
            }

            try {
                task.run();
            } catch (Throwable t) {
                // 生产系统中记录日志和指标。
            } finally {
                backend.execute(this::runNext);
            }
        }
    }
}
```

这版为了聚焦 ordering，没有做 idle key cleanup。生产系统还要处理 hot key、bounded queue、backpressure、backend rejection、task timeout、durability，以及安全删除 idle key 的 race。

## Thread-Safe Token Bucket Rate Limiter<img src="./icons/microsoft.gif" />

**LeetCode：无完全一致题。相关热身：LC 362、LC 933。**

### 题目

实现线程安全的 Token Bucket：

```java
boolean tryAcquire();
boolean tryAcquire(int permits);
```

配置：

```text
capacity        桶最多存多少 token
refillRate      每秒补多少 token
```

初始化桶为满。每次请求先根据经过时间补充 token；足够则消费并返回 true，否则 false。并发调用不能超发。

### 思路

桶要记住四样状态：容量、每秒补充速率、当前 token 数、上次补充时间。一次「补充 → 判断 → 扣减」必须是原子状态转换。第一版直接用 `ReentrantLock`。用 `System.nanoTime()` 测 elapsed time，避免墙上时钟回拨。

### 掌握程度：B 级

会写核心状态和 `tryAcquire` 流程即可，不要求死背完整限流框架。需要真正理解：Token 会随着时间恢复，一次请求必须先补充、再判断、再扣减，这三个动作在并发下必须作为一个整体。

### 伪代码

```text
状态：

桶容量、每秒补充速率、当前 token 数、上次补充时间，外加一把锁。
初始化时桶是满的，记下当前的单调时钟。


tryAcquire(permits)：

    加锁。
    先补充 token：看距上次补充过了多久，按速率把 token 补上，但最多补到桶容量，然后更新上次补充时间。
    token 不够 permits：解锁，返回 false。
    否则扣掉 permits，解锁，返回 true。
```

为什么要加锁：如果两个线程同时看到只剩一个 token，在没有同步的情况下，它们都可能判断「够用」，最后一共发出两个 Permit。所以补充、判断、扣减必须原子化。第一版用 `synchronized` 或 `ReentrantLock` 都可以。

### Java 答案

```java
import java.util.concurrent.locks.ReentrantLock;

public class TokenBucket {
    private final double capacity;
    private final double refillPerSecond;

    private double tokens;
    private long lastRefillNanos;

    private final ReentrantLock lock =
            new ReentrantLock();

    public TokenBucket(double capacity,
                       double refillPerSecond) {
        if (capacity <= 0 || refillPerSecond <= 0) {
            throw new IllegalArgumentException();
        }

        this.capacity = capacity;
        this.refillPerSecond = refillPerSecond;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public boolean tryAcquire() {
        return tryAcquire(1);
    }

    public boolean tryAcquire(int permits) {
        if (permits <= 0) {
            throw new IllegalArgumentException();
        }

        lock.lock();
        try {
            refill();

            if (tokens < permits) {
                return false;
            }

            tokens -= permits;
            return true;
        } finally {
            lock.unlock();
        }
    }

    private void refill() {
        long now = System.nanoTime();

        double elapsedSeconds =
                (now - lastRefillNanos)
                / 1_000_000_000.0;

        tokens = Math.min(
                capacity,
                tokens + elapsedSeconds * refillPerSecond
        );

        lastRefillNanos = now;
    }
}
```

Distributed follow-up：如果要全局限流，单机锁不再够。可以讨论 Redis + Lua / server-side atomic operation，或者「本地快速限流 + 上层全局 quota」。核心 trade-off 是全局精确性、延迟与可用性。

## Producer-Consumer / Simple Fixed Thread Pool<img src="./icons/microsoft.gif" />

**LeetCode：无完全一致题。**

### 题目

不允许直接使用 `ExecutorService / ThreadPoolExecutor`，实现一个简化固定大小线程池：

```java
boolean submit(Runnable task);
void shutdown();
```

要求构造时创建固定 worker；所有 worker 从共享有界队列取任务；多个 producer 可以并发 submit；队列满时不能无限增长；一个 task 抛异常不能杀死 worker；shutdown 后拒绝新任务，并尽量处理已经入队的任务。

允许使用 `BlockingQueue`，因为本题重点是理解 Worker、Producer-Consumer、Backpressure、Shutdown 与 Exception Isolation，而不是重写 AQS。

### 掌握程度：C 级

理解设计和生命周期，不要求完整默写 Java Thread API。这道题不值得在冲刺期重新背一整套 `Thread`、`Runnable`、`BlockingQueue`、`interrupt` 的拼写。应该能清楚讲出：`submit` 把任务放进一个有界队列；固定数量 Worker 不断从队列取任务执行；队列满了必须有 Backpressure 策略；单个 Task 抛异常不能杀死 Worker；Shutdown 后拒绝新任务，并让已有任务尽量处理完。

### 伪代码

```text
初始化：

    建一个有界任务队列。
    起固定数量的 worker 线程，每个 worker 都执行同一个循环。


submit(task)：

    线程池已经 shutdown：直接拒绝。
    尝试把任务放进队列。
    队列已满：按策略处理——拒绝、阻塞、或让调用者自己执行，显式产生背压。
    否则返回成功。


worker 循环：

    只要线程池还没停，或者队列里还有没做完的任务：
        等着从队列里取一个任务，暂时取不到就继续等。
        执行这个任务；抛了异常只记录下来，不能让一个任务杀死整个 worker。


shutdown()：

    标记为停止。
    后续 submit 一律拒绝。
    唤醒正在等待的 worker。
    已经进了队列的任务尽量继续处理完。
```

真正需要能回答：为什么要有界队列；队列满了有哪些策略；Task 抛异常为什么不能杀死 Worker；为什么 Shutdown 不能粗暴杀掉所有线程。

### Java 答案

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.TimeUnit;

public class SimpleThreadPool {
    private final BlockingQueue<Runnable> queue;
    private final List<Thread> workers =
            new ArrayList<>();

    private volatile boolean stopped = false;

    public SimpleThreadPool(int workerCount,
                            int queueCapacity) {
        if (workerCount <= 0 || queueCapacity <= 0) {
            throw new IllegalArgumentException();
        }

        queue = new ArrayBlockingQueue<>(queueCapacity);

        for (int i = 0; i < workerCount; i++) {
            Thread worker = new Thread(
                    this::workerLoop,
                    "simple-pool-" + i
            );

            workers.add(worker);
            worker.start();
        }
    }

    public synchronized boolean submit(Runnable task) {
        if (task == null) {
            throw new IllegalArgumentException();
        }

        if (stopped) {
            return false;
        }

        // 队列满就拒绝，显式产生 backpressure。
        return queue.offer(task);
    }

    public synchronized void shutdown() {
        if (stopped) {
            return;
        }

        stopped = true;

        for (Thread worker : workers) {
            worker.interrupt();
        }
    }

    private void workerLoop() {
        while (!stopped || !queue.isEmpty()) {
            try {
                Runnable task =
                        queue.poll(200, TimeUnit.MILLISECONDS);

                if (task == null) {
                    continue;
                }

                try {
                    task.run();
                } catch (Throwable t) {
                    // 单个任务失败不能杀死 worker。
                }

            } catch (InterruptedException e) {
                if (stopped && queue.isEmpty()) {
                    return;
                }
            }
        }
    }
}
```

Follow-up：队列满时可以 Reject、Block Caller、Caller-Runs、Drop 或 Drop Oldest。没有唯一正确答案，要根据业务能否丢任务、caller 能否被阻塞，以及过载时想保护谁来决定。

## 40 亿个 uint32，1 GiB 内存，找出所有恰好出现两次的数字<img src="./icons/microsoft.gif" />

**LeetCode：无完全一致题。**

### 题目

有约 40 亿个 unsigned 32-bit integer，值域：

```text
0 ~ 2^32 - 1
```

可使用的额外数据内存约为：

```text
1 GiB = 2^30 bytes
```

找出所有**恰好出现两次**的数字。输入不能整体放进 HashMap。

### 思路

整个 `uint32` 值域有 `2^32` 种可能。我们不需要记录精确计数，只需要四种状态：

```text
00 = 0 次
01 = 1 次
10 = 2 次
11 = 3 次及以上
```

每个可能值只占 2 bits：

```text
2^32 × 2 bits
= 2^33 bits
= 2^30 bytes
= 1 GiB
```

更新规则：`00 → 01 → 10 → 11`，到 `11` 后保持不变。最后扫描整个值域，状态为 `10` 的就是答案。

### 掌握程度：C 级

重点是口述算法和空间计算，不要求默写完整 Java。这道题本质不是 Java API 题，而是先算值域，再算每个值最少需要多少 bit，最后判断能否放进内存。真正要会的是 2-bit 状态编码。

### 伪代码

```text
uint32 的完整值域一共 2^32 个可能值。

我们只关心四种状态，每种状态用两个 bit 表示：
    00 = 没出现；01 = 出现 1 次；10 = 恰好 2 次；11 = 3 次或更多。

总内存 = 2^32 个值 × 每个 2 bit = 2^33 bit = 2^30 byte，正好 1 GiB。
所以一张 2-bit 状态表就装得下。

扫描输入，每读到一个数：
    把它对应的状态往前推一格——没出现变 1 次，1 次变 2 次，2 次变 3 次及以上，到顶就保持不变。

扫完后遍历整个值域：
    状态停在「恰好 2 次」的数字，就是答案。
```

如果面试官严格说只有 `1 GB = 1,000,000,000 bytes`，完整 2-bit 值域放不下。此时把 `uint32` 值域按高位切成多个 Range，每一轮只给一个 Range 建表并重新扫描输入，用更多扫描次数换更低峰值内存。

### Java 概念答案

真实 JVM 中直接申请 1 GiB `byte[]` 还会有 JVM / 对象开销，因此严格总内存限制下更适合 mmap / off-heap 或 range partition。下面代码用于表达 2-bit table 的核心算法。

```java
import java.util.function.LongConsumer;

public class TwoBitFrequencyTable {
    // 每 byte 保存 4 个 uint32 的 2-bit 状态。
    private final byte[] states =
            new byte[1 << 30];

    public void add(long unsigned32) {
        if (unsigned32 < 0
                || unsigned32 > 0xFFFF_FFFFL) {
            throw new IllegalArgumentException();
        }

        int byteIndex = (int) (unsigned32 >>> 2);
        int shift = (int) ((unsigned32 & 0b11L) << 1);

        int b = states[byteIndex] & 0xFF;
        int current = (b >>> shift) & 0b11;
        int next = Math.min(3, current + 1);

        int mask = 0b11 << shift;
        b = (b & ~mask) | (next << shift);

        states[byteIndex] = (byte) b;
    }

    public void forEachExactlyTwice(
            LongConsumer consumer) {

        for (long value = 0;
             value <= 0xFFFF_FFFFL;
             value++) {

            int byteIndex = (int) (value >>> 2);
            int shift = (int) ((value & 0b11L) << 1);

            int b = states[byteIndex] & 0xFF;
            int state = (b >>> shift) & 0b11;

            if (state == 0b10) {
                consumer.accept(value);
            }
        }
    }
}
```

复杂度：

```text
扫描输入          O(N)
扫描完整值域      O(2^32)
payload 内存      1 GiB
```
